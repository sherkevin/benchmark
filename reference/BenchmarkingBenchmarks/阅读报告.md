# BenchmarkingBenchmarks · 工具调用评测的效度审计

> **原文**：Benchmarking the Benchmarks: A Validity Audit of Tool-Calling Evaluation
> **作者**：Vishvesh Bhat, Jay Vaghasiya, Muhammad Ahmed Mohsin, Asad Aali
> **出处**：arXiv:2607.02577，2026-06-30，cs.SE
> **阅读方式**：基于完整摘要与元数据

---

## 0. 一句话

**它审的是"评分器自己准不准"**——把四大工具调用 benchmark 家族的评分结果与专家人工判断逐条比对，发现 **18.5% 的不一致率**，结论是"现在的工具调用分数可能反映的是评分器的假象，而不是 agent 的能力"。

---

## 1. 数据量

| 项 | 数值 |
|---|---|
| 被审 benchmark 家族 | **4 个**：BFCL v4 · τ²-Bench · LiveMCPBench · MCP-Atlas |
| 专家复核任务数 | **496 条** |
| 评分器与人工不一致 | **92 处** |
| 不一致率 | **18.5%** |
| 同配置重复评测 | LiveMCPBench 上 **23 次** |
| 重复评测分数区间 | **57.9% – 76.8%**，跨度 **18.9 个百分点** |

**最刺眼的一个数字**：同一套配置重复跑 23 次，分数能差 18.9 个百分点——**足以改变排行榜结论**。

---

## 2. 它归纳的两类评分器失效模式

这个分类对我们直接有用，因为我们属于左边这一类。

| | 确定性 benchmark（我们属于这类） | LLM 裁判 benchmark |
|---|---|---|
| 失效形态 | **脆弱的状态匹配**（brittle state matching）· **轨迹锁定**（trajectory lock-in）· **真值本身错**（incorrect ground truths）· 基于子串的通信判定失败 · **奖励基准错位**（reward-basis misalignment） | rubric 漂移 · 幻觉式判定完成 · **只看答案不看过程**（answer-only scoring）· 跑与跑之间方差大 |

**逐条对照我们自己**：

| 失效形态 | 我们的暴露面 |
|---|---|
| **brittle state matching** | 我们的 cp 判定基于工具返回记录，不做字符串匹配，**风险低** |
| **trajectory lock-in**（锁定唯一正确路径，别的合理路径被判错） | **须自查** —— 我们的 `no_path_violation` 要求 cp1→cp6 严格拓扑序，若 agent 用另一种合理顺序（例如先建池再查文献）会被判违规。这正是 trajectory lock-in |
| **incorrect ground truths** | 我们有 23 条质量门 + 格位唯一性断言，**风险中低** |
| **reward-basis misalignment** | 我们的 `task_score` 公式把过程分与 gate 绑在一起，口径明确，**风险低** |

## 3. 它的建议：拆解指标

作者主张 **decomposed metrics**——把"工具调用"、"任务完成"、"结果验证"**分开计分**，不要混成一个总分。

**我们的现状**：cp1–cp6 本身就是拆开的（文献/建池/查证/筛选/排序/答案），且 `task_score` 保留了过程分与 gate 两个分量。**这一条我们已经做到，且做得比它建议的更细。**

## 5. 对我方：可借 / 可打点

### 可借（两条，都很实用）

1. **"重复跑比对"必须做**。它用 23 次重复暴露了 18.9 个百分点的方差。我们的矩阵设计是 **3 轮**，**3 轮够不够要看方差**——建议先在少量题上跑 10+ 轮测一下我们自己的跑间方差，若方差大则 3 轮的结论不稳。
2. **评分器自身要有人工对照**。它用 496 条专家复核给评分器定标。我们目前只有"金标准轨迹回放全过 + 非解轨迹不全过"两条机械检验，**没有人工对照集**。

### 可打点（一条，重要）

**`trajectory_lock_in` 是我们 `no_path_violation` 的真实风险**：

我们强制 cp1（文献）→ cp2（建池）→ cp3（查证）→ cp4（筛选）→ cp5（排序）→ cp6（答案）的严格时序。但化学上，"先建候选池再查文献确认方向"也是合理工作流。若 agent 这么做，我们会判它违规并卡 gate。

**这条要么承认是设计约束（在文档里明说"我们规定了唯一合法顺序"），要么放宽为"部分序"（只强制真正有依赖的边，如 cp3 必须在 cp4 前）。** 建议列入待讨论清单。
