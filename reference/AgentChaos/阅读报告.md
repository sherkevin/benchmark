# AgentChaos · 对 agent 系统做混沌工程（ASE 2026）

> **原文**：AgentChaos: Chaos Engineering for Agent Systems via Programmatic Fault Injection
> **出处**：arXiv:2608.06790，2026-08-07，**ASE 2026**，DOI 10.1145/3832783.3837437
> **阅读方式**：基于完整摘要与元数据

## 0. 一句话
**它在 HTTP 层注入 LLM API 故障**（因为所有 agent 系统都走同一个接口），无需改源码。最刺眼的发现：**所有系统在故障下都退化，pass@1 最多掉 50 个百分点**。

## 1. 关键数字
| 项 | 内容 |
|---|---|
| 故障配置 | **65 种** |
| 故障分类 | crash（崩溃）· omission（遗漏）· value（值错误），作用于 content 与 tool call 字段 |
| 注入方式 | **运行时、非侵入式**，在共享的 HTTP 层拦截并改写 LLM API 响应 |
| 关键设计 | **验证每个故障是否真被触发**，以过滤未触发任务、避免低估故障影响 |
| **主结果** | 所有系统都退化，**pass@1 最多下降 50 个百分点** |
| **重要观察** | 排名在不同模型间**一致**，说明**鲁棒性取决于系统实现而非模型能力** |
| 现有诊断方法 | 故障类型准确率 **< 53%**，故障步骤 **< 56%** |

## 2. 机制与判分
注入故障后测 pass@1 下降幅度；另测诊断方法能否识别故障类型与步骤。**判定是硬的**。

## 3. 对我方
**可借（两条）**：

1. **"验证每个故障是否真被触发"这个纪律值得学**。类比到我们：我们的降级模式（`no_recording`/`unavailable`）设计了，但**有没有验证过它们真的会在预期条件下触发**？建议补一个测试：人为制造无录像、gateway 不可用的情形，确认判分器按预期降级而非崩溃或误判。

2. **"鲁棒性取决于系统实现而非模型能力"**这一发现提醒我们：H1 与 H2 的差异可能主要来自实现质量，而非 harness 范式优劣。这与 HarnessOpt-Bench 的"原生 harness 并非一贯更优"呼应。

**可打点**：故障注入是可靠性测试，非能力评测。我们的 benchmark 不含故障注入维度（我们假定工具可靠）。**这是一个可声明的范围边界。**
