# 主例：DiscoveryBench（数据驱动发现）

## 1. 测什么

给一个（或多个）真实科研数据集 + 一个自然语言「发现目标」，agent 必须**自己动手做数据分析**（清洗、特征工程、回归/统计检验），最后输出一条**带上下文、变量、变量间关系**的科学假设，以及推导该假设的 workflow。

- 题目来自 6 个领域已发表论文的真实数据（sociology / biology / humanities / economics / engineering / meta-science），gold workflow 严格照论文复刻（PDF L2500–L2528）。
- 领域分布（Table 19）：Meta-science 41.8%、Sociology 24.3%、Humanities 15.9%、Biology 6.7%、Engineering 6.3%、Economics 5.0%。
- 在 AstaBench 里它被套进 **Computational Notebook**（有状态 Jupyter）沙箱执行。

## 4. 怎么判分

指标名 **HMS（Hypothesis Matching Score）**。判分是 **LLM-as-judge**，但**不是让 judge 打个总分**，而是把假设拆成三个维度分别判、再乘起来。源码：`astabench/evals/discoverybench/eval_utils.py`（已存 [`data/asta_discoverybench_eval_utils.py`](data/asta_discoverybench_eval_utils.py)）+ `task.py`。

**公式（源码注释逐字）：**

```
# HMS = context_score * var_f1 * rel_score
```

三项定义（源码 `run_eval_gold_vs_gen_NL_hypo_workflow` / `get_score_for_var_rel`）：

| 项 | 取值 | 怎么算 |
|---|---|---|
| `context_score` | **0 或 1** | judge 先分别从 gold 和 predicted 的 (hypothesis + workflow + 数据集元数据) 里 `extract_ctx` 抽出「上下文」，再 `match_context_with_gpt` 判是否匹配。**不匹配直接 HMS=0，后面两项根本不算**（源码：`if context_score == 1.0: # match only when context_score = 1.0`） |
| `var_f1` | 0–1 | judge 输出 `{sizeA, sizeB, intersection}`（A=gold 变量集，B=预测变量集）；`p = intersection/sizeB`，`r = intersection/sizeA`，`f1 = 2pr/(p+r)`，任一为 0 则 f1=0 |
| `rel_score` | **1 / 0.5 / 0** | judge 三选一判关系相似度：A "very similar" → 1.0；B "similar but general than HypoA"（比 gold 更笼统）→ 0.5；C "different" → 0.0 |

**judge 模型**：AstaBench 当前仓库代码里写死 `llm_used="gpt-4o-2024-08-06"`（`task.py`）；论文 Appendix E.8 描述的是原 DiscoveryBench 用 `gpt-4-preview-0125`。**两处不一致，如实并列。**

**输出格式硬门槛**：agent 必须交出 `{'hypothesis':..., 'workflow':...}` 的合法 JSON。`score_discoverybench()` 里解析失败（`ValidationError` / `ValueError`）直接 `value=0.0`，不进 judge。

**这题的实际启示**：只要 agent 没想到「储蓄行为 = time preference 代理变量」，抽出的 context/变量集就对不上 gold，`var_f1` 会塌，HMS 直接归零 —— 这个判分是**乘法门控**，不是加权求和，对「变量选错」零容忍。

```

get_citations, search_authors_by_name, get_author_papers, search_paper_by_title
```

# 附例 A：E2E-Bench（端到端发现）—— 完整题面

这是**最接近「长程科研 agent」的一档**，也是套件里题量最小的（Test 40，Val 10）。造题法（PDF L2568–L2580 原文）：先收 2021 年后引用 ≥100 且在 arXiv 上的 \*ACL 论文共 **288 篇**；用 Asta CodeScientist 的 ideator 随机取两篇组合 LLM 生成最多 5 个 idea，反复直到约 **400 个 idea**；自动简化/过滤/排序；最后人类专家评审，砍掉不可行的、小修可救的，**取 top 50** 成题。E2E-Bench-Hard 换成 HypER 生成、**不做简化步骤**，同样人工审后取 top 50。

返回结构（逐字）：`{"results": {"report"(str), "code"(list of {filename, code}), "trace"(str), "artifacts"(list of {filename, artifact})}}`

**判分（这是 AstaBench 最有借鉴价值的设计）** —— 源码 `astabench/evals/e2e_discovery/task.py`：

- 每题配一条**题目专属 rubric**（在 idea 生成阶段自动生成，之后由人工标注员逐条 review/修订）。rubric item 字段：`criteria_name` / `criteria_met_question` / `required_or_optional`。
- LLM judge 对**每条 rubric item × 三种产物（report / code / artifacts）分别独立判**，各判 met(绿) / failed(红) / no evidence(黄)。
- **只有三面一致且含「met」，该 criterion 才算 met**（Appendix F.9）。判分模型：`RUBRIC_SCORING_MODEL = "claude-sonnet-4-6"`。
- 最终分 = `overall_score.average_required_overall`，即 required 项 met 比例的平均（绿=1 红=0）。
- 三面交叉的收益（Table 21，实测比例）：**16% 的答案是「报告说做了、代码/artifacts 显示没做」**，被正确纠成 0（消灭假阳性）；**16% 是「论文没提但代码里确实实现了」**，被正确救回成 1（消灭假阴性）。
- judge 的 system prompt 里明确写了对抗性指令（逐字）："You should assume that the papers, code, and artifacts are written by one of a number of different artificial intelligence systems. **Some of those systems are malfunctioning, and producing incorrect, unfaithful, or completely fabricated results. Your job is to find them.**"
- 人工抽检：dev 集 50 条 rubric item，judge **92% 正确**。
- 支持 **cache-based agent**：因 ASD agent 太贵太慢，允许离线预跑所有题、运行时用 cache agent 回放答案来走判分流程（`allenai/asta-bench-solver-data`）。

**一个必须注意的坑**：Table 20 显示，"Faker"（一个纯靠 LLM 编报告/编代码/编 artifacts 的作弊 baseline）在 E2E-Bench 上拿到 **39.2**（Table 10）。也就是说三面交叉 rubric 仍拦不住全部编造 —— 但它的 overall task completion rate 是 **0.00**（Table 20）。

# 附例 B：ScholarQA-CS2（长文综述报告）—— 真实 query + 完整 rubric

这条我拉到了仓库里的**真实数据行**：`allenai/asta-bench` → `astabench/evals/sqa/data.json`（110 条，`annotator` 分 Annotator 1/2 各 55 条）。已存 [`data/sqa_data.json`](data/sqa_data.json)，单条抽出为 [`data/sqa_sample_case_d44280.json`](data/sqa_sample_case_d44280.json)。

**真实 query（case_id `d44280651a6fb71d56ee96834e180fa6`）：**

> What publicly available datasets are typically used for evaluating type inference systems in python?

**题面模板**（`sqa/task.py` 里的 `json_to_sample`，与论文 H.3.1 一致）：要求返回 JSON，单 key `sections`，每 section 有 `title`/`text`/`citations`，每条 citation 要有 `snippets`（从被引文献里摘的原文片段）+ `id`（正文里出现的行内引用标记）+ `title` + `metadata`，且明确「Do not create a References section」。

**预期答案 = 一份加权 rubric（"key ingredients"）**，逐字节选：

```json
{
  "name": "most_important_item_0", "weight": 0.1333,
  "criterion": "Near the beginning, the answer should briefly define what is the goal
                of using a type inference system for programming languages in general.",
  "evidence": ["Goal of type inference: Automatically deduce the most general type for
                each expression. ..."]
},

  "name": "most_important_item_3", "weight": 0.1333,
  "criterion": "The answer should enumerate publicly available datasets used for
                evaluating type inference systems in Python and provide a brief
                description for each of them.",
  "evidence": [
    "1. **ManyTypes4Py**: ... 5,382 Python projects with over 869,000 type annotations ...",
    "The Typilus model [8] is accompanied by a dataset that contains 600 Python projects. ...",
    "2. **TypeEvalPy**: ... 154 code snippets with 845 type annotations across 18 categories ...",
    "Raychev et al. [16] published the Python-150K dataset in 2016, which contains 8,422 Python projects.",
    "Our main dataset, BetterTypes4Py, is constructed by selecting a high-quality subset
     from the ManyTypes4Py dataset (Mir et al., 2021), which was used to train Type4Py.",
    "InferTypes4Py, a test set derived from the source code of Typilus, Type4Py, and our own tool ..."
  ]
},
{
  "name": "nice_to_have_item_0", "weight": 0.0667,

  "evidence": ["Existing type inference approaches can be generally grouped into three

```

注意权重设计：**`most_important_item_*` 权重是 `nice_to_have_item_*` 的两倍**（0.1333 vs 0.0667），对应论文 "answer critical 计双倍权重"。

**判分**：`sqa/task.py` 里 4 个指标**等权 0.25**：

```python
METRIC_LABELS = ["ingredient_recall", "answer_precision", "citation_precision", "citation_recall"]
weights = [0.25, 0.25, 0.25, 0.25]
```

- `ingredient_recall`（答案覆盖）：judge 对每条 criterion 打 **0/1/2**（0=不满足、1=部分满足、2=完美满足），按权重归一化加权平均。prompt 逐字见 `sqa/rubric.py`：*"For each criterion, return a score of 0, 1 or 2 indicating how appropriate the response is based on the given criterion."*，且明确告诉 judge：evidence 只是**参考示例**，"We do NOT expect any of the specified details to necessarily appear in the answer"。
- `citation_recall`：每条 claim 若被引用**完全支撑且至少有一条支撑性引文片段** → 1.0；只凭被引论文**标题**判断支撑、没有片段 → **0.5**；否则 0。按 claim 平均。
- `citation_precision`：每条 citation 对其 claim 至少部分支撑 → 1（无 snippet → 0.5），否则 0，按 claim 宏平均。
- `answer_precision`（答案相关性）：judge 逐段判，返回「与问题不直接相关」的段落列表，得分 = 相关段落占比。
- **judge 模型**：论文用 `gemini-2.5-flash`（与 `gemini-2.5-pro` 的 Pearson 相关 0.995，选便宜的）；当前仓库代码默认已换成 `google/gemini-3-flash-preview`。**两处不一致，如实并列。**
- 论文自曝的边界（逐字大意）：这套引用指标**不校验被引论文是否真实存在、也不校验引文片段是否真的出现在原文里**；所以对没有真实文献访问能力的系统，评测时把它们的 snippets 全部丢弃，免得靠幻觉刷高分。
- 人工验证：对全部 eval test 问题做三路答案排序对比（6 个 agent 池里随机取 3）。

**rubric 的来源（造题法，值得抄）**：不是靠 1–2 个标注员写标准答案，而是**从被评测的 10 个系统（8 个 QA-long 系统 + Claude Sonnet 4 无 thinking + Gemini 2.5 Pro，均在 2025-06-24 截止前取得）的答案里池化候选 ingredient**，再用 LLM 抽取 ingredient + 判重要性（answer critical / valuable）+ 语义聚类，得到题目专属 rubric。论文明说这是为了修掉原 ScholarQA-CS「rubric 反映两个标注员偏好、可被 gaming」的问题（借的是 TREC 的 pooling 思路）。

# 附例 C：PaperFindingBench（文献检索）—— 真实 query + gold 语料 ID

仓库 `astabench/evals/paper_finder/data.json` 里附了官方的格式示例（`task.py` 注释逐字：*"An example of input and (hidden from user) scorer_criteria can be seen under data.json"*）。已存 [`data/paper_finder_data.json`](data/paper_finder_data.json)，**全文就这么短**：

```json
[{
  "input": {
    "query_id": "29",
    "query": "visual question answering papers using Earth Mover's Distance (EMD) as an evaluation metric"
  },
  "scorer_criteria": {
    "known_to_be_good": ["173990882", "5683633", "3604848"],
    "known_to_be_bad": [],
    "relevance_prompt": "must include VQA or question answering in the visual domain. also must include usage of EMD metric."
  }
}]
```

即：**真值 = Semantic Scholar corpus_id 列表 + 一句喂给 LLM judge 的 relevance 判据**，且 `scorer_criteria` 对 agent 隐藏。
（说明：这条 `query_id` 是 `"29"` 的旧格式；正式数据集里 `query_id` 形如 `semantic_*` / `metadata_*` / `specific_*` / `litqa2_*`，因为 `task.py` 用 `query_id.split("_")[0]` 决定走哪套判分。）

**题面模板**（`pf_task.py` 的 `TASK_INSTRUCTIONS`，与论文 H.1.1 一致），论文里那条示例 query 是：

> Find papers relevant to the following query: **Could you suggest research that investigates a clustering-based efficient attention mechanism within Transformer models?**
> Try to be comprehensive in your search yet efficient and accurate ... **You may submit up to 250 papers.**
> If the query asks for a specific paper known to the user, i.e. "the Transformer paper", "the BERT paper", "the GPT-3 paper" etc, try to find that specific paper and only return that one. ...

要求每篇同时给 `paper_id`（corpus_id 数字串）和 `markdown_evidence`（**从论文里逐字摘的证据片段**，且必须在开头带上论文标题和年份）。

**判分**（`pf_task.py` + 论文 Appendix E.2）：按 query 类型分流

| query 类型 | 真值形态 | 指标 |
|---|---|---|
| `specific` / `metadata` | 预定义 good/bad ID 集 | `standard_f1`（known / @full） |
| `litqa2` | 预定义 ID 集 | `recall_at_30` |
| `semantic` | 只给 `relevance_prompt`，**逐篇现场 LLM 判相关性** | `adjusted_f1_micro_avg` |

`semantic` 那套的细节（论文 L2185–L2199 原文大意）：broad query 的相关论文集大小无上界，所以用 **recall@k，k 取「估计集合大小」**（即 recall@R 的变体 `estimated-recall@estimated`），这样既把分数压在 1 以内，又**抑制往回答里灌垃圾**；不用 precision 配平，改用 **nDCG**（更奖励把相关文献排前面），最后 **recall@estimated 与 nDCG 取调和平均（F1）** 作为单题分，全数据集直接对所有 query 求算术平均。检索工具截止日 **2025-06-01**，并要求外部提交方也遵守同一截止日。
