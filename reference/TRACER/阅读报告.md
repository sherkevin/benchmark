# TRACER · 多模态工具 agent 的可验证生成溯源（TRACE-Bench）

> **原文**：TRACER: Verifiable Generative Provenance for Multimodal Tool-Using Agents
> **作者**：Bihui Yu, Caijun Jia, Jing Chi, Xiaohan Liu, Yining Wang, He Bai, Yuchen Liu, Jingxuan Wei, Junnan Zhu
> **出处**：arXiv:2605.09934，2026-05-11，cs.CL
> **阅读方式**：基于完整摘要与元数据

---

## 0. 一句话

**它命名了一个我们也在解决的问题：provenance gap（溯源缺口）**——

> 现在的工具型 agent 通常会把「执行过的工具轨迹」和「最终答案」都暴露出来，但**很少说明哪一条工具观测支撑了哪一句生成的断言**。

这句话几乎是我们"真值从 tool call 反查"这条设计的问题陈述。区别是：它用生成式方法**补上**这个缺口（让 agent 自己产出溯源记录），我们用判分器**绕过**这个缺口（不看 agent 说什么，直接查工具记录）。

## 1. 数据量与成绩

| 项 | 数值 |
|---|---|
| 提出的 benchmark | **TRACE-Bench**，做句子级溯源重建 |
| 任务形态 | 从粗粒度的多模态工具轨迹中，重建"每句话由哪条证据支撑" |
| 主结果（Qwen3-VL-8B + TRACER） | 答案准确率 **78.23%**，摘要准确率 **95.72%** |
| 相对最强闭源工具增强基线 | **+23.80 个百分点** |
| 工具调用量 | 从 **4,949 次降到 3,486 次**（比纯工具 SFT 更省） |

**一个反直觉发现**：`simply adding tools often introduces noise`（单纯加工具常常引入噪声）——工具调用多不等于效果好。

## 2. 核心机制：三类语义支撑关系

TRACER 不是事后加引用，而是**在生成每句答案的同时**产出一条结构化溯源记录，记录里含三样东西：

1. **supporting tool turn**（支撑它的那一轮工具调用）
2. **evidence unit**（证据单元）
3. **semantic support relation**（语义支撑关系）

关系空间只有三类，这个分类很值得抄：

| 关系 | 含义 | 对应场景 |
|---|---|---|
| **Quotation**（引用） | 直接复用 | 原样搬运工具返回值 |
| **Compression**（压缩） | 忠实凝缩 | 把工具返回的一堆数总结成一句 |
| **Inference**（推断） | 有依据的推导 | 基于工具返回值推出新结论 |

---

## 3. 判分粒度与验证方式

**四道验证**（对每条溯源记录）：

1. **schema checking** —— 格式对不对
2. **tool-turn alignment** —— 引用的那轮工具调用真的存在吗
3. **source authenticity** —— 来源是真的吗
4. **relation rationality** —— 声明的关系类型合理吗

验证通过的溯源随后被转成两样东西：**可追溯性约束** + **溯源导出的局部 credit**（用于强化学习）。

## 4. 对我方：可借 / 可打点

### 可借（一条很有价值）

**三类支撑关系（Quotation / Compression / Inference）可以用来细化我们的 cp3**。

我们现在的 cp3 是"覆盖性检查"——该查的 ID 都查过了就给分。但这只能判"查没查"，判不了"**查到的东西有没有被用对**"。如果借它的分类：

- agent 报的性质值与工具返回值完全一致 → Quotation，最硬
- agent 做了聚合/比较 → Compression，需检查聚合是否正确
- agent 推出了工具没直接给的结论 → Inference，最需要警惕

**这可能是 cp3 的一个升级方向**，但要注意：判定 Compression/Inference 的正确性可能需要语义判断，会破坏我们"全硬判定"的边界。**所以只建议引入 Quotation 一类的严格比对（数值对账），其余两类不引入。**

### 可打点

- 它的 TRACE-Bench 是**多模态**（视觉工具为主），任务域与我们不重叠，不构成直接竞争。
- 它把溯源用于 **RL 训练信号**，与我们"纯评测不训练"的定位不同。这也提醒：我们的 cp 若被用于训练，同样会面临 OpenAI CoT 监控那篇指出的"优化过头则伪装"风险。
