## 0. 一句话总结

TRACE-Bench 不是一个新采集的任务集，而是**在 ToolVQA（ICCV 2025）已有的多模态工具轨迹上，加一层"句子级溯源标注"**：把"agent 调了哪些工具"这种粗轨迹，改写成"答案的第 i 句话，由第几轮工具的哪一段输出、以何种关系支撑"。判分判的是这层标注的真假。

## 1. 测什么

### 1.1 问题定义：provenance gap（溯源缺口）

> "Current tool-using agents usually expose the executed tool trajectory and the final answer, but they rarely specify **which tool observation supports each generated claim**. We call this missing claim-level dependency structure the **provenance gap**."
> ——Abstract

缺口的后果（Introduction 原文）：

> "If the final answer does not state which observations support which claims, a correct response may come from **faithful tool use, parametric memory, accidental guessing, or ungrounded inference**."

### 1.2 任务形态

给定输入 `x = (q, M, H₀, U)`：问题 q、多模态上下文 M（图）、可选历史 H₀、工具集 U。
模型产出的不是单一答案 `y`，而是 `(y, G)`：

- 答案按句切分 `y = (s₁,…,s_N)`
- 每句 sᵢ 配一组溯源项 `Pᵢ = {(ℓᵢⱼ, zᵢⱼ, rᵢⱼ)}`
  - `ℓᵢⱼ` = 工具轮次 ID（如 `OCR_1`、`Calculator_2`）
  - `zᵢⱼ` = 被引用的证据片段 / 定位到的多模态证据
  - `rᵢⱼ ∈ {Quotation, Compression, Inference}`
- 溯源图 `G = {(sᵢ, Pᵢ)}`

### 1.3 数据规模（Table 3，原文数值）

| 项 | 值 |
|---|---|
| 保留实例 | **14,183**（从 23,655 候选过滤，保留率 59.96%） |
| 切分 | train 10,470 / val 1,163 / test 2,550（沿用 ToolVQA 官方 held-out test） |
| 总工具调用 | 40,491 |
| 溯源记录总数 | 36,431（平均 2.57 条/例，1.07 条/句） |
| 平均 query 长度 | 15.46；平均 response 长度 78.43 |
| 平均推理句数 | 2.4 句 / 2.56 条锚定溯源 |
| 关系分布 | **Quotation 24,239（66.5%）/ Inference 8,364（22.9%）/ Compression 3,828（10.5%）** |

工具调用分布：ImageDescription 12,594、GoogleSearch 9,666、OCR 5,801、Calculator 3,281、TextToBbox 3,094、RegionAttributeDescription 3,094、CountGivenObject 2,961。

## 2. 真实 query 原文

论文 5.3 Case Study / Figure 4 用的就是这一条。我把它与上游 ToolVQA released `dataset.json` 的**第 1501 条**对上了（该条同时命中 "motorcycle racing" + "July 10, 1955" + "Yamaha"，全库唯一）。

### 2.1 论文 Figure 4「Problem Description」区块（PDF 矢量文本，逐字）

```
Question: "When did one of the manufacturers displayed in this image first enter motorcycle racing?"
Ground Truth:  July 10, 1955
Required Path: Image → Identify Yamaha → Search racing history → July 10, 1955
```

### 2.2 多模态输入（实拉图片）

- ToolVQA 原始路径：`/network_space/server126/shared/yinshaofeng/ToolLLM/GTA/datasets/COCO2017/train2017/train2017/000000394002.jpg`
- 即 **COCO 2017 train / 000000394002.jpg**，已下载至 `figs/coco_000000394002.jpg`（640×427）
- 图片内容（人工核对）：室内车库里并排停放的复古赛车摩托，整流罩上有 **YAMAHA** 字样、号码牌 **4 / 1-2 / A64**、金色轮圈

> 这张图直接解释了论文 Figure 4 里 OCR 的返回值 `"YAMAHA 4 12 A64"` 和 RegionAttributeDescription 的返回值 `"... gold-colored wheels and no prominent factory branding."`——都是图上真实可见的内容。

### 2.3 上游真实工具轨迹（ToolVQA instance 1501，逐字，完整）

**该实例声明的可用工具**（4 个）：`ImageDescription`、`GoogleSearch`、`Calculator`、`TextToImage`

**Turn 1 — user**
```
When did one of the manufacturers displayed in this image first enter motorcycle racing?
```

**Turn 2 — assistant（thought + tool_call）**
```
thought: "To answer the question about motorcycle racing, I first need to identify the
manufacturers present in the image. Using the ImageDescription tool, I can analyze the
visual information, logos, and branding on the motorcycles to recognize relevant
manufacturers. This directs me to a specific manufacturer—in this case, Yamaha."

tool_calls: ImageDescription(image="/.../train2017/000000394002.jpg")
```

**Turn 3 — tool (ImageDescription) 返回**
```
"The image shows a lineup of vintage racing motorcycles parked indoors, likely in a garage
or pit area. The bikes have aerodynamic fairings with number plates, visible branding and
logos. The motorcycles appear to be models from Yamaha and other manufacturers, and they
feature distinctive racing liveries with various color schemes. Several gold wheels and
slick tires are also visible, highlighting their performance-oriented design."
```

**Turn 4 — assistant（thought + tool_call）**
```
thought: "Upon identifying Yamaha as one of the manufacturers in the image, I can proceed
to research when Yamaha entered motorcycle racing. By using the GoogleSearch tool, I
specifically ask about Yamaha's history in racing. This search reveals the exact
date—July 10, 1955—when Yamaha first became involved in motorcycle racing."

tool_calls: GoogleSearch(query="When did Yamaha first enter motorcycle racing?")
```

**Turn 5 — tool (GoogleSearch) 返回**
```
"1 - Answer box: Yamaha's 60 years in Grand Prix Racing Motorsports have been an essential
part of Yamaha Motor's corporate culture since our founding, and the first time a Yamaha
motorcycle competed in earnest happened 10 days after the company was established, at the
third Mount Fuji Ascent Race on July 10, 1955."
```

**Turn 6 — assistant（final）**
```
"July 10, 1955"
```

**gt_answer**（ToolVQA 判分口径）
```json
{"whitelist": [["1955"]], "blacklist": []}
```

> **注意**：这就是 TRACE-Bench 所谓的 "coarse tool trajectory"（粗轨迹）——它有 thought、有工具调用、有工具输出、有参考答案，**但没有任何一句话说"最终答案的哪一句由哪一段工具输出支撑"**。TRACE-Bench 要补的正是最后这一层。

## 3. 预期答案：一条 provenance record 长什么样

### 3.1 官方 JSON schema（Appendix D / Figure 6 生成器 prompt，逐字）

```json
{
  "role": "assistant",
  "content": {
    "response": "...",
    "sentence": [
      {
        "sentence_id": 1,
        "text": "...",
        "provenance": [
          {
            "tool_id": "...",
            "source_text": "...",
            "relation": "..."
          }
        ]
      }
    ]
  }
}
```

### 3.2 字段硬约束（Appendix D 原文要点）

- **tool_id 命名**：`tool_id = <context[i].name>_<i>`，`i` 从 1 开始（**按轨迹位置编号，不是按该工具第几次被调用**）。示例：`ImageDescription_1`、`OCR_2`、`GoogleSearch_3`。
- **source_text**：**必须是对应 `context[i].output` 的精确子串（逐字符匹配）**，禁止编造。最终答案句的溯源必须引用直接支撑答案的那段工具输出（通常是提供关键数字/事实的最后一个关键工具输出）。
- **relation**：三选一（见 3.4）。若用 Inference，`source_text` 必须包含推导所需的关键事实（如年份/数字）。
- **response 的信息来源被限死**：只能来自 `context[i].thought`（按 i=1..n 顺序整合改写）+ `answer`（仅作最终结论）。不得引入 context.thought / answer 之外的新事实。
- **句子必须能还原 response**：所有 sentence.text 按 sentence_id 拼接后必须严格还原 response；response 里不许有不在 sentence 列表里的句子，反之亦然。
- 每句**至少 1 条** provenance。

### 3.3 本条实例的 gold provenance（论文 Figure 4，逐字）

TRACER-RL（正确 + 简洁 grounded path，2 轮工具）：

```
Response excerpt: "... we first confirm the brand ... Yamaha. We then review Yamaha's
                   racing history ... July 10, 1955."

Final Provenance:
  • Sentence 1 → ImageDescription_1 → Yamaha
  • Sentence 2 → GoogleSearch_2 → July 10, 1955
```

TRACER-SFT（同样答对，但轨迹里多调了 OCR）：

```
Response excerpt: "... Yamaha is identified ... official debut ... July 10, 1955."

Final Provenance:
  • Sentence 1 → ImageDescription_1 → Yamaha
  • Sentence 2 → GoogleSearch_3 → July 10, 1955
  • OCR → not cited
```

> **注意 `GoogleSearch_3` vs `GoogleSearch_2`**：同一个 GoogleSearch，SFT 记为 `_3`、RL 记为 `_2`，因为 SFT 轨迹是 ImageDescription→OCR→GoogleSearch（位置 3），RL 轨迹是 ImageDescription→GoogleSearch（位置 2）。这正好印证 3.2 里"按轨迹位置编号"的规则。
>
> 论文 Figure 4 对 TRACER-SFT 的诊断原文：
> "Phenomenon: OCR appears in the tool trajectory, but no final claim cites OCR. Diagnosis: Correct answer, but one called tool is ignored."
> 这是 provenance 机制最核心的价值演示：**被调用 ≠ 被使用**。

### 3.4 三种关系怎么标（Table 5，逐字，含官方示例——恰好也用这条 Yamaha 例子）

| Relation | Definition | Example |
|---|---|---|
| **Quotation** | The claim directly reuses or reports information explicitly stated in the tool observation, with minimal semantic transformation. | OCR returns "Yamaha", and the claim states that the visible text reads "Yamaha". |
| **Compression** | The claim faithfully condenses a longer or redundant observation into a shorter statement without introducing new reasoning. | An image description lists multiple visual details, and the claim summarizes that the image shows a Yamaha-branded motorcycle. |
| **Inference** | The claim is derived by combining, comparing, or computing over one or more evidence units, while remaining grounded in the cited observations. | A search result gives the first racing date and the image identifies the manufacturer; the claim answers when that manufacturer first entered motorcycle racing. |

Figure 3 的构造流水线示意给出了**完整字段填好的两条记录**（query: "How much does the red drink cost?"）：

## 4. 怎么判分

### 4.1 六个指标（Table 1 + Appendix B.4）

| 指标 | 定义（B.4 原文要点） |
|---|---|
| **Acc.** | 原 VQA 任务最终答案是否正确（端到端，可调工具） |
| **SummAcc.** | **给定**一条工具轨迹、**不允许再调工具**，模型能否从中推出正确答案——隔离"整合/总结已观测证据"的能力 |
| **Traceability Acc.** | **LLM-as-a-judge（judge model = Gemini-2.5-Pro）**：逐条检查 ①引用的 tool_id 是否对应真实工具调用 ②引用证据能否回溯到该工具观测 ③关系标签是否语义合理。**必须全过才算 traceable** |
| **Prov. Precision / Recall / F1** | 与 test set 的 reference provenance 标注比对；每条标注视为一个「证据–断言链接 + 关系类型」。P = 预测链接中正确的比例，R = 参考链接被召回的比例 |
| **Tool Call** | held-out test 上的工具调用总数（越低越好） |
| **Tool Error** | 工具报错总数（越低越好） |

### 4.2 四层验证（对每一条溯源项）

Method §3.2 的形式化：

- `C_schema ∈ {0,1}`：输出合法、每句有编号、每句至少一条 provenance
- 逐项返回 `v_ij^turn`（引用的工具轮次是否存在）、`v_ij^src`（引用来源是否真实）、`v_ij^rel`（声明的关系是否支撑该句）
- 项级有效性：**`v_ij = v_ij^turn · v_ij^src · v_ij^rel`**（乘积，一项挂全挂）

Figure 2 (C) 的两段式画法：

```
(1) Format Check                    (2) Semantic Verification
    JSON schema valid                   Tool & Turn Alignment
    Sentence id complete                Source Authenticity
    Provenance attached                 Relation Rationality
```

**验证器 prompt（Appendix D / Figure 7，逐字要点）**，输出结构化 JSON：

```json
{
  "overall_correct": true/false,
  "error_details": ["Error 1 description", "Error 2 description"],
  "sentence_check": [
    {
      "sentence_id": 1,
      "tool_id_correct": true/false,
      "source_text_correct": true/false,
      "relation_correct": true/false,
      "sentence_correct": true/false
    }
  ]
}
```

验证器三条规则（逐字）：
1. **Tool and Round Validation** — `tool_id` 格式 `ToolName_Number`，且"Number = the N-th time this tool is called"，须与 messages 中 tool_call 顺序完全一致
2. **Source Authenticity Validation** — `source_text` 必须完整来自该 tool_id 轮次的原始 `tool_response`，**不允许编造、拼接、替换或不存在的内容**
3. **Text and Relation Rationality Validation** — 逐 sentence_id 判 Quotation/Compression/Inference 是否与 text↔source_text 的实际变换匹配

### 4.3 训练侧奖励（评测之外，但同一套验证器）

- 答案奖励 `R_vqa = 𝕀[Eval(y) = y*]`
- 引用效率奖励 `R_cite = |T_cited| / max(|T_called|, 1)`——**惩罚从未支撑最终回答的工具调用**
- 可追溯性奖励（**硬闸门**）`R_trace = C_schema · ∏_i ∏_j v_ij`——只有每一条溯源项全过才等于 1
- 总奖励 `R_total = R_vqa · R_trace · (w₀ + w_cite · R_cite)`
  > "This design treats traceability as a **strict requirement rather than a soft bonus**: an answer with fabricated or unsupported provenance receives **zero** training reward."
- 工具轮局部 credit `c_t = R_vqa · R_trace · min(1, Σ_ij 𝕀[ℓ_ij = ℓ_t] · v_ij)`——某轮工具只有在"为一个正确且完全可追溯的答案提供了已验证证据"时才拿分

### 4.4 数据集自身的三阶段过滤（§4.2 / C.4）

1. **Stage 1 Outcome Consistency + Schema Validation**：重建答案须与参考答案语义一致（矛盾的直接删——否则溯源解释的是错误推理路径）；规则解析器校验 JSON schema，解析错误/畸形/缺句级溯源/非法 relation/不存在的 tool id/证据字段不全 → 丢弃
2. **Stage 2 Counterfactual Evidence Removal**：把某条被引证据**移除或 mask**、其余轨迹完全保留，重新评估答案与溯源。**答案/溯源变了 → 保留（evidence-sensitive）；没变 → 说明该引用冗余、可由别处恢复、或已在参数化知识里 → 过滤**。原文明确这只是"conservative filtering signal"，不当作因果必要性的绝对证明
3. **Stage 3 LLM-as-a-Judge Provenance Verification**：深查 trajectory alignment（每个 tool_id 都对应真实调用、每段证据都真能回溯）+ relation rationality；含"unsupported evidence / incorrect tool alignment / implausible evidence–relation–claim triples"的记录永久删除

**常见 provenance 失效模式（C.3 原文）**：malformed schema、缺句级证据、无效 tool-turn 引用、证据单元无法对齐到所引观测、relation 标签与实际变换不符、反事实移除下证据不敏感。举例："a model may call OCR but never use the OCR result in any final claim, or cite a retrieved snippet while actually relying on a previous visual description."

## 5. Agent 工具清单

### 5.1 TRACE-Bench 保留的 7 个工具（Table 4，逐字）

| Tool | Function | Observation Type |
|---|---|---|
| **ImageDescription** | Produces a global description of the input image, including salient objects, scene layout, visual attributes, and visible entities. | Global visual description |
| **OCR** | Extracts text visible in the image. | Recognized text |
| **TextToBbox** | Grounds a textual object or phrase to its corresponding image region. | Bounding box or grounded region |
| **RegionAttributeDescription** | Describes attributes of a specified image region, such as color, shape, texture, or local semantics. | Region-level visual description |
| **CountGivenObject** | Counts instances of a specified object category in the image. | Object count |
| **GoogleSearch** | Retrieves external textual knowledge for open-domain entity or fact verification. | Retrieved textual snippet |
| **Calculator** | Performs deterministic arithmetic or symbolic computation. | Computed value |

覆盖面：global visual perception / localized inspection / OCR / counting / retrieval / deterministic computation。

### 5.2 工具与关系的亲和性（C.2，原文数值）

- **Quotation 24,239 条**中：ImageDescription **8,463**、OCR **4,987** 占绝对主导——"视觉模型倾向优先引用抽取到的几何与文本属性，作为推理的事实锚点"
- **Inference 8,364 条**中：GoogleSearch **4,029**、Calculator **2,080** 亲和性极强——单纯视觉引用不足以解题，需外部检索引入背景 / 把引用到的数值送进计算器做符号推导
- **Compression 3,828 条**中：ImageDescription **1,899**、GoogleSearch **1,101**——这两类工具返回文本常含大量冗余，模型自发做摘要降噪

### 5.3 本条实例（ToolVQA 1501）声明的可用工具

`ImageDescription`、`GoogleSearch`、`Calculator`、`TextToImage`（注意 `TextToImage` 不在 TRACE-Bench 保留的 7 个之内——TRACE-Bench 是从源轨迹里"retained"了 7 个工具）

### 5.4 同一条题上四种 agent 的行为对比（Figure 4，逐字）

| # | 系统 | 结论 | 轨迹 | 诊断（原文） |

## 7. 对我方的可用点（一句话）

这条例子最硬的价值不在 78.23% 这个数，而在 **Figure 4 第 1 行**：TRACER-SFT 答对了、工具也调了、轨迹看起来完整，但 **OCR 这一轮从头到尾没有任何一句断言引用它**。"调过 ≠ 用过"这件事，只有句子级溯源能看出来，覆盖性检查（该查的都查了就给分）看不出来。

同时要注意它的边界：`v_ij^src`（source_text 必须是工具输出的精确子串）是**可硬判的**，`v_ij^rel`（关系是否合理）在论文里是**用 Gemini-2.5-Pro 当 judge 判的**——也就是说四层验证里有一层是软判定。若要借这套机制，Quotation 的严格子串比对可以直接硬化落地，Compression / Inference 的合理性判定则会引入 LLM judge 依赖。
