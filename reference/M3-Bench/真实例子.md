# M³-Bench 完整真实例子（Fish 任务 · id=00050000）

> 全部内容来自实拉的论文全文（arXiv:2511.17729v4 HTML）与实拉的官方数据文件（HF `test_mcp_GT.json` / `test_mcp_fuzzy.json`）。逐字引用处标注来源，未做任何改写或补全。

---

## 0. 一句话

给一张鱼的照片 + 一句大白话请求，agent 要**先靠视觉认出物种**，再串起 wiki/天气/路线/周边 POI 共 5 个 MCP 工具、4 步（其中第 1 步 2 个调用并行）产出一份可执行钓鱼行程；判分把**工具调用逐个匈牙利匹配对齐**后分开算「参数语义忠实度」和「工作流结构一致性」，再加 4 个 LLM 裁判评端任务。

---

## 1. 测什么

**任务族**：`(5) Fish`，28 个任务族之一，该族共 **11 条**轨迹实例（`type=="fish"`）。

论文对该族的官方定义（§6.1 逐字）：

> **(5) Fish** Plan a New Jersey fishing trip for the detected species.
> 1. Use wiki/summary to summarize the detected fish species.
> 2. Use wiki/search to search for the top spot for fishing in NJ recently.
> 3. Call weather/get_weather for local conditions at the spot.
> 4. Use google-maps/compute_route to plan a route from a default start.
> 5. Use google-maps/places_nearby_search to search for restaurants and bait shops.

**考的三个「M」**（论文 §1 定义）：

| 维度 | 在本例中的体现 |
|---|---|
| **Multi-Modal** | 物种名不在文字里，只能从图片认出来；认错则后续所有调用的参数全错（论文称 visual grounding 是 MCP 轨迹的核心难点） |
| **Multi-Hop** | 4 步且后步消费前步产物：先定物种→定钓点→查该点天气→算到该点的路线→搜该点周边（`L≥2` 且存在跨步依赖边） |
| **Multi-Threaded** | Step 1 内 `wiki/summary` 与 `wiki/search` 互不依赖，**同一步并行发出**（步内无依赖边，顺序无关） |

**Fuzzy task description**：给模型的是模糊自然语言，不给工具清单、不给轨迹（论文 Table 1 中 M³-Bench 独有勾选项之一）。

## 4. 怎么判分

三层，**调用级不用 LLM**，只有端任务级用 LLM。

### 4.1 先对齐：Similarity-Bucketed Hungarian Alignment（§4.1）

1. **序列化**：每个调用 `c = (tool(c), args(c))` 用 `φ(·)` 拍平成规范文本签名，保留工具名、必需参数、顺序无关集合。
2. **嵌入 + 余弦**：句子编码器 `E` 得 `S_ij = cos(x*_i, x̂_j) ∈ [-1,1]`。
   代码实测默认：`sentence-transformers/all-MiniLM-L6-v2`（`evaluate_trajectories.py:667`）。
3. **按工具名分桶**：`I_k = {i | tool(c*_i)=k}`、`Ĵ_k = {j | tool(ĉ_j)=k}`，**只允许同名工具配对**（防止跨工具骗分）。
4. **代价矩阵 + 匈牙利**：`C_rc = 1 - S_rc`（若 `S_rc ≥ τ_weak`），否则罚值 `λ_pen`；每桶内解线性分配 `min ⟨C, Π⟩`（Kuhn–Munkres），只保留 `S_ij ≥ τ_weak` 的可行对，得全局匹配集 `M`。
5. **阈值**：`(τ_strong, τ_weak) = (0.8, 0.6)`，由 40 对人工标注（strong/medium/weak 多数投票）扫参标定（§6.4）。代码默认值一致：`--tau-strong 0.80 --tau-weak 0.60`。

三个刻意的设计选择（§4.1「Properties and rationale」）：
- **tool bucketing** → 不给跨工具的分；
- **step agnosticism**（对齐不要求同一步）→ 允许「先错后改对」仍被认账；
- **similarity gating** → 认同义改写与顺序无关参数，但不虚增覆盖率。

论文明确说这是为了替掉 LLM 裁判做调用级打分，列了 LLM 判的 5 个毛病：circularity/lineage bias、prompt gaming、weak argument verification、knowledge substitution、opacity。

### 4.2 对齐之上的 6 个指标

| 指标 | 定义 | 抓什么错 |
|---|---|---|
| **Recall** | `Σ\|M_m\| / Σ N_gt,m` | 漏调用 / 调错工具 |
| **Precision** | `Σ\|M_m\| / Σ N_pred,m` | 多余调用（浪费资源） |
| **Argument Similarity** | 对 `S_ij ≥ τ_strong` 的匹配求相似度均值 | 工具对了但**参数语义错** |
| **Step Coherence** | 每个 GT 步的匹配散落到 `\|P(ℓ)\|` 个预测步 → `sc(ℓ)=1/\|P(ℓ)\|`，按匹配数 `w_ℓ` 加权 | 本可并行的**被无谓拆步** |
| **Merge Purity** | `1 - H(G\|P)/log G_act`（条件熵归一化） | 把因果不同的多跳子目标**并成一步** |
| **Order Consistency** | `1 - (1/Q)Σ[(a_u-a_v)(b_u-b_v)<0]`（逆序对比例） | 因果依赖步**顺序倒置** |

**防刷分**：三个结构指标（StepCoh / MergePur / OrdCons）都按各样本 recall 加权成 recall-covered 分：
`F_cov = Σ N_gt,m · r_m · F_m / Σ N_gt,m`，`r_m = |M_m|/N_gt,m`。
理由（原文）：弱系统只匹配上少数好啃的工具会让分母极小、结构分虚高。

### 4.3 4-LLM 裁判集成（§4.4）

- **Task Completion**：4 个裁判各出 `[0,1]` 分，**去掉最高最低、取中间两个平均**（trimmed mean）：
  `TaskComp_m = ½ Σ_{j ∈ J\{j_min, j_max}} s_m^(j)`
- **Information Grounding**：额外把 GT 与预测轨迹都给裁判，出**步级** groundedness 分 `g ∈ [0,1]`，同样 trimmed mean。考的是「答案有没有被工具返回的证据支撑」，而非模型自带知识。
- **实际裁判阵容**（`scripts/evaluate_final_answer.sh` 逐字）：
  `gpt-5-mini, gemini-2.5-flash, deepseek-chat, grok-4-fast-reasoning`
- 代码细节：Task Completion 让裁判在 `0–10` 区间输出 `\boxed{数字}` 再归一化，Information Grounding 直接 `0–1`；prompt 里明确 "Judge solely based on the visible prediction content; do not use or allude to any ground truth."（`evaluate_final.py:42`）

### 4.4 最终 Average Score

Table 2 的 `Average Score` = 上述 8 列（Recall / Precision / ArgSim / StepCoh / OrdCons / MergePur / TaskComp / InfoGrnd）的平均。

## 5. Agent 装备

### 5.1 MCP 生态

- 论文 v4：**27 servers / 232 tools**（摘要 + §3.3）
- `mcp_servers.json` 实测：**28 个 server 条目，其中 `dinox-mcp` 标了 `"disabled": true`**（2026-05-10 changelog：付费限额的 DINO-X 被本地 Ultralytics YOLO 的 `mcp-yolo` 顶替，工具名 `detect-all-objects` / `detect-objects-by-text` 与 payload 形状保持一致）→ **28 - 1 = 27 活跃**，与论文对上
- 28 条目全名单：`weather, wiki, ocr, amazon, google-maps, tmdb, pyzbar-mcp, openlibrary_mcp, imagesorcery-mcp, healthcare-mcp, food_nutrition_mcp, dinox-mcp(disabled), mcp-yolo, linkimage-mcp, google-air, ppt, Reddit-MCP-Server, excel, nationalparks, paper_search, metmuseum-mcp, nasa-mcp, okx, hugeicons-mcp, yahoo-finance, math, nixos, car-price`
- 领域覆盖（§3.3）：Academic & Knowledge、Science & Space、Geography & Travel、E-commerce & Finance、Office Automation、Weather & Air Quality、Health
- 选服务器的原则（§3.3 逐字）：*minimal functional overlap*，偏好 orthogonal / well-documented / stable，砍掉冗余和不稳的以减少 confounds

**本例实际用到 4 个 server / 5 个工具**：`wiki`（summary, search）、`weather`（get_weather）、`google-maps`（compute_route, places_nearby_search）。

### 5.2 Agent 循环（`round_runner.py` + `scripts/benchmark_fuzzy.sh`）

每轮两阶段（对应论文 Prompt: Plan / Prompt: Process）：

1. **Prepare（选工具）**：把全量工具清单（含 docstring）塞进 system prompt，模型**只输出这一轮要用哪些工具 + 计划**，不直接调用——论文说这是 "selection only to stabilize reasoning and keep the chain controllable"。
   prompt 逐字片段：`"You are an assistant with MCP tool invocation capability. You must call one or more MCP tools, possibly in multiple rounds, to complete the task. Consider necessary steps as much as possible... Extra steps may reduce your final score"`
2. **Work（执行）**：优先走原生 function calling；不支持则回退到 prompt 路径，要求 `Return STRICT JSON ONLY with a single top-level key 'tool_calls'`，每项 `{"name": "server_name/tool_name", "arguments": {...}}`；同一轮的多个 tool_calls **并发执行**（`_call_tools_concurrently`，asyncio + 信号量）→ 这就是 multi-threaded 的落地方式。JSON 解析失败会重试一次，仍失败记 `stop_reason: invalid_tool_calls`。
3. **Stop/Continue**：每轮后二元判断证据够不够；够了就只输出终答。

**运行参数（`benchmark_fuzzy.sh` 逐字）**：`--TOP_TOOLS 400 --max_step 6 --max_concurrent 10 --num_client 5 --max_new_tokens 32768 --fuzzy`
→ 最多 6 步、单步最多 10 个并发调用。

**中间产物持久化**：MCP 工具产出的图片/文件路径落在临时 workspace（`media/runs/`，`M3_WORKSPACE_MODE`），后续步骤可引用（论文摘要的 "persistence of intermediate resources across steps"）。2026-07-25 changelog 还提到工具产出的图片会**实际回喂给模型看**，不只给文件名。

### 5.3 被测模型（14 个）

`gpt-5 / gpt-5-mini / gpt-5-nano / internvl3.5 / gemini-2.5-pro / gemini-2.5-flash / gemini-2.5-flash-lite / claude-haiku-4-5 / claude-sonnet-4-5 / Llama-4-Scout-17B-16E-Instruct / Qwen2.5-VL-72B-Instruct / glm-4.5v / grok-4-fast-reasoning / grok-4-0709`

### 5.4 GT 是怎么造的（§3.1 Executor–Judge + 人审）

`人写显式 instruction（定 intent 与可用工具）` → `Executor 逐步产轨迹` → `Judge 拿初始 prompt + 图 + 完整对话审计`：因果错序或事实错误直接**拒**，否则**重构 optimal trajectory**（删掉失败/冗余调用、把可并行的合并进同一步）→ `人工验证 scope 与逻辑一致性` → 成为 benchmark reference。

**人评背书（§6.4）**：30 位做 MCP 的 PhD/研究者，每人 20 组盲评配对（原始 MLLM 轨迹 vs 人工优化 Best Trajectory），Best Trajectory 被选中 **98.16%（589/600）**。
