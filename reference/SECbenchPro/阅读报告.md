# SEC-bench Pro · 长程安全任务（已被 OpenAI 采用）

> **原文**：SEC-bench Pro: Can Language Models Solve Long-Horizon Software Security Tasks?
> **出处**：arXiv:2605.26548，2026-05-26（v2 2026-07-20）
> **阅读方式**：基于完整摘要与元数据

## 0. 一句话
**它是长程任务评测里少见的"被工业界采纳"的例子**——摘要明写：**SEC-bench Pro 已被 OpenAI 用于评估其最新模型的长程安全能力**。

## 1. 关键数字
| 项 | 内容 |
|---|---|
| 题量 | **344 个**已验证漏洞 |
| 目标 | V8 与 SpiderMonkey 浏览器引擎 · Linux 内核 |
| 覆盖漏洞族 | 内存安全 · 沙箱 · JIT · 竞态 · 内核子系统 |
| 任务 | 从披露报告中**复现可用的 PoC 输入** |
| 最强成绩 | **Codex + GPT-5.5 解出 58%** |
| 开源模型 | GLM-5 只解出 **13/344** |
| 副产品 | 构建与评测过程中**发现了 V8 与 SpiderMonkey 的 3 个漏洞**，含一个沙箱逃逸，获 Google 漏洞奖励 **$20,000** |
| **方法学贡献** | 论证**现有规则型判分器对生成的 PoC 判定不准**，改用新的 LLM-based judge |

## 2. 机制与判分
PoC 能否触发目标漏洞（可执行判定），但作者认为规则型判分不足，改用 LLM judge —— **判定由硬转软，这个转向值得注意**。

## 3. 对我方
**可借（一条反向警示）**：

**它是从"规则型硬判分"转向"LLM judge"的案例，理由是规则判不准。** 这与我们的路线相反，因此**必须理解它为什么这么转**：PoC 的"成功"形态多样（不同的崩溃、不同的利用方式都可能算成功），规则难以穷举。

**对照我们的情形**：我们的答案是**单一 ID**，比对方式唯一，**不存在"多种成功形态"的问题**。所以我们能坚持硬判定，不是因为我们更严谨，而是**因为我们的任务形态允许**。这一点在对外表述时应说清，避免显得在批评用 LLM judge 的工作。

**可打点**：软件安全域。归入"长程任务评测"类，其"被 OpenAI 采纳"可作为长程评测受重视的佐证。
