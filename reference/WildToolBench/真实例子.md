## 1. 测什么

测**真实用户行为下的多轮 × 多步工具调用**。作者的立场是一句反直觉的话：真正难倒模型的不是人为设计的复杂任务，而是用户行为本身的"野性"。

三个挑战（论文 §3.3/§3.4/§3.5）：

| 挑战 | 含义 | 数据集中的落地 |
|---|---|---|
| **Compositional Tasks**（组合型任务） | 一句话里塞进多个简单需求，需要编排**工具调用拓扑**（tool-call topologies），`T` 是树而非链，目的是压 TTFT | 任务类型分 `Single-Tool` / `Sequential` / `Parallel` / `Mixed Multi-Tool` |
| **Implicit Intent**（意图散在多轮里） | 意图不在当前这句话里，要回头翻上下文 | 三个子类型：`Partial Information`（信息只给一部分）/ `Coreferential Reference`（只用代词/省略指代）/ `Long-Range Dependency`（依赖距离 i−j>2 的远端轮次） |
| **Instruction Transition**（指令混杂） | 任务查询、澄清、闲聊混着来，模型要**临场切策略** | 每个场景 4 个任务，类型在 `g_single` / `g_multi` / `g_chat` / `g_clarify` 间切换；最多 3 次切换 |

**数据规模**（论文 §3.6，我已用官方 jsonl 逐条核对一致）：

| 项 | 论文 | 我实测 `Wild-Tool-Bench.jsonl` |
|---|---|---|
| 场景（session） | 256 | **256 行** ✅ |
| 任务（task） | 1024 | **1024**（每场景恰好 4 个）✅ |
| 平均对话轮数 | 5.27 turns（BFCL 3.75） | **5.27** ✅ |
| 平均工具调用步数 | 1.92 steps（BFCL 1.68） | 真实工具步 1.45；含两个伪工具后约 1.92 |
| 工具 | 8 大类 24 子类 | **618 个不同工具名**，每场景 2~17 个（均值 4.88） |
| 语言 | — | 中英双份字段（`tools`/`english_tools` 等） |

任务类型分布（实测）：`Single-Tool` 256、`Chat` 256、`Clarify` 256、`Parallel Multi-Tool` 156、`Mixed Multi-Tool` 84、`Sequential Multi-Tool` 16 —— 即**每个场景必然各含 1 个单工具 + 1 个闲聊 + 1 个澄清 + 1 个多工具**。
隐藏意图子类型分布（实测，共 768 = 256×3，第 1 轮不计）：`Coreferential Reference` 349、`Partial Information` 240、`Long-Range Dependency` 179。

工具来源：论文 §3.2 说沿用 ToolAlpaca 做法，从 https://github.com/public-apis/public-apis 取 **400 个 tool list、约 1600 个 API**，清洗后按场景选子集。

## 2. 真实 query 原文（一段真实多轮对话）

**来源**：官方数据集 `wild-tool-bench/data/Wild-Tool-Bench.jsonl` 第 35 行，`id = wild_tool_bench_34`。完整原始 JSON 已存为本目录 [`example_wild_tool_bench_34.json`](./example_wild_tool_bench_34.json)。以下为 `english_*` 字段逐字原文。

**环境**：`Current Date: 2024-02-06 22:38:38 Tuesday`（这是唯一的 system prompt）
**可用工具（5 个）**：`getExchangeRate`, `getAllExchangeRates`, `convertCurrency`, `getSupportedCurrencies`, `getHistoricalRates`
**任务类型序列**：`Single-Tool` → `Chat` → `Clarify` → `Parallel Multi-Tool`（4 类全齐，3 次切换）
**隐藏意图序列**：`Coreferential Reference` → `Coreferential Reference` → `Partial Information`

```
[Turn 1 · user]      I want to know how much CNY can be exchanged for 100.5 JPY.
                     The result needs to be rounded.
[Turn 1 · assistant] According to the current exchange rate, 100.5 Japanese yen can be
                     exchanged for approximately 5 Chinese yuan.

[Turn 2 · user]      Can you tell me what the exchange rate will be in three days?
[Turn 2 · assistant] I'm sorry, I can't query the exchange rate between the Japanese yen
                     and the Chinese yuan three days later at present. However, I can query
                     the current exchange rate and historical exchange rates. Do you need
                     to query them?

[Turn 3 · user]      I want to know the exchange rates of one of the currencies against
                     the US dollar and the euro.
[Turn 3 · assistant] Do you want to know about Japanese yen or Chinese yuan?
[Turn 3 · user]      The second
[Turn 3 · assistant] According to the query results, the current exchange rate of the
                     Chinese yuan against the US dollar is 0.157, and against the euro
                     is 0.144.

[Turn 4 · user]      What about the past week? Check both this time.
[Turn 4 · assistant] ### Exchange Rates of CNY against USD (Past Week)
                     - 2024-01-30: 0.156
                     - 2024-01-31: 0.157
                     ...（CNY/USD、CNY/EUR、JPY/USD、JPY/EUR 四组共 20 个数据点）
```

**这段对话为什么"野"**——三个挑战在同一段对话里同时出现：

- **Turn 2 是闲聊/拒答陷阱（`g_chat`）**：用户问"三天后的汇率"。手上 5 个工具全是查当前和历史汇率的，**没有一个能预测未来**。正确动作是**不调工具**、直接说做不到并给替代方案。同时"the exchange rate"是指代——指 Turn 1 的 JPY→CNY。
- **Turn 3 是澄清陷阱（`g_clarify`）**：`"one of the currencies"`——哪一个？JPY 还是 CNY？信息真的缺，正确动作是**反问**。用户回答 `"The second"`（就两个字），模型得自己数出"第二个"= CNY。
- **Turn 4 是并行编排 + 部分信息（`g_multi` Parallel + Partial Information）**：`"What about the past week? Check both this time."` 一句话 12 个词，要还原出**四件事**：① "past week" = 起止日期需按当前日期 2024-02-06 自行推算成 `2024-01-30` ~ `2024-02-05`；② "both" = JPY **和** CNY（回溯 Turn 3 那个"二选一"，这次两个都要）；③ 目标币种沿用 Turn 3 的 USD 和 EUR；④ 2 基准币 × 2 目标币 = **4 个互不依赖的调用，应当并行发出**（串行发也算对，但拿不到 OP 分）。

> 注：论文自己的图例（Figure "case_study"，已存为本目录 `paper_case_study.png`）是另一段同构的真实例子——BBC 新闻 → `"Yesterday ESPN"`（Partial Information，只给两个词）→ `"I want to obtain the metadata of one of them"`（Coreferential → 触发 Clarify）→ `"The last one in the first round of results"` → `"Get the metadata of all the rest articles for me. Also, I want to know about other articles by the authors of these rest articles."`（Long-Range Dependency + 并行）。图中还标了两个典型失败：把 `"Yesterday ESPN"` 当成意图不明而反问（`Intent drift occurs, incorrectly asking for intent`），以及在上下文已有内容时重复追问（`Omitting contextual information and repeatedly asking users for existing content`）。

## 3. 预期答案（期望的工具调用序列）

数据集字段 `english_answer_list`，逐字原文。每个节点含 `idx` / `dependency_list`（人工标注的依赖边，用于建 DAG）/ `action{name,arguments}` / `observation`。

```
########## TASK 1 [Single-Tool] ##########
idx=0 dep=[]    convertCurrency({"amount": 100.5, "fromCurrency": "JPY", "toCurrency": ["CNY"]})
                → {"response": {"convertedAmount": 4.9}, "status_code": 200}
idx=1 dep=[0]   prepare_to_answer({"answer_type": "tool"})
                → "According to the current exchange rate, 100.5 Japanese yen ..."

########## TASK 2 [Chat] ##########
idx=0 dep=[]    prepare_to_answer({"answer_type": "chat"})
                → "I'm sorry, I can't query the exchange rate ... three days later ..."
                ★ 全程零工具调用。调任何工具即算错。

########## TASK 3 [Clarify] ##########
idx=0 dep=[]    ask_user_for_required_parameters(
                  {"tool_list": [{"tool_name": "getExchangeRate",
                                  "missing_required_parameters": ["baseCurrency"]}]})
                → "Do you want to know about Japanese yen or Chinese yuan?"
                （用户回填 "The second"）
idx=1 dep=[0]   getExchangeRate({"baseCurrency": "CNY", "targetCurrency": ["USD", "EUR"]})
                → {"exchangeRates": [{"targetCurrency":"USD","rate":0.157},
                                     {"targetCurrency":"EUR","rate":0.144}], ...}
idx=2 dep=[1]   prepare_to_answer({"answer_type": "tool"})

########## TASK 4 [Parallel Multi-Tool] ##########
idx=0 dep=[]    getExchangeRate({"baseCurrency":"CNY","targetCurrency":["USD"],
                                 "startDate":"2024-01-30","endDate":"2024-02-05"})
idx=1 dep=[]    getExchangeRate({"baseCurrency":"CNY","targetCurrency":["EUR"],
                                 "startDate":"2024-01-30","endDate":"2024-02-05"})
idx=2 dep=[]    getExchangeRate({"baseCurrency":"JPY","targetCurrency":["USD"],
                                 "startDate":"2024-01-30","endDate":"2024-02-05"})
idx=3 dep=[]    getExchangeRate({"baseCurrency":"JPY","targetCurrency":["EUR"],
                                 "startDate":"2024-01-30","endDate":"2024-02-05"})
                ★ 四个 dep 全为空 = 四路并行，最优路径深度 = 1 步（一次发 4 个 tool_call）
idx=4 dep=[0,1,2,3]  prepare_to_answer({"answer_type": "tool"})
```

注意 Task 3 的正确答案里 `baseCurrency` 必须是 `"CNY"` —— 这个值不在任何一条用户消息里明说，得从 `"The second"` 推出来。Task 4 的 `startDate/endDate` 也不在对话里，得从 system prompt 的 `2024-02-06` 推出来。

## 4. 怎么判分

**判分完全是规则化的，没有任何 LLM judge**（我在 `repo/*.py` 全文 grep `judge|llm.?as` 零命中）。代码：`wtb/eval_runner.py` + `wtb/checker_utils.py` + `wtb/tool_call_graph.py`。

### 4.1 主指标

| 指标 | 定义 | 代码位置 |
|---|---|---|
| **Task Accuracy** | 单任务判对 / 1024 | `calc_accuracy` → `total_info["task"]` |
| **Session Accuracy**（主榜指标） | **一个场景 4 个任务全对**才算对 / 256 | `session_correct`，任一任务错则整场记 0 |

单任务判对 = `action_name_label == correct` **且** `action_arguments_label == correct`（`eval_runner.runner`）。

### 4.2 两级校验

**第一级：动作名（在线，边推理边判，错了立刻中断该任务以省算力）**
- 模型**发了 tool_calls** → 按 `ToolCallGraph` 枚举出的合法路径集做**增量路径匹配**（论文 §3.3 的 enumerate–match–score）。当前步不在候选集里 → `error: action name not in candidate_answer_function_list`，中断。
- 模型**只发纯文本、没发 tool_calls** → 若该步 ground truth 是 `prepare_to_answer`（该直接答）或 `ask_user_for_required_parameters`（该反问）则判**对**。
  ⚠️ **关键细节：`g_chat` 和 `g_clarify` 的正确性 = "有没有忍住不调工具"，自然语言的措辞本身完全不评分。** 反问问得对不对、答得好不好，都不看。
- 并行调用：预测和答案各自按 `(name, arguments)` 排序后逐一对齐，且**数量必须严格相等**（代码里是 `assert len(predict_tool_calls) == len(answer_actions)`）。

**第二级：参数（离线，`ToolArgsChecker.check`，两步）**

① `tool_check` —— 对着 tool schema 查格式：JSON 能否解析、必填缺失、出现未定义参数、类型不符、枚举越界，嵌套 object/array 递归查（8 种 `error_schema:*`）。
② `answer_check` —— 对着标准答案递归比值：
- dict：**key 集合必须完全相等**（多一个 key 也算错）
- array：**长度必须相等**，逐项递归
- string：① 完全相等 → 对；② 去空格转小写后相等 → 对；③ 答案长度 < 10 字符 → `SequenceMatcher` 编辑相似度 **≥ 0.8** 才算对；④ 否则（长文本）→ **ROUGE-L F1 ≥ 0.7**（含中文则先 jieba 分词）
- 其他标量：必须严格相等

所以自由文本类参数（如摘要、搜索词）是**软匹配**，结构化参数（数字、枚举、日期、布尔）是**硬匹配**。

### 4.3 有过程分

有，两个细粒度过程指标（论文 §3.3 + Table 3）：

- **OP Rate（Optimal Path Rate，最优路径率）**：对 `Parallel` 和 `Mixed` 任务。人工标注邻接依赖 → 深度优先拓扑排序**枚举全部合法执行路径**（不是只留一条最优路，这是它对 WorfBench/TaskBench 的批评点）→ 模型走完的路径若**深度最小**才算 optimal。串行发 4 个能拿对，但拿不到 OP 分。参数错会把 `is_optimal` 强制置回 `False`。
- **AP Rate（Accomplish Progress Rate，完成进度率）**：对 `Sequential` 和 `Mixed` 任务。`complete_step / total_step`，即失败前走对了几个节点，给部分分。

还按 **task type**（7 类）、**task order**（第 1/2/3/4 个任务）、**turn subtype**（First Turn / Subsequent / Coreferential / Partial / Long-Range）五个维度分桶报准确率。

### 4.4 一个重要的实现选择：teacher forcing

`base_handler._pre_messages_processing` 构造历史时，用的是**标准答案的最优路径**（`optimal_path`），不是模型自己上一轮的输出。即**前面任务答错不会污染后面任务**，每个任务都从干净的黄金历史起跑。这让"任务序号越靠后越差"（Table 2 的 1→4 列单调下降）这个结论干净地归因于"依赖上下文更多"，而不是误差累积。

### 4.6 论文另外报的

- §4.4：instruction transition 次数越多，task accuracy 越低，**最多掉 30 个点**。给的机制解释是 **self-conditioning**（引 Sinha et al., 2025）：上一轮调了工具就倾向继续调，上一轮并行就倾向继续并行。
- §7 Limitations 自认：人工标注限制了规模扩展；"同时保证质量 + 遍历所有策略切换类型"限制了任务长度。
- §3.2 数据构造：先从真实用户日志里采样做 few-shot（**声明不泄露真实用户数据**，只让分布对齐）→ 多 agent（User Agent + Assistant Agent）生成初始轨迹 → 自动查函数幻觉/参数幻觉/类型错误/冗余调用 → **5 名人类专家**逐条修正并标注依赖边 → 随机抽 20% 复核讨论。Appendix C 特别提到人工重写的动机：合成对话"太有条理"，不像人话，所以把 `"What is the weather like in Shanghai today?"` 手改成 `"How about Shanghai?"`。

## 5. Agent 工具

**两层**。

**第一层：给模型的真实工具**。每个场景注入该场景的工具子集（2~17 个，均值 4.88；全库 618 个不同工具名）。用各模型**原生 Function Call 格式**（论文 §4.1："We employ each model's native Function Call format to achieve optimal performance"；Claude 走 `inputSchema`）。system prompt 只有一句 `Current Date: {env_info}` —— **没有任何任务指令或行为提示词**。本例的 5 个工具：

| 工具 | 说明 | 必填 |
|---|---|---|
| `getExchangeRate` | 查两币汇率，可指定日期区间取历史数据 | baseCurrency, targetCurrency |
| `getAllExchangeRates` | 查某基准币对全部支持币种/加密货币的汇率 | baseCurrency |
| `convertCurrency` | 金额换算，可选 `rounding` | amount, fromCurrency, toCurrency |
| `getSupportedCurrencies` | 列支持币种，`type` 枚举 `fiat`/`crypto`/`all` | 无 |
| `getHistoricalRates` | 查指定单日历史汇率 | baseCurrency, targetCurrency, date |

**第二层：两个"伪工具"，只存在于标准答案里，不注入给模型**（这点从 `base_handler.py` 的分支逻辑可确认——模型是靠"输出纯文本而非 tool_call"来隐式命中它们的）：

| 伪工具 | 参数 | 语义 | 出现次数（实测） |
|---|---|---|---|
| `prepare_to_answer` | `{"answer_type": "tool" \| "chat"}` | 收尾出话。`tool` = 基于工具结果总结；`chat` = 不用工具直接答 | **1024**（每个任务恰好 1 次） |
| `ask_user_for_required_parameters` | `{"tool_list":[{"tool_name": ..., "missing_required_parameters":[...]}]}` | 反问用户补必填参数，并**指明是哪个工具缺哪个参数** | **324** |

`ask_user_for_required_parameters` 的参数设计值得注意：它把"该反问"这件事**结构化**成了"`getExchangeRate` 缺 `baseCurrency`"，而不是一句自由文本。但如 §4.2 所说，评测时并不校验这个结构——模型只要输出纯文本就算命中。这是标注信息比评测严格度更丰富的一处。

**环境反馈**：不真调 API。`observation` 是标注时固化在数据里的 mock 返回（`{"response": {...}, "status_code": 200}`），所以评测**完全离线、可复现**。
