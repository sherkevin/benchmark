## 0. 一句话

**这篇不评测 agent，而是评测「benchmark 本身有没有病」**——用 AI 扫描器去读 agent 的执行记录（transcript），自动找出四类会让评测结论失效的缺陷，其中两类正是我们这套 benchmark 的核心设计目标。

**为什么对我们特别重要**：它给出了一份**外部的、可被第三方执行的自查标准**。我们此前论证"答案不可及""不能靠蒙"都是自说自话，这篇提供了别人已经在用的判据与扫描工具。

## 2. 四类缺陷的准确定义（原文 Table 1）

这是本篇最该抄走的部分。

| 缺陷类型 | 定义 | 原文列举的具体形态 |
|---|---|---|
| **Ground Truth Access**<br>（答案可及） | 非预期的、与任务成功相关的信息对模型可见，使其**无需真正完成任务即可通过** | 直接答案泄漏 · solver 文件 · 隐藏测试信息 · 可从网络访问的解答 · 过度暴露的提示 · **从预训练暴露中记住 benchmark 特定答案** |
| **Tool Failures**<br>（工具故障） | 工具、软件环境、API、网站或外部包失效，导致模型**因与能力无关的原因**失败，混淆结论 | 缺依赖 · API 坏了 · 资源不可达 · 环境配错 |
| **Answer Format Ambiguity**<br>（答案格式歧义） | 输出结构、单位、精度、任务范围等关键要求缺失或未充分指定 | 未指定答案格式/单位/精度/输出结构/任务范围 |
| **Guessing Vulnerability**<br>（可蒙对） | 任务允许通过随机、启发式或**半知情的猜测**成功，而非真正完成任务 | 答案空间小 · 多选题可明显排除 · **输出基数低** · 提示无意中收窄了合理答案集 |

## 3. 怎么测（方法三阶段）

**阶段一 · 定判据框架**：从三个候选框架（AI 评测质量记分卡、Eval Factsheets、ABC）中选了 **ABC**，理由是最全面且专门针对 agentic benchmark。

**阶段二 · 开发扫描器**：判据要能落成扫描器，必须同时满足两条——

- **Presence（可现性）**：该缺陷在轨迹里理论上表现得出来；
- **Verifiability（可验性）**：能由扫描器或人确认它被满足或违反。

被排除的典型例子：需要比对外部资源状态的"状态变更比对"（扫描器不擅长）；以及"所有工具版本是否明确声明"这类不看轨迹就能查的条目。

**阶段三 · 冻结后验证**：扫描器**先冻结**，再在 held-out 测试集上跑；人工评分者事后对测试集样本评分，用人工判断作为参照来量化扫描器表现。

---

## 4. 判分粒度

- 粒度是**单条轨迹 × 单类缺陷 → 0–3 严重度**，不是二值；
- 附带一套**抽样方法论**：回答"要看多少条轨迹才能确定某 benchmark 至少存在一处违规"，并给出置信度下界的概念验证。

---

## 5. 结果与作者自陈的局限

**结果**：在五个被广泛使用的 benchmark 中识别出若干**经核实的质量问题**，其中一部分**靠随机人工抽检不太可能发现**。

**局限（作者明说）**：并非所有案例都被识别出来；扫描器表现在不同 benchmark、不同判据、不同模型之间**差异很大**；此外评测领域缺乏标准化，这本身就在拉低扫描器表现。

## 6. 相关工作里的硬数字（可直接引用）

这些是别人审计出来的真实缺陷，作为"benchmark 有病是普遍现象"的证据：

| 来源 | 发现 |
|---|---|
| **HAL（Holistic Agent Leaderboard）** | 汇编 **21,730 条** agent rollout（9 模型 × 9 benchmark），用 Docent 查出 **τ-bench few-shot agent 的数据泄漏 bug**，以及 AssistantBench 的提示设计缺陷 |
| **UK AISI**（Wynne & Ududec 2025） | 审计 **6,390 条**轨迹，发现某模型约 **30% 的任务是通过 submission tool 拒答**，而非真去尝试 |
| **ABA（Auto Benchmark Audit）** | 用 agentic 审计器评估 **168 个** benchmark，发现"加上轨迹能比纯静态检查查出更多重大问题" |
| **BenchGuard** | 审计 ScienceAgentBench 与 BIXBench；在 ScienceAgentBench 上附完整轨迹使召回从 **83.3% → 91.7%** |
| **PostTrainBench** | 用 LLM-as-Judge 查 reward hacking，在五个 agent 上标出 **23 个测试数据误用的污染标记** |
| **ABC 原作**（Zhu et al. 2025a） | 在 SWE-Lancer 里发现**文件系统问题可让 agent 摸到真值**；OSWorld 里若干任务含失效链接 |
| 已被公开质疑的 benchmark | CORE-Bench · SWE-Bench-Verified · SWE-Bench Pro |

## 7. 对我方：可借 / 可打点

### 可借（三条）

1. **把四类缺陷做成我们自己的验收清单**。我们已有 23 条出题质量门，但那是查"题目本身合不合规"；这四条查的是"**题目会不会被绕过**"，是另一个维度。
2. **抽样方法论可以抄**。我们的 3,600 次矩阵跑完后，可按它的方法算"要抽查多少条轨迹才能对'无违规'有足够置信度"，而不是全查或凭感觉抽。
3. **扫描器先冻结再验证**这个流程纪律，与我们"判分器改动前先冻结、再复算"的做法一致，可互相印证。

### 可打点（两条，须自查）

| 缺陷类型 | 我们的现状 | 自查结论 |
|---|---|---|
| **Ground Truth Access** | A 侧可查 92,153 实体 / B 侧只回存在性不回性质值；per-case 视图 34 份；标识符全匿名化（封住"从预训练记住答案"这条） | **应能通过**，且匿名化正面覆盖了原文列举的"记忆预训练答案"形态 |
| **Guessing Vulnerability** | **这条是我们的真实风险点** —— 原文明确把"答案空间小""输出基数低"列为可蒙对的形态。我们 fixed 类的候选格位若成员数少，终态答案确实可能被蒙中 | **须实测**：统计每题候选池规模与"随机蒙对概率"，若某题蒙对概率过高需重造。已知旁证：此前实测某模型终态蒙对但 cp1–cp5 全 0（task=0.100），说明**过程卡点能识别蒙对，但终态本身可被蒙中** |

**这条打点的价值**：它把我们"过程卡点"的必要性论证从"设计理念"提升为"**对已知缺陷类型的针对性防御**"——终态可蒙对是行业公认缺陷，而我们的 cp1–cp6 正好让蒙对者拿不到分。
