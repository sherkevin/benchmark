## 1. 这份标准审什么

方法论必须同时满足四件事：定义能运行；信息边界没有泄漏；新增机制和最近邻有可检验差异；结果能够由原始事件独立恢复。一个能跑的代码、一个新名字或一个更大的 backbone 都不构成方法贡献。

本标准分开审 pre-call selector、post-call verifier、delayed updater 和 agent interface。验证器在调用后能读到的 confidence，不能被当成 selector 在调用前可用的信息。声称 online、realtime 或 dynamic 时，必须存在真实的事件时钟、反馈释放和单事件更新；静态 full-panel 重训不算在线方法。

## 2. 来源层级

| 层级 | 含义 | 用法 |
|---|---|---|
| O | AAMAS 官方对 originality、significance、soundness、reproducibility、clarity、relevance、presentation 和 state of the art 的要求 | 决定方法必须自洽、可复现、与已有工作有差异 |
| P | 代表性论文把现实困难写进形式模型，再让机制、理论/推导、对照和边界围绕同一困难展开 | 决定“机制必要性”和“证据闭环”的审法 |
| C | 本项目的 selected-only、延迟队列、provider/version lifecycle、失败语义和 confirmation freeze | 防止把开发回放或事后信号包装成动态 JEV |

官方没有规定固定公式、固定定理或固定分数。本文件的分数和硬闸门是项目内部的科学防守线。

## 3. 硬性淘汰条件

任一项为“是”，直接 FAIL，不进入总分。修复后必须重新评分。

| 编号 | 硬门槛问题 | 触发例子 |
|---|---|---|
| H1 | 输入、动作、反馈、延迟、状态、终止和失败是否都有可执行定义？ | 只写“在线更新”，没有 feedback release tick |
| H2 | 选择前是否严格看不到当前真值、未选输出和未来反馈？ | full-panel 先算完再声称 selected-only |
| H3 | 公式、伪代码、配置和实现是否在同一版本表达同一个算法？ | 论文写 cosine，代码用 dot product |
| H4 | 新机制是否相对最近邻改变了信息、状态、目标或计算，并有可证伪反例？ | 只换 encoder、loss 或名称 |
| H5 | “实时/在线/动态”是否有事件级更新时间、p50/p95、内存和预算？ | 只报告一次平均耗时 |
| H6 | 是否有 matched baseline、初始化权限和机制消融？ | 只和 Random 或过时方法比较 |
| H7 | raw event → state → metric 是否可独立恢复？ | 只有 notebook 最终均值 |
| H8 | confirmation 是否在方法、菜单、阈值和 epoch 冻结后才打开，且不回流调参？ | 看 confirmation 后选 epoch |
| H9 | 动态主张是否有可观察的 arrival、retire、version shift 或环境变化？ | 固定数据上重复 epoch 就叫 dynamic |
| H10 | 每条核心机制/理论主张是否至少有一个能推翻它的条件，且负结果保留？ | 只给支持主张的 seed 和设置 |

## 4. 评分方法

### 4.1 统一锚点

M1–M15 每项取 $q_i\in\{0,1,2,3,4\}$，总分满分 60。每项必须填写 score / evidence_path / excerpt_or_log_line / gap / action。

- **4 分**：正文、伪代码、实现和原始证据一致；独立复核者能重算，并有反事实、压力或理论边界。
- **3 分**：主流程可执行且可复核；证据完整，只有不改变结论的局部缺口。
- **2 分**：定义或代码基本存在，但边界、独立重算或压力证据缺一；只能算开发级。
- **1 分**：只有断言、公式片段或人工演示，关键前提需要作者补充。
- **0 分**：缺失、互相矛盾、发生泄漏，或原始证据推翻该项。

无正文、代码、测试、配置、原始日志或恢复器路径的项目，最高只能给 1 分；只靠口头解释不能加分。

### 4.2 通过条件

同时满足以下条件才算“方法通过”：

1. H1–H10 全部为“否”；
2. M1–M8、M10–M12、M15 每项至少 3 分；
3. M9、M13、M14 每项至少 2 分且不得为 0；
4. 四个分组的平均分均达到 3 分：任务契约（M1–M4）、机制数学（M5–M8）、实时公平（M9–M12）、证据主张（M13–M15）；
5. 总分至少 49/60；
6. 至少有一项 matched-backbone 对照、一项最强现代近邻和一张失败/负结果表。

通过表示“方法具备内部投稿审查资格”，不表示 AAMAS 会录用。任一硬门槛失败时，分数不能抵消。

## 6. 最小方法验收包

提交方法评分前必须有以下五类证据：

1. **可实现性**：独立环境按同一配置得到相同事件数和状态 hash；
2. **信息边界**：注入未选输出、未来标签或 confirmation 标签时测试失败，正常流不读取它们；
3. **机制贡献**：主方法与 matched frozen/online/replay 对照的差异来自新增机制；
4. **实时压力**：延迟、冷启动、provider family 相关性或动态事件至少覆盖一项直接主张；
5. **恢复与负结果**：原始 JSONL、恢复脚本、失败现场和停止规则齐全，不能只保留最好 seed。

## 7. 双人评分和复核规则

只对当前生效方法文档和标明版本/commit 的论文草稿评分。作者和没有参与实现的复核者独立填写：

ID | 维度 | 作者分 | 复核分 | 生效分=min | 证据路径 | 缺口/修复动作

无法在 30 分钟内从配置和 raw event 重算指定最小样本时，M6、M7、M14 最高 2 分。两人分差达到 2 分，先补证据再重评；不能用讨论把分数调高。selector 的证据不能移作 verifier 的证据，development 证据不能移作 confirmation 证据。

## 8. 评分结果的动作

- 任一 H 触发：FAIL，先修信息合同、实现一致性或冻结流程；
- M1–M8、M10–M12 或 M15 低于 3：HOLD，不能写成最终方法贡献；
- M9、M13、M14 为 0：停止效果实验，先补实时、消融或恢复证据；
- 总分 49/60 以下：只保留为 development method；
- 总分达到 49/60 且所有门槛通过：进入 benchmark 联审，不等于录用预测。

当前普通 SGD、Bayesian posterior、PILOT 或 LinUCB 的可运行性只能支持相应 baseline 项；没有新增可观测信息或可识别动态事件时，不得把它们更名为动态 JEV 创新。post-call verifier 的结果也不能回填 selector 的方法分数。
