## 先说结论

方法只有同时满足“定义能运行、信息边界不泄漏、机制区别于最近邻、结果能独立恢复”四个条件，才算可投稿。一个能跑的代码和一个新名字都不构成方法贡献。

## 1. 硬性淘汰条件

| 编号 | 硬闸门问题 | 不通过例子 |
|---|---|---|
| H1 | 输入、动作、反馈、延迟、状态和终止条件是否都有定义？ | 只说“在线更新”，没有反馈何时到达 |
| H2 | 选择前是否严格看不到当前真值、未选输出和未来反馈？ | 用完整 panel 先训练再声称 selected-only |
| H3 | 公式、伪代码和实现是否表达同一个算法？ | 论文写 cosine，代码用 dot product |
| H4 | 新机制是否和最近邻在目标、信息或状态上存在可检验差异？ | 只是换一个 encoder/head |
| H5 | 是否报告了单步更新、推理延迟、内存和失败语义？ | “实时”只凭模型参数量判断 |
| H6 | 是否有 matched baseline 和可解释的消融？ | 只和 Random/Best Fixed 比 |
| H7 | 核心结果能否从原始事件日志独立恢复？ | 只有 notebook 最终均值 |
| H8 | 是否在看过 confirmation 后改了 epoch、阈值、菜单或目标？ | 测试集参与调参 |

任一项为“是”就不通过。

## 2. 十二项评分

统一评分：`0` 缺失/错误；`1` 部分定义或只能人工补全；`2` 正文、代码和日志一致。

| ID | 检查项 | 2 分必须看到什么 | 证据记录 |
|---|---|---|---|
| M1 | 数学对象 | 输入 $x_t$、菜单 $A_t$、动作 $a_t$、反馈 $r_t$、历史 $H_t$、状态 $S_t$ 的 shape、来源和案例 | method section |
| M2 | 时间顺序 | pre-call、provider execution、post-call verification、feedback release、update 的时序图 | timeline |
| M3 | 信息合同 | 每个模块列出可读字段和禁止字段，代码有断言 | isolation test |
| M4 | 机制必要性 | 解释新增状态/更新为何针对困难，且有去掉机制的反例或消融 | mechanism proof |
| M5 | 算法一致性 | 公式、伪代码、实现、配置和日志 hash 一致 | code/config audit |
| M6 | 近邻公平 | 与最近 baseline 使用相同菜单、特征、反馈、预算和初始化权限 | baseline matrix |
| M7 | 理论或可计算保证 | 给出适用条件下的复杂度、稳定性、无偏性/偏差来源或可证伪推导 | derivation/proof |
| M8 | 实时成本 | 单事件更新时间、p50/p95、峰值内存、冷启动成本可测 | runtime log |
| M9 | 延迟和分布鲁棒性 | 至少预登记 delay/shift 条件，并报告结果和失败边界 | delay/shift table |
| M10 | 消融与反事实 | 去掉冷启动、状态、验证门或 replay 后，变化方向能解释机制 | ablation |
| M11 | 失败恢复 | failure、missing、unknown、未释放 feedback 不被静默改标签；恢复后逐事件一致 | recovery receipt |
| M12 | 主张校准 | 论文只声称实际覆盖的端点、菜单、延迟和 confirmation | claim ledger |

### 通过阈值

- H1–H8 全部为“否”；
- M1–M7 每项必须为 `2`；
- M8–M12 至少 4 项为 `2`，其余不得为 `0`；
- 总分至少 `20/24`；
- 至少保留一个 matched-backbone 对照、一个最强现代近邻和一个失败/负结果表。

## 3. 方法验收的最小实验包

提交前必须能定位下列五件事：

1. **可实现性**：独立环境按配置运行，得到相同事件数和状态 hash；
2. **信息边界**：把未选输出或未来标签注入时，测试必须失败；正常运行不读取它们；
3. **机制贡献**：主方法与 matched frozen/online/replay 对照的差异来自新增机制；
4. **压力条件**：延迟、冷启动、provider family 相关性或分布变化至少覆盖一项与主张直接相关的压力；
5. **恢复与负结果**：原始 JSONL、恢复脚本和失败记录齐全，不能只保留最好 seed。

没有这五件事，方法不能进入 confirmation 或投稿构建。

## 4. Reviewer 六问

1. 选择前到底能看到什么？
2. 新方法和最接近方法的数学差异在哪里？
3. 如果把新增机制删掉，哪一项结果应该消失？
4. 反馈延迟时，更新发生在哪一个 tick？
5. 单条更新需要多久，失败如何恢复？
6. 哪个实验最可能推翻方法？

任一问题不能在正文或主表中回答，相关评分项最多 1 分。

## 5. 评价标准的来源

- **O 官方要求**：soundness、reproducibility、clarity、relevance、state of the art 和正文自洽，见官方 [Reviewer Guidelines](https://warwick.ac.uk/fac/sci/dcs/aamas2027/guidelines-and-policies/reviewer-guidelines/) 与 [Submission Instructions](https://warwick.ac.uk/fac/sci/dcs/aamas2027/guidelines-and-policies/instructions/)。
- **P 代表性规律**：近年 AAMAS 方法论文把现实困难写进模型，并让机制、理论/推导、对照和边界围绕同一个困难；来源矩阵列出代表性样本。
- **C 项目加严**：selected-only、延迟队列、provider lineage、恢复日志和 confirmation freeze 是本文特殊任务的公平性要求。

## 6. 不通过后的动作

先修正信息合同和实现一致性，再谈模型复杂度；先补最近邻和消融，再谈“创新”；如果可观测信息不足以支撑收益，就缩小主张，不用更大的 backbone 掩盖。

## 7. 评分执行规则

写作者和一名未参与实现的复核者分别按原始配置、代码和事件日志打分。两份评分不取平均，较低分生效；复核者无法重算的项目不得给 2 分。
