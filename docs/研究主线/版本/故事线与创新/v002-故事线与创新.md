## 一句话判断

科学工具会正常返回却给出错误结果。我们的任务是：在调用前从具体 provider 菜单中选一个工具，收到延迟的、只针对已选工具的对错反馈后更新后续选择；调用后还要判断结果是否值得直接使用，必要时复核或拒答。

## 问题从哪里来

现有医药结果库里，同一个分子和性质常由多个具体 provider 给出不同结果。格式正常不能说明结果可靠。真正的困难有三个：

1. 选择发生在结果返回前，未选 provider 的当前输出不能偷看；
2. 对错反馈只在调用结束并可能延迟后到达，更新不能假设同步标签；
3. 选对工具和发现当前结果不可靠是两个时点，不能用调用后的 confidence 冒充调用前信息。

因此论文研究的是“带延迟选择反馈的科学工具调用”，医药 provider 只是一个有独立真值、可复核输出的具体场景。

## 论文故事链

1. **真实失败**：不同 provider 对同一分子会分歧，正常返回不等于可用。
2. **可计算任务**：给定分子、端点和冻结的 provider 菜单，先选一个 provider；终止后得到该选择的 0/1 correctness，并按预登记时钟释放。
3. **方法缺口**：固定赢家不能适应分布，普通在线头又没有处理好延迟和调用后可信度；把标准算法换个名字也不是贡献。
4. **研究切口**：把“调用前选择”和“调用后验证/升级”拆成两个信息边界明确的环节，再测试轻量状态能否在有限反馈下带来可复现收益。
5. **论文结论**：只有在同一菜单、同一反馈权限、同一预算下超过最强合法对照，且独立确认集通过，才主张方法有效；否则如实报告信息边界或方法失败。

## 创新点：当前怎样表述

当前保留的创新候选是一个**动态 JEV 工具适应流程**：

- 选择器在调用前只使用分子、端点、菜单和已释放的历史；
- provider 返回后使用其 confidence、运行状态和复核结果估计当前结果风险；
- 风险高时追加第二个工具或拒答；终止后的 selected-only correctness 按延迟队列更新后续状态；
- 选择、验证、更新各有独立日志，可以单独证伪。

这里的创新是把信息边界、实时更新和调用后可信度连成一个可审计的流程。LinUCB、SGD、Bayesian posterior、PILOT、Laya/JEV 表示本身都是比较对象或可复用组件，不单独算创新。

## 证据边界

已经观察到的证据：

- 722 条 BBB development replay 上，静态 representation diagnostic 的 Best Fixed accuracy 为 `0.915512`；该实验只说明直接选择的难度，不是最终动态方法结果。见 `task/task49-pharma-benchmark-baseline-freeze/fingerprint_diagnostic_v1/report.md`。
- 调用后 numeric confidence 对 correctness 有 held-out 信号；固定阈值的第二工具复核开发结果为 `0.923823` accuracy、平均调用数 `1.206`。这是开发证据，不是 confirmation 结果。见 `task/task49-pharma-benchmark-baseline-freeze/confidence_escalation_v1/report.md`。
- selected-only 的若干在线 head、transfer、memory 和动态 risk gate 没有通过预注册闸门。它们是停止和边界证据，不等于创新点被单次实验推翻。

尚未成立的部分：最终动态 JEV 的状态、更新规则、provider 资格和独立 confirmation 仍未冻结。因此本文件不写“已经证明动态 JEV 有效”。

## 主张纪律

论文只允许在证据满足对应闸门后使用以下主张：

| 主张 | 必须有的证据 |
|---|---|
| 任务真实且有难度 | 公共 truth、provider 分歧、无泄漏的信息合同 |
| 调用后验证有用 | 预登记阈值、匹配调用成本、独立恢复和 confirmation |
| 动态更新有用 | 延迟反馈回放、最强 matched baseline、跨 seed/端点结果 |
| 方法可推广 | 至少一个未参与开发的端点或 scaffold-disjoint confirmation |

若某个候选失败，先检查实现、数据资格、信息边界和预算是否正确；只有在这些都通过后，才讨论是否修改创新假设。重大修改要先形成双方确认的决议。

## 论文应该怎样把这条故事讲完整

这里写的不是“录用公式”。AAMAS 没有规定每篇论文必须使用同样的段落数；我们要保留的是一条在代表性论文中反复出现的论证行为：**具体现实问题 → 可复现失败 → 失效原因 → 只针对该原因的 insight → 可执行机制 → 匹配证据 → 适用边界**。这条行为逻辑是本项目写作时的硬约束。

### 一句话主张轴

整篇论文必须能用一句话回答：

> 在科学工具正常返回但可靠性未知的情况下，延迟的 selected-only correctness feedback 如何改变调用前选择和调用后验证，使 agent 在相同信息与预算下更可靠地使用工具？

这句话同时限定了问题、机制和评价对象。Introduction 建立它，Method 把它写成接口和状态，Experiments 逐条检验它，Discussion 解释它在哪些条件下失效。不能在不同章节把主线偷偷换成“更大的 backbone”“一个通用 router”或“所有工具都能验证”。

### 引言的段落顺序

| 段落 | 这段只做什么 | 本项目的内容 | 下一段接什么 |
|---|---|---|---|
| P1 | 说明领域为什么在意 | 科学工具已经成为 agent 的可调用能力，同一性质由多个 provider 估计 | 正常返回不等于可用 |
| P2 | 给出真实失败 | 同一分子/端点的 provider 结果可能分歧，格式正常但结论错误；给一个可复核例子 | 选择时还不知道谁会错 |
| P3 | 解释旧方法为什么不够 | 未选 provider 输出不可见；correctness 只对已选工具产生且可能延迟；post-call confidence 不能回填 pre-call selector | 需要明确的信息时序 |
| P4 | 给出全文最重要的 insight | 把调用前选择、调用后验证/升级和 delayed update 放进同一个事件合同；JEV 是可恢复的动态状态 | insight 必须进入形式模型 |
| P5 | 一两句说方法 | 选择器、验证器、更新器各自的输入输出、状态和开销 | 下一节定义对象和执行步骤 |
| P6 | 列出可验证贡献 | 每项写主张、最近邻、证据和失败条件；没有结果时不写“提升” | 后文用 RQ 和表图回答 |

正文不写“我们先试了 A，再改成 B”的编年史。失败尝试留在消融、错误分析或附录；主文先给读者最终的问题、机制和比较边界。

### 每个段落的内部结构

每个段落默认由三步组成：

1. **Topic sentence**：第一句说清本段要证明、定义或区分的关系；
2. **支持句**：给事实、反例、公式、引用或结果；新符号先解释，再给具体 case；
3. **桥接句**：说明这段为什么把问题交给下一段。

一段只完成一个动作。问题重要性、方法定义、实验结果和局限不能挤在同一段里。把所有段落第一句抽出来后，应该仍能读出：`真实分歧 → 选择时序 → 旧方法缺口 → 动态 JEV insight → 接口 → 证据 → 边界`。

### 各章节的行为逻辑

- **Abstract**：现实实践 → 具体失败 → 命名对象 → 机制改变了什么 → 覆盖的任务/反馈/对照 → 真实 headline result → 机制性边界 → 持久教训。没有 confirmation 数字时，不能用 development replay 数字冒充方法效果。
- **Related Work**：按冲突关系写，不按年份堆。至少区分 static/offline routing、contextual online provider selection、delayed/partial feedback 和 dynamic pool。P04/P06 已覆盖 contextual provider selection，本文必须说明自己增加了什么约束。
- **Problem/Method**：每个小节先用一两句说明本节目标；然后按“输出接口 → 输入与信息边界 → 执行步骤 → 公式/伪代码 → 替代方案为什么不够”的顺序展开。
- **Experiments**：按研究问题组织，不按执行顺序。RQ1 测 direct selection，RQ2 测 post-call verification，RQ3 测 provider/version event 后的 recovery，RQ4 测 delay、failure、menu、endpoint 和 scaffold 边界。主表回答主问题，消融解释机制，错误分析说明边界。
- **Discussion**：解释结果意味着什么，不重复表格数字；把结论限制在真实 provider 资格、数据端点和反馈合同覆盖的范围内。
- **Conclusion**：只留一条持久教训，不引入新方法、数据或未来工作清单。

### 行文风格

- 一个概念只用一个术语：JEV、selector、verifier、updater、provider 不互换叫法；
- 先用日常语言解释，再给术语和正式定义，再给例子；
- 公式前先说它要算什么，公式后说明如何由日志恢复；
- 主动语态、短句、具体动词，少用“显著”“有效”“创新”等没有证据的形容词；
- 每条引用都要完成对比工作，不能只挂在句末；
- 用绝对差、区间和分母表达结果，不用过多小数位制造确定性；
- 强主张必须有对应证据，证据不够就缩小主张；负结果保留在能解释机制边界的位置。

## 故事线的写作验收

### 1. Topic-sentence 检查

只读引言、方法、实验、讨论的第一句，陌生读者应该能复述：问题是什么、旧方法为什么不够、我们改变了什么、哪张图/表能推翻它、何时不工作。

### 2. Claim–evidence 检查

每个贡献写成四列：`claim / 最近邻 / 证伪实验 / 当前证据状态`。当前候选主张分别对应 direct selected-only selection、delayed online update、post-call verification/escalation。若一条证据被拿来同时证明三件事，默认不通过，除非实验中有三个独立 intervention。

### 3. Reviewer 五问

给审稿人标题、摘要、引言和主图，他应该能回答：

1. 具体失败是什么？
2. P04/P06 等最近方法为什么不够？
3. 新机制改变了哪个信息或计算？
4. 哪张图/表能推翻它？
5. 在什么条件下不工作？

答不出来时，不增加泛背景；先修 P2–P5 的转接或收窄主张。

### 4. 这套规则的边界

这套规则是本项目的内部写作与论证标准，不是 AAMAS 的官方模板，也不保证录用。它不要求每篇论文必须六段引言或四个 RQ；它要求本论文的故事、方法、实验和文字遵循同一条可检查的因果链。真正能否投稿，仍取决于问题重要性、方法 soundness、最近邻差异、真实证据和可复现性是否同时成立。
