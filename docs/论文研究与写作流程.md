## 1. 总原则

这套流程的目的，是让 idea、方法、benchmark、baseline、实验和论文互相能对上。它不把“多个 agent 同意”当成创新，也不把自动审稿分数当成真值。所有经验结论必须回到原始实验日志，所有外部事实必须回到已核验的一手来源。

每个阶段只解决一个问题：

1. 研究问题是不是清楚；
2. 候选机制是不是比最近邻多了可检验的东西；
3. benchmark 和 baseline 是否公平；
4. 实验能否把主张推翻或支持；
5. 论文是否把证据写对。

大方向冲突进入人工决策门；小的实现选择由 coordinator 按现有决议和合同处理。worker 不直接改生效主线文档。

## 2. 阶段门

| 阶段 | 要回答的问题 | 必须产物 | 通过条件 |
|---|---|---|---|
| P0 Charter | 这轮只研究什么，不研究什么？ | `research/charter.md` | venue、中心问题、非主张、资源边界和当前 gate 写清 |
| P1 Evidence | 最近邻和一手证据是什么？ | `sources.jsonl`、`evidence.jsonl`、`claims.jsonl` | 每个关键外部 claim 有可回查来源，快筛摘要不直接入正文 |
| P2 Idea | 有没有至少三个不等价方向？ | `idea_matrix.md`、candidate cards | 每个候选都有 gap、机制、最近邻、预测、最小实验和 kill criterion |
| P3 Debate | 关键假设经得起攻击吗？ | `debate.md`、claim graph、decision matrix | 证据、反例、决定性测试和未决异议都被记录；不能靠多数票过门 |
| P4 Mechanism | 公式和更新能不能真的算？ | method/math audit、counterexample tests | 状态、动作、反馈时钟、更新算子、复杂度和实例化例子齐全 |
| P5 B-lock | benchmark/baseline 是否能证明主张？ | authoritative manifest、baseline contract、实验矩阵 | Gate A/B 通过；同菜单、同信息、同预算、同反馈时钟 |
| P6 E-lock | 实验是否可证伪、可复核？ | `experiment_card.md`、pre-results review | RQ、estimand、controls、seeds、统计、失败语义、停止条件和 verifier 冻结 |
| P7 Execute | 实验是否按合同真实运行？ | raw JSONL、config、hash、失败现场 | 先 CPU/smoke + 独立 verifier，再单条 Nebula 任务；不丢失败 |
| P8 Reconcile | 数字和主张是否逐项对应？ | result table、claim–evidence map、analysis report | 每个经验句能追溯到 run/table/figure；不改 raw result 迁就故事 |
| P9 Draft | 论文是否按 RQ 和论证链组织？ | LaTeX draft、figures、refs | field assumption → failure → named object → mechanism → evidence → boundary |
| P10 Red-team | AAMAS 审稿人会从哪里拒稿？ | 五角色 review、确定性 audit、revision map | CRITICAL 问题未闭合时不能标 Accept |
| P11 Release | 是否可以交付/投稿？ | final PDF、supplement、source manifest | 引用、数字、日志、代码、模板和版本全部可复核 |

研究可以从 P0/P1/P2 并行准备，但不能跳过 P3–P6 直接用远程结果倒推方法。当前项目 Gate A/B/C 仍 HOLD，因此暂不把新效果型 A800 任务当作下一步。

## 3. Idea card 和 debate 协议

### 3.1 Candidate card

每个候选方向使用同一张卡：

```text
problem / failure mode
gap relative to nearest prior work
mechanism and state/action/feedback definition
falsifiable prediction
smallest decisive experiment
closest alternatives and fair controls
likely failure mode
kill criterion
data/compute feasibility
```

至少三个候选先独立产生，再交给审查角色。候选不能只改名字、拼接常见组件或把开发结果写成预测成功。

### 3.2 角色和轮次

默认六个角色：literature scout、domain specialist、methods/statistics auditor、feasibility/compute auditor、devil's advocate、theory–experiment auditor。每条实质意见必须使用：

```text
POSITION: support | challenge | clarify | revise | unresolved
TARGET: claim / assumption / design choice
EVIDENCE: source ID + locator，或 NONE
REASONING: 证据为什么影响目标
DECISION TEST: 哪个最小观察会改变立场
CONFIDENCE: 0.0–1.0 + 理由
```

轮次固定为：

1. Round 0：各角色独立，不看其他人的结论；
2. Round 1：每人只攻击高影响假设，必须附证据或明确 `NONE`；
3. Round 2：候选作者回应、修改、让步或标记 unresolved；
4. Synthesis：coordinator 生成 claim graph、support/objection/decision-test 矩阵和下一步 experiment card。

若一整轮没有新证据或新决定测试，立即停止；最多三轮。少数意见如果能改变实验或投稿结论，必须保留。

### 3.3 辩论的反事实

只有当我们要声称“debate 过程本身带来收益”时，才运行：single-agent、no-debate、majority-vote、structured-debate 四组反事实，并报告质量、成本、延迟和 false alarm。普通研究决策只需按协议审查，不把每次讨论都扩成实验。

## 4. Orca 执行方式

Orca 是任务和证据的控制面。标准 DAG 如下：

```text
P0 charter
  ├─ literature task
  ├─ domain/data task
  ├─ method/theory task
  ├─ feasibility task
  └─ devil task
       ↓
debate-1 → debate-2 → coordinator synthesis → human decision gate
       ↓
proposal → experiment card → CPU/verifier → one remote run
       ↓
reconciliation → paper draft → five-reviewer red team → release gate
```

执行约束：

- 一个 role 一个 Orca task/worktree；role 只写自己的报告和 evidence records。
- coordinator 读取结构化产物后更新 `decision matrix`；worker 不直接改三份生效主线文档、authoritative manifest 或原始日志。
- 阶段之间使用 Orca decision gate；gate 未通过，后续 task 保持 blocked，不靠聊天里的“差不多”放行。
- `task/` 保存实验卡和报告，`experiments/logs/` 保存 raw evidence，`research/` 保存来源与论证；每个 task 的 handoff 要写路径、状态、未决问题和下一步。
- Orca CLI/runtime 不可用时，不能把普通 collaboration subagent 结果冒称为 Orca Run；可先按同一 artifact schema 工作，恢复 runtime 后再绑定 Run。

当前 Orca 适配只采用官方通用 `orca-cli`/`orchestration`，没有找到官方 paper 专用 skill。PaperOrchestra 和第三方 paper-orchestration 可以借其 artifact/章节分工，但不能覆盖本项目的 benchmark、baseline、真实反馈和 AAMAS 验收门。

## 5. 论文写作和审稿收口

### 5.1 成稿结构

正文按“张力—根因—洞察—机制—证据—边界”推进：

1. 领域现有做法和隐含假设；
2. 具体 failure mode；
3. 现有方法为什么在该信息边界下失效；
4. 一个中心 insight 和命名对象；
5. 方法接口、更新时序和可计算机制；
6. RQ-driven 主表、消融、错误分析和成本；
7. 适用边界、失败结果和可复现 artifact。

### 5.2 终稿红队

终稿用五个独立视角：EIC/significance、methodology/statistics、domain/related work、systems/reproducibility、devil's advocate。先独立报告，再由 editor 综合。所有批评要指向段落、表格、数字或来源；CRITICAL objection 未解决，不能靠润色标记通过。

最终还要经过确定性检查：引用存在且支持 claim、表格数字能从 raw logs 重算、实验矩阵与 baseline contract 一致、模板编译通过、supplement 可复现。

## 6. 当前项目的直接用法

当前从 P0/P1 重新开一份 charter，但执行重点在 P3–P6：

1. 继续使用现有的 BBB authoritative manifest、development baseline master table 和 Gate A/B/C audit，不重造 benchmark。
2. 为动态 JEV 只保留有新信息来源、明确决策实验和 kill criterion 的候选；普通 online head/LinUCB 的负结果已入证据链，不重复调参。
3. debate 的第一轮审查 benchmark qualification、baseline fidelity、反馈时钟和动态 event 定义；第二轮才审方法公式和 Agent 端到端 claim。
4. Gate A/B/C 全部通过后，才冻结 P6 experiment card 并建一条 A800；结果返回先做 P8 reconciliation，再写摘要 headline。

这份流程是过程标准，不会自动改变三份研究主线文档中已经确认的 benchmark、baseline 或创新点。任何改变主线的决定，仍按决议文件规则单独记录。
