# 工具调用能力上限作为总故事

## 背景

此前的故事线容易被读成“做一个动态 provider selector”或“学习 provider 的联合可靠性”。这两个表述都只是研究切口，不能承载项目最终目标。项目真正要提升的是 agent 解决任务的能力上限：当多个工具功能重叠但工作范围不同，agent 能否更聪明地选择、解释、验证、互补、拒答和继续调用。

## 决定

1. 论文总故事定义为：**通过让 agent 更聪明地调用工具，提升它在真实任务上的能力上限。** 工具调用不是一次选择，而是一个从工具适配到证据决策再到持续适应的过程。
2. “最合适的工具”不是全局平均准确率最高的工具，而是结合当前任务、工具历史工作范围、已释放反馈、当前证据和调用成本后，预期最终损失最低的工具。
3. 得到第一个工具结果后，agent 要把它当成证据，判断下一步是：调用相似工具相互验证；调用互补工具获取不同证据；直接给出答案；拒绝回答；或继续申请更多工具。
4. MIRA 是承载这条总故事的统一方法名。联合可靠性、工具工作范围、证据后验、调用价值和 delayed outcome 更新都是方法组件或候选实现，不得单独取代总目标。
5. 现有一次调用 direct selection 继续作为 primary benchmark，用来证明第一步工具适配；两次及多次调用作为 sequential evidence extension，用来证明验证、互补、拒答和继续调用能力。扩展任务不得静默替换 primary。
6. 实验结果必须分层报告：首次选择质量、后续证据决策质量、持续适应质量和最终任务能力。不能用后续调用的收益冒充首次选择提升，也不能用 likelihood 改善直接冒充 agent 能力提升。

## 理由

- 这个总故事把医药 provider 路由放回 Agent 研究语境：provider 是具有不同工作范围和错误结构的外部能力源，agent 的核心能力是管理证据和调用成本。
- 它保留了当前 benchmark 的可执行切口，同时为验证、互补、拒答和实时适应提供自然扩展，不需要一开始把任务扩展成无边界的通用 Agent benchmark。
- 它能吸收当前负结果：固定赢家、边际 residual 和单纯 action change 都不能代表能力提升；必须看最终可靠答案、错误交付、拒答、调用成本和延迟反馈下的恢复。
- 它也约束创新叙事：联合模型只有在改善后续证据决策和最终 utility 时，才能成为 MIRA 的核心机制；只有改善预测 likelihood 时，只能作为内部模型或辅助分析。

## 后果

- `docs/研究主线/生效/01-故事线与创新.md` 升级为 v004，并将能力上限、工具工作范围和证据决策写入主线。
- `02-方法论.md` 后续版本必须把状态拆成工具工作范围状态与当前任务证据状态，并明确动作集合包含验证、互补、拒答和继续调用。
- `03-Benchmark与Baseline.md` 后续版本必须保留 E2a primary，同时为 sequential extension 增加同预算的 fixed cascade、Independent Evidence、Joint Evidence、拒答成本和最终 utility 指标。
- 当前 MIRA-Relay、Joint Reliability candidate、实验评分和 confirmation 状态不因本决议自动改变；候选仍需通过对应 CPU/A800 和独立确认闸门。
- 论文标题继续遵循已有 0007 决议，不把 MIRA 写入标题。
