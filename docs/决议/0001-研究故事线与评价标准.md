## 1. 这份决议要解决什么问题

项目里所有关键选择都要回到同一条主线：我们要解决的真实问题是什么，方法为什么能解决它，实验为什么能证明它，论文为什么值得 AAMAS 审稿人相信。

故事、方法、benchmark、baseline 和创新点不能各自成立、互相脱节。它们必须形成一条可以被复核、验证和证伪的链条。

## 2. 故事线与方法论

研究故事线与方法论必须同时满足以下要求：

- 充分：关键背景、问题、限制、方法、实验和结论不能缺环。
- 合理：每个设计都来自任务痛点、信息边界或可验证的理论理由，不能只因为某个工具方便就加入。
- 完备：输入、决策、反馈、更新、评估和失败处理都要定义清楚。
- 自洽：问题定义、数学形式、算法、benchmark、baseline 和论文主张不能互相矛盾。
- 有创新性：创新必须服务于真实问题，能说清与已有方法的差异、必要性和可验证结果。
- 切口明确：论文只围绕一个清楚、足够具体的问题展开，不用堆叠模块来制造贡献数量。

任何候选方法都要回答四个问题：它解决了哪一个已确认的痛点？它使用了什么新信息或新结构？它与最近邻方法到底差在哪里？如果结果失败，我们如何知道是方法失败、信息不足还是实验设计失败？

## 3. Benchmark 与 baseline

### 3.1 Benchmark

Benchmark 的选择必须足够合理，能够真正支撑论文要证明的结论。主 benchmark 必须具备公认性和权威性，至少要能说明任务来源、数据来源、真值定义、评测协议和社区认可依据。

自建数据或自建回放环境可以作为补充，也可以用于工程验证；如果要承担论文主结论，必须另外给出清楚的权威来源、独立真值和可复现的构造与审计证据。数据现成、规模较大或与现有代码契合，不能单独构成采用它作为主 benchmark 的理由。

Benchmark 还必须与主张匹配：如果主张是实时适应，就必须有真实或严格回放的反馈时序；如果主张是工具选择，就必须在调用前限制可见信息；如果主张是验证或拒答，就必须把调用后信息和拒答成本写入评测。

### 3.2 Baseline

Baseline 必须既能完成同一个任务，又足以代表当前比较水平。候选 baseline 至少应覆盖以下一种或多种角色：

- 近期、在同类任务上有代表性的先进方法；
- 与主方法最接近的公开方法或开源实现；
- 能检验核心机制是否真的有效的 matched-backbone 对照；
- 仍然有解释力的经典方法或强固定策略。

每个 baseline 都要记录原论文问题、输入、监督、决策时点、更新方式、许可证、代码版本和本项目中的适配改动。不能把年代久远、任务不匹配的方法凑数，也不能只挑容易超过的对照。

## 4. 创新点

创新点必须立得住，不能因为一个小问题、一个实现细节或一次未充分的实验就被轻易推翻。

判断创新点时，必须先检查：

1. 它是否直接服务于已确认的任务痛点；
2. 它是否有清楚的数学或机制解释；
3. 它是否与最近邻工作做过公平对照；
4. 它是否有能推翻自己的实验条件；
5. 它的收益是否来自方法本身，而不是信息泄漏、数据选择、预算或实现不公平。

如果出现问题，先区分“需要修正的实现/实验问题”和“创新假设本身不成立”。前者应修复后复核，后者才进入创新点修改讨论。任何推翻、缩小、替换或重新定义创新点的动作，都必须先与用户讨论并获得双方确认，不能由单次失败结果自动完成。

## 5. 决议的应用场景

遇到以下情况，先查阅本目录中状态为“生效”的决议：

- 有两个或多个方案都能做，但无法判断取舍；
- 现有数学形式、benchmark 或 baseline 不足以支持下一步；
- 实验结果与原故事线冲突；
- 任务开始偏离已确认的研究切口；
- 想要推翻、缩小或替换已有创新点；
- 想为了得到更好的数字临时改变数据、预算、反馈权限或评测规则。

如果决议已经给出边界，就按决议执行；如果没有覆盖当前问题，先提出候选方案并写明需要双方确认的地方，不把临时判断当成统一标杆。
