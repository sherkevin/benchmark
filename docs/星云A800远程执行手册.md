## 一、卡名先说清楚：这里没有 A100

队列里的卡是 **A800-SXM4-80GB**，不是 A100。A800 是 A100 的国内合规版本，显存同为 80 GB，差别在 NVLink 带宽被限制（A100 是 600 GB/s，A800 是 400 GB/s）。

这件事有实际影响：**单机多卡的数据并行几乎不受影响，跨机的模型并行会受影响**。本项目跑的是 49 个工具 × 730 分子的批量推理，属于单机内并行的场景，A800 与 A100 没有可感差别。真正要留意 A800 互联的场景是大模型的张量并行跨机切分，本项目不涉及。

`实测` `nebula-cli queue list` 的输出：

```
| Queue                  | GPUs                              | Q.CPU | Q.GPU | Q.Mem | Avail | Backlog |
| damo_genomic_gene_a800 | A800-SXM4-80GB,空闲GPU:84(8*10+4*1) | 2192  | 120   | 30960 | 84    | 0       |
| damo_genomic_gene_h20  | H20,空闲GPU:8(8*1)                  | 192   | 8     | 960   | 8     | 0       |
| damo_genomic_gene_l20z | L20Z                              | 0     | 48    | 0     | 48    | 0       |
```

读这张表的方式：

- `8*10+4*1` 是空闲卡的**物理分布**——10 台机器各空 8 卡，另有 1 台空 4 卡。这一列比 `Avail` 有用，因为它告诉你单机最多能拿到几张连续卡：**8 张**。申请 8 卡以上必然跨机。
- `Q.CPU 2192 / Q.GPU 120 / Q.Mem 30960` 是配额总量。除下来每卡约 18 核、258 GB 内存，但这是上限不是承诺。
- `l20z` 那行 Q.CPU 和 Q.Mem 都是 0，说明它是公共池按卡时计费的队列，跟 a800/h20 的独占配额不是一回事。本项目用 a800。

`实测` 每卡实际能拿到多少，看团队正在跑的 9 个 Notebook（`nebula-cli queue get damo_genomic_gene_a800`）：1 卡的一律是 `cpuCores 15 / memoryGB 240`，4 卡的是 `60 / 960`，8 卡的是 `120 / 1875`。**每卡 15 核 240 GB 是经过验证能调度成功的配比**，`neb` 的默认值就取这个。

## 二、先想清楚：你要的是哪一种执行形态

平台有两种形态，选错了会很痛。

**Notebook（开发机）**：一个长期存活的容器，网页里开 JupyterLab / WebIDE / Terminal。它是交互式的，适合装环境、试代码、看数据。三个硬约束：

- 页面 3 天不访问会被判为空闲回收（判据是页面访问，不是 CPU 占用），所以长任务要用 tmux 兜住，并且每天去开一次页面。
- `/home` 有 200 GB 和 40 万 inode 的上限。数据集别解压到这里。
- 容器里禁止跑 Codex 之类的 Agent 程序，2026-03-25 起的生产网红线。

**训练任务（`run mdl`）**：提交后平台拉起容器、执行你的 entry、跑完退出。它不是交互式的，但**不受 3 天回收约束**，可以跑很久，失败了有 logview 可查，产物落 OSS。

本项目的 49 工具跑批应该走训练任务。理由不是"训练任务更高级"，而是跑批的本质是**无人值守的长流程**，而 Notebook 的 3 天回收正好卡在这个需求的喉咙上。Notebook 留给装环境和调试用。

一个容易误会的点：跑批不是训练，但用训练任务提交完全合适。`run mdl` 的语义就是"拉起一个容器执行 entry"，它不关心你里面跑的是反向传播还是分子预测。

## 三、代码怎么进容器：默认行为是个陷阱

这是全篇最重要的一节。`nebula-cli run mdl` 有三种代码来源模式，`源码` 里的判定函数 `detectCodeSourceMode` 说得很直白：

```js
function detectCodeSourceMode(params, ideWorkspace) {
  const hasIde = !!(ideWorkspace || params.ide_workspace);
  const hasGit = !!params.git_path;
  if (hasIde && hasGit) { printAndExit("不能同时指定 --ide_workspace 和 --git_path"); }
  if (hasIde) return "ide_workspace";
  if (hasGit) return "git";
  return "oss";       // ← 什么都不传时的默认值
}
```

**默认模式 `oss` 会把当前工作目录整个打成 zip 上传。** `源码` 里的 `zipExcludingFiles(this.workDir, ...)`，`workDir` 默认是 `./`（`getNebulaWorkDir` 的兜底分支）。`.git` 永远排除，`--ignore` 是追加排除。

在本仓库根目录跑，就是打包 4.9 GB：`archive/` 1.7 GB、`.venv/` 730 MB、`data/` 596 MB、`src/` 518 MB。`源码` 里有一道 1 GB 的闸门（`checkWorkdirSize`），超了会拒绝并提示加 `--force`——**不要加 `--force`**，那是把 4.9 GB 真的推上去。

`实测` 2026-09-21 在一次误提交里看到了完整过程：

```
Generated zip file path: /tmp/_nebulactl_504cb4d3.../xdl_python_package.zip
[OSS Upload] Size: 0.00 MB (1179 bytes)
[OSS Upload] Bucket: ados-nebula
[OSS Upload] URL: http://ados-nebula.oss-cn-zhangjiakou.aliyuncs.com/NEBULACTL_%23_damo_genomic_gene_.../xdl_python_package.zip
```

那次只有 1179 字节，因为是在一个空临时目录里跑的。但它暴露了两件事：代码包传到平台自己的 `ados-nebula` 桶（不是业务桶），而且**传完就提交，没有二次确认**。

所以本项目的规矩是：**永远走 git 模式**。传 `--git_path` 就完全跳过本地打包和体积检查，平台侧自己去 clone。这也顺带解决了可复现性——任务里跑的是哪个 commit 有明确记录。

```bash
--git_path=git@gitlab.alibaba-inc.com:jingwu.jw/benchmark.git \
--commit_id=21b39e905675165f2517502da6b2c7d45e6a7db6
```

`源码` 里还有一条强制校验：用 `--git_path` 时必须同时给出 `--git_branch`、`--commit_id`、`--git_tag` 之一，否则直接退出。**优先用 `--commit_id`**，因为分支会动——你提交之后、容器启动之前，如果有人往分支推了新代码，跑的就不是你审过的那份。钉 sha 不会。

两个前提：

1. 仓库必须在**内网 GitLab**（`gitlab.alibaba-inc.com`）。生产容器不能 clone github / modelscope，这是平台红线。本仓库的 origin 已经是内网地址。`实测` `git remote get-url origin` → `git@gitlab.alibaba-inc.com:jingwu.jw/benchmark.git`。
2. 那个 commit 必须**已经推到远端**。平台侧 clone 的是远端，本地未推送的提交它看不到。`neb doctor` 会检查这一条。

第三种模式 `--ide_workspace` 是把训练工作台的代码空间当来源，适合在工作台里长期迭代的场景。本项目不用——本地有完整仓库和内网 remote，git 模式更简单也更可控。

## 四、cluster.json：三个键都必须写

`源码` 里 `genXdlConfig` 是这么读 cluster.json 的：

```js
worker: {
  instance_num: workerCount,
  cpu_cores: clusterConfig.worker.cpu / 100,
  gpu_cores: clusterConfig.worker.gpu / 100,
  memory_m: clusterConfig.worker.memory
}
```

`cpu` 和 `gpu` 的单位是**百分之一**（100 = 1 核 / 1 卡），`memory` 单位是 MB。CLI 直接做除法，所以三个键缺任何一个都会得到 `NaN` 而不是报错——生成的配置带着 NaN 提交上去，失败信息会很莫名。**别信"cpu 和 memory 可以不填，系统自动算"这种说法**，那是老 nebulactl 文档里的话，跟这个 CLI 的实现不符。

单卡（对应团队 Notebook 的实测配比）：

```json
{"worker": {"cpu": 1500, "gpu": 100, "memory": 240000}}
```

8 卡：

```json
{"worker": {"cpu": 12000, "gpu": 800, "memory": 1920000}}
```

`neb` 会自动生成这个文件放在临时目录里，用 `--file.cluster_file=<路径>` 指过去，不需要你在仓库里留一个 cluster.json。

`--file.cluster_file` 是个**透传参数**，所以它不出现在 `nebula-cli run mdl --help` 的选项表里。`源码` 确认 `run` 命令注册时带了 `allowUnknownOption(true)`，未知参数会进 `params` 再写进配置。同理，`--env` 这类老 nebulactl 的参数在这个 CLI 里没有对应实现，别指望它生效——要传环境变量得另想办法（写进 entry 脚本，或用 `--property_file`）。

## 五、worker_count 是总卡数，不是节点数

`源码`：`instance_num: workerCount`，配合 `gpu_cores = clusterConfig.worker.gpu / 100`。

所以最终占用的卡数 = `worker_count × (cluster.json 的 gpu / 100)`。两种写法都能表达 8 卡：

- `--worker_count=8` + `gpu: 100` → 8 个 worker，每个 1 卡（8 个独立容器）
- `--worker_count=1` + `gpu: 800` → 1 个 worker，8 卡（1 个容器，容器内自己做并行）

**选哪种取决于你的代码怎么写。** 批量推理跑 49 个工具，工具之间互不相干，用第一种（多 worker 各跑一份分片）比第二种简单，不需要写任何分布式代码。真要用第二种，容器里能拿到 `RANK`、`WORLD_SIZE`、`LOCAL_RANK`、`MASTER_ADDR` 这些环境变量（`文档`：分布式训练常见环境变量）。

超过 8 卡必然跨机（第一节那张 `8*10+4*1` 说明了单机上限），跨机就得自己处理分布式初始化。`neb` 对此有一道护栏：申请超过 8 卡时直接拒绝，要 `--allow_big` 才放行。

## 六、镜像：algo_name 有白名单

`实测` 漏传 `--algo_name` 时平台的原话：

```
algo_name None not in damo_genomic_gene_a800 allow algo_name list:
['pytorch201', 'pytorch210', 'pytorch220', 'pytorch240', 'pytorch260',
 'pytorch280', 'pytorch1131', 'pytorch2100', 'pytorch2120',
 'pytorch2100_py310_cu128']
```

这份白名单是队列级的，写死在服务端。`neb` 把它硬编码成 `ALLOWED_ALGO_NAMES`，提交前先校验，免得又白提交一次。

本项目选 **`pytorch280`**：cuda 12.8、python 3.10.13、自带 conda（`文档`：平台 Pytorch 镜像 ReleaseNotes）。选它的理由是 `requirements.txt` 钉的是 py3.10，且注释里写明"云端实测：py3.10.14 + mcp 1.29.0 + matplotlib 3.10.9 可用"。

装依赖走 pip 镜像，不是 conda 源：

```bash
pip3 install -r requirements.txt \
  -i http://yum.tbsite.net/aliyun-pypi/simple/ \
  --extra-index-url http://yum.tbsite.net/pypi/simple/ \
  --trusted-host yum.tbsite.net
```

**生产网禁 conda 源**，仓库里那些 `conda env create -f environment.yml` 的安装脚本在容器里会失败。派单文档 `docs/远程跑批任务_全部工具.md` 里 CardioTox 等工具写的是 conda 路子，迁到星云时要逐个改成 pip。这是一笔还没做的工作。

要装 Java（FPADMET、Toxtree、EPA TEST、CypReact 都需要）或者 R（FPADMET），基础镜像里未必有，可能得做自定义镜像（`文档`：制作自定义镜像），或者在 entry 里现装——后者每次任务都要重装，慢但省事，适合先跑通。

## 七、数据怎么读：OSS 挂载

`文档`（挂载 OSS）里的规则：OSS 桶挂到容器内**固定路径 `/data/oss_bucket_0/`**，`oss://<bucket>/A/B` 对应 `/data/oss_bucket_0/A/B`。挂多个桶时按填写顺序编号 `_0`、`_1`。

提交时加四个参数：

```bash
--oss_access_id=<AK> --oss_access_key=<SK> \
--oss_bucket=ai4sci-develop-storage \
--oss_endpoint=oss-cn-zhangjiakou.aliyuncs.com
```

`--oss_endpoint` **不能带 `http://` 前缀**，文档专门警告过这点。

业务侧的存储现状（2026-09-20 实测列举）：`ai4sci-develop-storage` 桶里按人名拼音分目录，`tianbian/data/`、`caixu/odysseus/`、`zhongyin/lingshu-cell/`。本项目的目录是 `jingwu/`，代码快照在：

```
oss://ai4sci-develop-storage/jingwu/benchmark-snapshots/benchmark-snapshot-20260920.tar.gz
```

509 MB，钉在 commit `21b39e9`，对象元数据带 `x-oss-meta-local-md5=08b4e9d22507614362b9cb5e839e6f43` 可自查完整性。挂上之后容器里是 `/data/oss_bucket_0/jingwu/benchmark-snapshots/`。`neb oss_path` 可以在两种写法之间互转。

两个使用要点：

- **代码走 git，数据走 OSS，别混。** 有了 git 模式就不需要从 OSS 拉代码快照，快照的作用是备份和给没有内网 GitLab 权限的人用。
- **OSS 挂载是对象存储，随机小文件读写很慢。** 代码解压到 `/home` 跑，数据尽量流式读，别在挂载路径上跑大量小文件的循环。

AK/SK 不能写进命令行——会进 shell history，也会被 `neb` 之外的任何日志记下来。放在仓库根的 `.env`（已在 `.gitignore` 里，仓库约定"AK 只放仓库根 .env"），`neb` 从那里读，并且打印命令时会把凭证值替换成 `***`。

`.env` 里要加的两行：

```
NEBULA_OSS_ACCESS_ID=<AK>
NEBULA_OSS_ACCESS_KEY=<SK>
```

## 八、提交与观察的完整流程

### 第 0 步：体检

```bash
cd /Users/jingwu/work/benchmark
tools/nebula/neb doctor
```

只读，检查 CLI 是否安装、登录态、默认项目、`algo_name` 是否在白名单、git remote 是否内网和 **HEAD 是否已推到远端**。普通 git-only 任务不需要 OSS 凭据；任务要挂 OSS 时改用 `neb doctor --mount_oss`，它才会把 OSS AK/SK 作为放行条件。最后一条最容易漏——本地提交了没推，git 模式会 clone 到旧 commit，跑出来的结果跟你以为的代码对不上。

退出码 0 表示全清，1 表示有问题（问题逐条列出）。agent 应该在提交前无条件跑一次。

### 第 1 步：看队列有没有卡

```bash
tools/nebula/neb queues
```

### 第 2 步：dry-run 看提交计划

```bash
tools/nebula/neb submit \
  --job_name jingwu_smoke_001 \
  --entry src/run_validation.py \
  --user_params "--limit 4"
```

输出（实测）：

```
=== submission plan ===
project        damo_genomic_gene
queue          damo_genomic_gene_a800
job_name       jingwu_smoke_001
image          pytorch280
resources      1 worker(s) x 1 GPU = 1 GPU total
               per worker: 15 core, 240 GB
               job total:  15 core, 240 GB
cluster.json   {"worker": {"cpu": 1500, "gpu": 100, "memory": 240000}}
capacity       84 GPU free, requesting 1 -> fits
code source    git git@gitlab.alibaba-inc.com:jingwu.jw/benchmark.git @ 21b39e905675
entry          src/run_validation.py
user_params    --limit 4

dry-run only.  Re-run with --yes to actually submit.
```

`capacity` 那行是提交前查一次空闲卡数。**卡不够不会失败，会进 Backlog 排队**，看起来像卡住了，所以提前知道比事后困惑好。

### 第 3 步：真提交

加上 `--yes`：

```bash
tools/nebula/neb submit \
  --job_name jingwu_smoke_001 \
  --entry src/run_validation.py \
  --user_params "--limit 4" \
  --yes
```

成功后输出里会有 `task_id: <32位十六进制>`，把它记下来——后面所有查询都靠它。加 `--wait` 会阻塞到任务结束，第一次冒烟建议加，省得来回查。

### 第 4 步：观察

```bash
tools/nebula/neb status <task_id>              # 状态、退出码、Timeline
tools/nebula/neb logs <task_id> --tail 200     # 默认 worker-0 的 stdout
tools/nebula/neb logs <task_id> -t stderr      # stdout 没线索时看 stderr
tools/nebula/neb diagnose <task_id>            # 失败时让平台的 AI 诊断
tools/nebula/neb list --status FAIL            # 列出失败任务
tools/nebula/neb stop <task_id> --yes          # 停掉
```

网页版 logview 在 `status` 的输出里，形如 `https://nebula2.alibaba-inc.com/log/logview/xdl/view?task_id=<id>`。要看历史每次尝试加 `--application_id`。

### 第 5 步：取结果

结果写到 OSS（容器内 `/data/oss_bucket_0/jingwu/...`），从 Mac 上取回来：

```bash
python3 - <<'PY'
import oss2
b = oss2.Bucket(oss2.Auth("<AK>", "<SK>"),
                "https://oss-cn-zhangjiakou.aliyuncs.com", "ai4sci-develop-storage")
for o in oss2.ObjectIterator(b, prefix="jingwu/results/"):
    print(o.key, o.size)
PY
```

也可以 `nebula-cli task download-code <task_id>` 把任务实际提交的代码包拉回来核对——这是确认"跑的到底是哪份代码"的权威手段。

## 九、踩过的坑与红线

**一，`nebula-cli task <子命令> --help` 不生效。** 会打印顶层帮助而不是子命令帮助。正确写法是 `nebula-cli task help <子命令>`。`实测`

**二，每次调用都会吐一段 `[AES] send fail FetchError ... gm.mmstat.com` 的堆栈。** 那是遥测被网络拦了，不是任务错误，忽略。`neb` 会自动滤掉这段噪音。`实测`

**三，`queue list` 偶发失败返回 `status: 13`。** 重试就好，张家口端点从本机出去经常抖。上传大文件要用断点续传加重试循环，单次 put 大概率超时。`实测`

**四，`run mdl` 不支持 `upload`。** `源码` 里明确抛 `MDL resource does not support upload. Use "run mdl" instead.`

**五，工作目录默认是当前目录，体积闸门 1 GB。** 见第三节。`neb` 用临时目录放 cluster.json，从根上避开这个问题。

**六，`--user_params` 的解析方式特殊。** `源码` 里 `parseStringDict` 按空白切分，`--key value` 和 `--key=value` 都认，但值里带空格会被切断。而且 `-D` 会被替换成 `--`。参数复杂时用 `--property_file`。

**七，同一个状态在两个命令里拼写不同。** `实测` `task list --status FAIL` 返回 0 行，`--status FAILED` 返回 2 行；而 `queue jobs` 的帮助里写的是 `FAIL`。两个命令对同一件事的取值不一致，且传错值不报错、只是静默返回空结果——这比报错更坑，因为你会以为没有失败任务。`neb list` 两种拼写都接受，内部统一成 `task list` 要的 `FAILED`。

**红线，容器里不能跑 Agent 程序。** Codex、Claude Code 这类，2026-03-25 起生产容器禁止。要 agent 参与就让它在 Mac 上调 `neb`，不要在容器里装 agent。

**红线，不能 clone 外网仓库。** github、modelscope 都不行。工具源码要么预先放进 OSS，要么在容器里用内网镜像。这条直接影响了 49 个工具的部署方案——派单文档里 10 个工具的地址是 github，在星云上装不了，得逐个找内网替代或预先把源码传进 OSS。

**红线，不能开隧道、不能挂长驻服务。**
