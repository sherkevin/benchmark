# 12 · 回写文档：更正 v4 与 v2 CSV 的可用性口径

Type: task
Status: open
Blocked by: 06, 07, 08

## 为什么

`docs/Pharma_Tools_Survey.md`（v4）与 `docs/step1_tool_inventory_v2.csv` 现在的"可用性"列记的是**入口存活**，不是功能可用。本轮跑完之后，第一次有了真实的功能状态数据，必须回写——否则两份文档会继续误导（v4 曾用"实测可用"描述入口存活，已更正为"入口存活"，但仍缺功能列）。

## 做什么

1. **v2 CSV 加三列**（不改既有 12 列，ADR-0002 的 schema 不动）：
   - `功能档位（L3/W/V）`
   - `功能核验结果（日期+结论）`：如 `2026-09-XX L3通过（三轮逐位一致）` / `2026-09-XX install_failed: 无arm64轮子`
   - `证据路径`：指向 receipt 或 web_evidence 目录
2. **v4 文档**：在"核验边界"那段之后加一节"功能核验结果"，给出 L3 通过数 / 失败数 / W 档数 / V 档数，并把附录七（功能实跑待办）改写为已完成项与剩余项
3. **更正记录**：v4 附录三追加本轮发现的所有事实更正（预期会有：某些工具实际装不上、某些 web 工具实际已下线、版本号与文档记载不符等）

## 硬约束

- **不许为了让数字好看而调整判据**。某工具 L3 不通过就是不通过，写进表里
- 报数时必须声明边界（项目记忆的教训）：说"N 个工具功能核验通过"时，同一句里写清"N 个中有多少是 L3、多少是 W 档单次取值"
- ADR-0002 的 12 列 schema 不改，只加列

## 验收

- v2 CSV 三列填满，每行都有证据路径
- v4 文档的数字与 `summary_v3.json` 逐项一致（不许两处数字不同）
- 若本轮结果推翻了 ADR-0003 的某条判据，**不要偷偷改判据**，另开 ADR-0004 记录并说明理由
