## 一、决议要点（先总）

| # | 决议 | 一句话 |
|---|---|---|
| **1** | **A/B 按 case 配对，不做全局静态切分** | 每道题自己配一组 A 可见集与 B 侧 gt，推理梯度**是配出来的、不是从库里筛出来的** |
| **2** | **梯度由三个参数调节** | 族内样本数、外推距离、干扰项数量 K |
| **3** | **存在性接口只回"在不在"** | A 内、库外一律返"不存在"；B 内返"存在"；**永不返性质** |
| **4** | **不需要拓扑结构** | 推理在**组成层面**（元素计数）进行，`edit_op` 定义为组成算子而非结构编辑 |
| **5** | **固定映射保留，且必须保留** | 它是 agent 归纳趋势的前提；映射表对 agent 全程不可见 |
| **6** | **材料侧扩数据，不降标准** | 维持药物 15 : 材料 15，由 E1 扩展材料数据源 |

## 二、为什么是 per-case 配对（owner 决议原文的技术展开）

### 2.1 owner 的判断

> agent 要以自己的推理能力和 A 中的知识去推出 B。如果 A 中的知识完全用不上，推出 B 是不可能的；如果 A 中的知识和 B 强相关，那么推出 B 太简单。**可以给每一个 case 自己配 A/B 对，针对性地做匹配。**

### 2.2 这条纠正了什么

监工原先按"一个大 A 库 + 一个大 B 库"的全局静态切分理解，因此把可造题量算成"库里天然形成的同族数"——实测药物侧 124 族、材料侧 9 族，并据此准备下调材料侧题量。

**这个前提是错的。** A 的内容为每道题定制后，族的构成可**按需组织**，容量不再受"天然族数"约束。

### 2.3 实现形态：逻辑视图而非物理多库

| 方案 | 说明 | 采纳 |
|---|---|---|
| 物理多库 | 每个 case 一份独立 A 库快照 | ❌ 30 份快照，存储与一致性成本高 |
| **逻辑视图** | 物理一份大库 + 每个 case 一份**可见集白名单**，agent 的查询被限制在该 case 的可见集内 | ✅ **采纳** |

**与 goal §2b② 的关系**：goal 要求的"物理分层"指 **A/B 之间**必须物理隔离（A 的查询不得带出 B）；per-case 视图是在 **A 内部**再切一层，两者不冲突、需同时成立。

## 三、推理梯度的三个调节参数

替代监工原提的"R² 区间卡"——那是在天然族里**筛**难度，而按 owner 的方案是**配**难度，参数化更直接。

| 参数 | 含义 | 太简单 | 适中（默认） | 太难 |
|---|---|---|---|---|
| **族内样本数 n** | A 可见集里同族、目标性质有序的样本数 | n ≥ 6（趋势一目了然） | **n = 3～5** | n ≤ 2（两点定不了趋势） |
| **外推距离 d** | gt 距 A 内最近同族样本的步数 | d = 1（下一个就是） | **d = 1～2** | d ≥ 3（goal §2b④ 已禁） |
| **干扰项数量 K** | A 可见集里非目标族的分子数 | K = 0（A 里只有一个序列，不用筛就知道外推谁） | **K = 20～30** | K ≥ 50（见 §3.1） |

### 3.1 K 的取值有实测依据

K 直接决定 goal §2b④ 第一条质量门（**A 内不存在不劣于 gt 的解**）的过滤力与判废率。以实测族的外推 gt（logS ≈ −7.098）为例，全库 2,299 条 logS 中有 **44 条（1.9%）不劣于它**：

| K | A 内至少混进一个不劣于 gt 的概率 | 判定 |
|---|---|---|
| 10 | 17.6% | 门的过滤力偏弱 |
| **30** | **44.0%** | ✅ 有实际过滤力且判废率可接受 |
| 50 | 61.9% | 判废率过半 |
| 100 | 85.5% | 绝大多数 case 被判废 |
| 300 | 99.7% | 不可用 |

**取 K = 20～30**：既让质量门有真实过滤力（不退化为重言式），又不至于让多数 case 因"A 内已有更优解"而废弃。

### 3.2 K=0 是必须避免的（本 ADR 新增的约束）

若 A 可见集只放目标族，则：

1. **质量门退化为重言式**——A 里除了目标族没别的分子，"A 内无替代解"自动成立，零过滤力。这正是 `goal.md` §2b④ 明确警告的"不能写成'仅穷举 A 拿不到 gt'"；
2. **题目退化**——agent 无需做任何筛选，看到唯一一个序列直接外推即可，考不出"从噪声中识别相关线索"这层能力。

**故干扰项为强制项，K ≥ 10 写入交付标准。**

## 四、存在性接口（owner 决议 + 已有实现确认）

### 4.1 定义域（三分支写死，与 goal §2b⑤ 一致）

| agent 提交的分子 | 返回 |
|---|---|
| ∈ B | `true`（存在） |
| ∈ A | `false` |
| 库外（既不在 A 也不在 B） | `false` |

**owner 原话**："因为我们的数据库本身就是有限的，对于 agent 预测出来的或者要查询的不存在的分子我们直接返回不存在，请另选就好了。agent 也可以查 B 中的物质，但是只能查存不存在，查不到性质。"

### 4.2 三条硬约束

1. **只返单个 bool**，不带性质、相似度、距离、"接近了"之类的任何提示；
2. **"不存在"的返回文案必须完全一致**——A 内与库外两种情况的返回体逐字节相同，否则可由文案差异反推出"这个分子在 A 里"，进而缩小搜索空间；
3. **`max_attempts ≤ 10`**（已在 `gateway.py:744` 写死 `max(1, min(int(max_attempts), 10))`），超限记 0 分，attempts 计入指标。

### 4.3 返"存在" ≠ 得分

评分依据是 **∈ `G_B`** 且经 B 侧性质复核满足题面目标窗口（goal §2b⑤）。接口返"存在"只是**停止信号**。二者混用会构成自证循环并被暴力枚举攻破。

## 五、不需要拓扑结构（监工原判断的纠正）

### 5.1 owner 的反问

> 为什么需要拓扑结构？

### 5.2 纠正

监工原判"A 侧只有分子式、没有拓扑结构，故 open 无法落地"，理由是 goal §2b 的 `edit_op(anchor) == gt` 需要结构编辑。

**这个理由不成立。** goal §2b③ 举的线索例子就是「**加上一个原子 a 就会增加 xxx 性质**」——这在组成层面完全可表达：

```
[16*]15[19*]25[22*]3  →  加一个 22 号  →  [16*]15[19*]25[22*]4
```

不需要知道该原子加在哪个位置。**`edit_op` 据此定义为组成算子**（增/减某元素若干个），封闭算子集 = {+n 个元素 e, −n 个元素 e}，跳数 ≤2 沿用 goal §2b④。

### 5.3 grounding 三条件的组成层面口径

| goal 条件 | 组成层面的判法 |
|---|---|
| ① `cited_value` 与 trace 中真实工具返回值在容差内一致 | 不变（查的是性质值，与结构无关） |
| ② `anchor ∈ A` | 不变（anchor 是 A 内实体 ID） |
| ③ `edit_op(anchor)` 规范化后 == 所提交分子 | **改为组成比对**：把 `anchor` 的元素计数按 `edit_op` 变换后，与提交的分子式做**多重集相等**判定 |

## 六、固定映射必须保留（监工原判断的纠正）

### 6.1 owner 的裁定

> 不必改，固定映射和分子计数本身就是让 llm 推理逻辑用的，不能改。这里只需要把映射关系隐去就好，测试的时候 agent 看不到这个映射关系。

### 6.2 监工原判为何是错的

监工原判"固定映射（C→16、H→19、O→22、N→81）可被频率分析破解，属 PR-31 残留"。

**错在两处**：

1. **固定性是推理的前提，不是漏洞。** 若每个 case 随机映射，agent 无法跨样本归纳"16 号元素增加 → logS 下降"——**推理链直接断掉**，open 类不成立；
2. **攻击路径在评测环境下不通。** 破解需三步：猜对元素映射 → 拼出真实分子式 → 查外部库反查真名。而评测环境中 agent 只有本项目的 mock 工具、**无外网访问**，第三步不可达。

### 6.3 边界的正确划法（写入本 ADR 供后续引用）

| 信息 | 给不给 | 理由 |
|---|---|---|
| 真实 InChIKey / 真实分子式字符串 / 真名 | ❌ **不给** | **一串即可直接定位**分子，无需推理 |
| 匿名域内的元素计数（固定映射下） | ✅ **必须给** | 需破解+拼式+查外库三步且外网不可达；且它是推理素材 |
| 映射表本身（`element_to_label`） | ❌ **不给** | agent 全程不可见（已在 `anonymization_mapping.json` 的 `visibility` 字段声明） |

**监工留痕**：此前把"真实 InChIKey"当优点记功（PR-31 成因）、又把"固定映射"当漏洞要改，是同一类错误的两个方向——都没分清"能直接定位"与"需多步推导且路径不通"的风险差别。

## 七、材料侧：扩数据，不降标准

**owner 裁定**：继续扩展，交给对应的工程师扩展。

- **维持药物 15 : 材料 15**，`query_spec.json` 的 open 段配比不改；
- 实测材料侧当前仅 9 个天然可用族（R²≥0.90 的 6 个里 ≥4 档的为 0）——**归 E1 扩展材料数据源**；
- 按 per-case 配对的口径，材料侧同样可组织视图，但**族成员的绝对数量仍需数据支撑**，这是扩数据的必要性所在。

## 八、同分异构的判法（实测撞到，本 ADR 补定）

实测药物侧 124 个天然族中 **91 个含"同组成不同分子"**，例如：

```
19 号 ×23  →  logS = −2.000  (z002914)
19 号 ×23  →  logS = −1.910  (z017792)
```

由于 agent 提交的是**组成**，必须定判法：

| 情形 | 判法 |
|---|---|
| 同组成对应多个 B 侧分子，**全部满足**题面目标窗口 | 全部纳入 `G_B`，命中任一即算命中（承 owner "gt 也可能是多个"） |
| 同组成对应多个分子，**部分满足、部分不满足** | **该 case 废弃** —— 组成无法区分它们，判分会变成运气 |
| 同组成分子仅在 A 侧出现 | 按 §4.1 返"不存在"，不影响判分 |

## 九、交付标准（供 E5/E1/E3/E6 落地）

| # | 项 | 通过标准 | 归属 |
|---|---|---|---|
| 1 | per-case 可见集视图机制 | 每个 open case 带一份可见集白名单；A 的查询被限制其中；**且不得带出 B** | E1 |
| 2 | 每个 case 的梯度参数落盘 | `n`（族内样本数）、`d`（外推距离）、`K`（干扰项数）三值显式记录 | E5 |
| 3 | 干扰项强制 | **K ≥ 10**，默认 20～30 | E5 |
| 4 | 质量门两条 | 第一条：A 内无不劣于 gt 的解（穷举可见集）；第二条：`edit_op(anchor)` 组成变换后 == gt 且 `evidence_set` 均可由 A 侧接口查得 | E5 造题时自检 + E3 提供判据 |
| 5 | 存在性接口三分支 + 文案一致 | A 内/库外返回体**逐字节相同**；只返 bool | E3 |
| 6 | 同分异构判法 | 按 §8 三种情形处置，部分满足即废弃 | E5 |
| 7 | 材料侧数据扩展 | 可用族数支撑 15 道；扩展来源须标真实 URL 与权威性 | E1 |
| 8 | 裸答基线 k=10 | 每个 open case 实跑，任一次命中 `G_B` 即判污染废弃 | E6 |

## 十、不做的事（边界）

- **不做**多跳（>2）推理 —— goal §2b④ 已禁，算子空间会爆炸；
- **不做**结构层面的 `edit_op` —— 按 §5 改组成算子；
- **不改**固定映射 —— 按 §6；
- **不降**材料侧标准 —— 按 §7 扩数据；
- **不把**"接口返存在"当评分依据 —— 按 §4.3。

## 修订 R1（2026-08-07）：补三处判定口径缺口

**触发**：E6 在实跑裸答基线时报出三处「跨线口径缺口」，其中**两处是本 ADR 与 E6-03 任务书的实质漏洞**（监工写规范时未定到底）。三条裁定如下。

### R1-① G_B 的 per-case 注册归 E5

**缺口**：15 道 dh open 的 `g_b` 只写在 case JSON 里，未注册进 `b_partition.json` 的 `cases`，导致 `hit_gb` 回落到**顶层** `g_b`——不是本 case 的 G_B，命中与未命中都不可信。

**裁定：归 E5，与造题同批完成。**

理由：本 ADR §9 项 4 已把「`G_B` 落盘」派给 E5，注册进 `b_partition` 是同一件事的收尾，不该拆到别人身上。**监工原文只写"落盘"未写"注册"，是表述不到位。**

要求：`b_partition.json` 的 `cases[<case_id>].g_b` 为该 case 的唯一 G_B 来源；顶层 `g_b` 仅作 fixture，判分不得回落到它——**回落即应报错，不得静默降级**。

### R1-② 组成 ↔ 实体 ID 的映射归 E3 判分侧

**缺口**（本 ADR 的漏洞）：§5 定了 agent 提交**组成串**（dummy-atom 分子式），§4.3 定了评分依据是 `∈ G_B`，但**没定 G_B 成员用什么表示**。实际 G_B 存的是**实体 ID**，判分器没有组成↔ID 映射，于是"命中 G_B"字面不可执行。

**裁定：映射层归 E3，放判分侧，不放 gateway 侧。**

理由：gateway 是给 agent 用的工具面，**它不该持有 G_B**（持有即有泄漏风险）；判分侧本来就持有 G_B 与真实身份，且按 §5.3 已具备组成多重集比对能力，加映射层天然合适。

**映射必须是一对多**：按 §8，同一组成可对应多个实体（同分异构）。故判定式为

$$\text{hit\_gb} = \mathbb{1}\big[\ \text{resolve}(c_{\text{submit}}) \cap G_B \neq \varnothing\ \big]$$

其中：
- $c_{\text{submit}}$：agent 提交的 dummy-atom 组成串；
- $\text{resolve}(\cdot)$：把组成串规范化后解析为**实体 ID 集合**（一对多，同分异构全收）；
- $G_B$：该 case 经 R1-① 注册的合格集（实体 ID 集合）；
- 交集非空即命中，与 §8「同组成多分子全满足则全纳入 G_B、部分满足即废弃」一致。

### R1-③ fixed 候选池的分母取「完整过滤邻域」

**缺口**（E6-03 任务书的漏洞）：任务书照抄 goal §2b 写"以同 case 候选池内随机抽样命中率为基线，超 2× 即废弃"，但**没定"候选池"是什么**。E6 实测三种口径后果迥异：

| 口径 | 实测后果 | 可否用 |
|---|---|---|
| 格内成员集 | type1 多为单成员格 ⇒ $p_{\text{base}}=1$ ⇒ 判据恒不触发 | ❌ 等于没这道门 |
| 全 A 库 | $p_{\text{base}} \approx 1.3\times10^{-5}$ ⇒ 2× 后仍≈0 ⇒ 任何一次命中都判污染 | ❌ 退化成 open 的绝对判据，抹掉 goal 给 fixed 单设口径的用意 |
| **完整过滤邻域** | $p_{\text{base}} = 1/\lvert\text{合格集}\rvert$ | ✅ **采纳** |

**裁定：取完整过滤邻域**——即"满足题面全部硬约束的候选集合"，这才是 goal 所指"同 case 候选池"的本意。

$$p_{\text{base}} = \frac{1}{\lvert S_{\text{feasible}}\rvert}, \qquad \text{废弃条件：} \ \text{pass@10} > 2 p_{\text{base}}$$

其中：
- $S_{\text{feasible}}$：该 case 下满足题面全部硬约束的候选集合（类型1 为合格者集合，类型2 为筛选后待排序的集合）；
- $\lvert\cdot\rvert$：集合势；
- $\text{pass@10}$：无工具裸答 10 次中命中 gt 的比例；
- 阈值 2× 沿用 goal §2b，不改。

**配套要求**：E5 按当前库快照复算每个 fixed case 的 $\lvert S_{\text{feasible}}\rvert$ 并落盘为 case 字段；`co` 系列（类型2）若无成员名单需补齐，或明确该 case 只能做 best-ID 单点判并在 report 说明。

### R1 的监工留痕

②③两条的根因相同：**规范写了判定公式，却没定公式里的对象用什么表示、集合的边界在哪**。与 ADR-0008 的 `no_path_violation` 悬空符号是同型错误——本 ADR §2b 引用处已警示过该教训，我自己又犯了一次。

E6 未自行选一个口径蒙头跑，而是列出三种后果并报监工裁定，**做法正确**。
