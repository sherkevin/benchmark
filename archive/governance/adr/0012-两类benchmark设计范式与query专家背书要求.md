## 背景

负责人口述四条设计决议，直接影响 benchmark 的 case 构造方式与 query 撰写规范。此前 fixed_discovery 与 open_discovery 两类模板已落地（ADR-0009），但"发现探索类"的设计细节（数据库 A/B 分离、存在性查询接口、线索性联系）此前未明确。同时 query 的专业术语与风格需要专家背书，防止模糊化操作不合理。

## 决策

### 1. 两类 benchmark 设计范式

**第一类：搜索推理类（fixed_discovery）**——对应固定数据库，GT 本身在数据库里，query 的目的就是查到它。这是当前已实现的范式：agent 检索文献→建候选池→查性质→筛选→排序→提交。GT 是数据库中的已知分子，query 隐去真名与数值，agent 通过工具调用找到它。

**第二类：发现探索类（discovery_haystack）**——数据库分为 A（agent 可查）和 B（agent 不可查）。给一个设计目标（如"针对 xxx 的分子，xxx 尽可能好，xxx 尽可能低"），agent 根据 A 中的信息推理出一个 A 中不存在的分子。agent 不知道该分子是否存在，只能给出推断。评分时去 B 里查询这个推断，看 agent 是否猜对。

发现类的关键设计约束：
- **线索性联系**：被推理出的分子必须与 A 中的分子有线索性联系（如"加上一个原子 a 就会增加 xxx 性质"），保证推理有据可依，不是瞎猜；
- **存在性查询接口**：agent 推出分子 m 后，必须查询一个接口判 m 存不存在——在 B 里就是存在（任务结束），不在就重新推断直到存在。agent 只能知道"存不存在"，不知道 m 的性质是什么；
- **B 不可见**：agent 在推理过程中完全看不到 B 的内容，只能通过存在性接口验证。

### 2. query 的专家背书要求

query 的模糊化操作（隐去真名与数值）必须合理——不能随意模糊到 agent 无法理解题意。为此：
- **query 必须基于专业咨询报告或专业论文**：每道题的 query 要能说"这是根据 xxx 论文/报告得到的"；
- **术语与风格要与领域专家一致**：需要调研其他 benchmark 的 query 写法（风格和术语），以及领域专家的 query 记录，确保我们的 query 不是自造的；
- **需要一轮全面的调研**：既看 benchmark 论文的 query 怎么写，也看专家们的实际 query 记录，作为权威参考。

### 3. 分子 mock 的等价变换原则

为保证 agent 不被自身已有知识干扰而纯粹测试推理能力：
- **所有分子做等价的唯一变换**（如 h2o → a2b），对每个元素做一致的替换；
- **性质与真实世界一致**：变换后的分子性质（ADMET/晶体性质）与真实分子完全一致，保证世界逻辑和推理知识自洽；
- **mock 不是随机化，而是等价映射**：每个真实分子对应唯一匿名 ID，性质不变，防止 LLM 记忆泄漏。

### 4. 实施路径

1. 搜索推理类（fixed_discovery）：继续扩充 case（当前 29 个），按既定 GT-first 四步法构造；
2. 发现探索类（discovery_haystack）：设计数据库 A/B 分离方案 + 存在性查询接口 + 线索性联系规则，落地第一个 case；
3. query 专家背书：调研其他 benchmark 的 query 写法 + 领域专家的 query 记录，形成 query 撰写规范；
4. 分子 mock：已有 mock_db 的匿名化机制（aa/xa/da/ea）已满足等价变换原则，继续扩充时保持一致。

## 影响

- fixed_discovery 继续按现有范式扩充，不受本决议影响；
- open_discovery 的材料 case 可视为"发现探索类"的简化版（无 A/B 分离，但有高压陷阱），后续按 A/B 分离方案升级；
- discovery_haystack 的实现需要新增：B 数据库、存在性查询工具（`check_molecule_exists`）、线索性联系规则引擎；
- query 撰写规范将影响所有后续 case 的 query 质量。
