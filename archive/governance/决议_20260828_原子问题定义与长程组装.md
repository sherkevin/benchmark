## §1 owner 的三条定义（原文，不是我的转述）

### 1.1 什么是原子问题

> "所谓原子问题，是**能够衡量的最小标准**。它并不是说只测了一个动作或者一个能力，而是指
> **从开始到结束这一段，只有一个产出，即一个可衡量、能被验证器验证的值**。"

### 1.2 长程任务怎么由原子问题组成

> "我们本身要做长程任务的话，是要把**若干个验证值拼在一块儿**，也就是**一个 trace 上有多个
> 验证点，一个验证点到下一个验证点之间的过程，就叫原子问题**。"

### 1.3 原子问题为什么不判中间结果

> "**一个原子问题，如果要判中间结果，那么它就不是原子问题。**"

⇒ 这句是**定义的推论，不是一条规矩**。一个原子问题按定义只有一个产出，里面本来就没有
"中间结果"这种东西可判。**它不构成"整个阶段不许有检查点"的禁令。**

### 1.4 检查点为什么必须有

> "'不带检查点就丧失项目存在理由'，这是对的。因为我们最终要做检查嘛，最终要得分，
> 没有得分，怎么判断好坏？"

## §2 由 §1 三条定义直接推出的结论

| # | 结论 | 推自 |
|---|---|---|
| ① | **一条 trace 上有 N 个验证点是合法的，也是必须的**（N 个原子问题串成一个长程任务） | 1.2 + 1.4 |
| ② | **"原子问题不判中间结果"是同义反复，不是禁令**；把它读成"当前阶段不许有 checkpoint"是过度概括 | 1.1 + 1.3 |
| ③ | **防作弊（背诵/穷举/运气）的闸应当作用在整条链上，不是每个原子上**。原子是短的一段、产出空间小，裸答撞上是正常的；只要整条链上的 N 个验证点合起来撞不上就行 | 1.1 + 1.2 |
| ④ | **每站的验证值必须是"可被验证器验证的值"**，不是"有没有做过某个动作"。"做了≥1 次检索即满分"这种关不合定义 | 1.1 |

**③ 是本轮最要紧的一条。** 之前的机械要求是"每一道原子题单独都要打赢裸答、撒网、常数答案"，
这与 1.1 的定义冲突：原子越小、产出空间越小，就越容易被背/被穷举/被蒙对。全库 13 道题
四种死法（`layer_01` 可背、`triage_01` 靠运气、`aedit_01` 头部裸答饱和、`sarflip` 的
`cp_rule` 是彩票），机械原因就是闸装在了原子这一层。

## §4 我这一轮犯的三个错（登记，起因就是防复发）

三个错有同一个形状：**拿"我以为的定义"或"我以为的实现"当前提，据此宣布某件事"不可能 /
越界"，从而把活着的资产判死。** 据此立第 ⑪ 类坑。

### 4.1 错一：把"agent 的记忆"和"世界的状态"混成一件事

我写过："我们的模拟世界没有记忆，所以长程在构造上不可能出现"、"路径依赖我们从来没造出来过"。

**owner 纠正**："作为现在的智能体，它其实是有自己的记忆的，可以做上下文管理。我们本质上
不是在调 API 来测，而是在用 Claude Code 来测，Claude Code 本身就是一个 Agent。"

**错在哪**：我看的是后端工具都是查表（`ws_mcp_server.py:43` 唯一可变状态是预算计数器），
就推出"路径依赖不存在"。但 harness 是 Claude Code，agent 自己有上下文；再加上**预算是不可逆
消耗的**，"先测哪个"确实决定了后面能推出什么。**路径依赖是存在的。**

### 4.2 错二：连"残留缺口"也说错了（未核实现就断言）

被纠正后我退了一步，说"残留是没有工具能造新实体"。**这一步也是错的，而且我这次是核过才发现的**：

| 事实 | 出处 |
|---|---|
| `edit_molecule` 在第一代 mock server **在线**，agent 可直接调 | `dag_poc/mcp_mock_server/mock_server.py:241-245` |
| 它走 RDKit 真造新分子（`RWMol` 增删原子/改原子序数） | `dag_poc/gateway.py:1743 _tool_edit_molecule`；`tools/a_edit_ops.py:29-50` |
| 答卷 grounding 条件③ **要求 trace 里存在 `edit_molecule applied=True` 且三元组相符** | `dag_poc/answer_schema.json:100` |

⇒ **造新实体 + 查 trace 验过程，第一代早就都实现了。**
真正的缺口只有枚举表自己登记过的那一条：**新造出来的分子查不到性质**
（`research/agent_action_全量枚举.md:117`"结构改动后查不到性质"）。就这一件。

### 4.3 错三：拿自己的定义去推翻 owner 的方法

我写过："我们定的规矩，跟'原子'这个词数学上互斥"，据此说造题范式有结构性问题。

**owner 纠正**：见 §1.1 —— 原子 = 能衡量的最小标准 = 一段只有一个可验证产出，**不是**"只测一个动作"。
按这个定义，我那句"互斥"不成立。真正互斥的是**闸装的位置**（§2 结论③），那是规矩的问题，
不是范式的问题。

**错在哪**：我没回去核 owner 对这个词的定义，直接按自己的理解用，然后把结论升级到
"范式有问题"这一层 —— 这同时也是坑②（过度升级）。

### 4.4 新增第 ⑪ 类坑：臆想一个"不可能"

| | 坑① | 坑⑪ |
|---|---|---|
| 形状 | 臆想一个"**必须** X" | 臆想一个"**做不到** X / 碰 X 就越界" |
| 后果 | 往一个没据的方向使劲 | **把活着的资产判死、把能走的路堵掉** |

**实例**（都在 2026-08-28 同一天）：① 未核 harness 与 `edit_molecule` 就断言"世界没记忆 ⇒
长程不可能"；② 未核 owner 定义就断言"原子与防作弊数学上互斥"；③ 把坑③ 当成 owner 的裁定
**引用了 4 次**当挡路依据，而它其实是一句正确的话被连升两级的产物（§3）。

**守则（三条，缺一条不许下"不可能"的结论）**：

1. **任何"不可能 / 做不到 / 现在碰就是越界"的断言，必须先核两样**：
   ① 涉及实现 ⇒ **去代码里核那个能力在不在线**（不是核你以为承载它的那个文件）；
   ② 涉及规矩 ⇒ **去 `DECISIONS.md` 查这条当初是谁定的、原文作用域多大**（§8 硬纪律已有此条，
   本坑把它从"改实现前"扩到"下否定结论前"）。
2. **术语按 owner 的定义用**。核不到定义就当面问，不许按自己的理解推导，更不许据此升级到
   "范式 / 方向有问题"这一层（叠加坑②）。
3. **"不可能"的结论要附一条可反驳的检查**：写清"如果 X 存在，我应该能在哪里看到它"，
   并说明我去看了、没看到。看都没看就写的"不可能"，一律撤回。
