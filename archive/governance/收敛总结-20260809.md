## 二、还差什么

### 2.1 头等大事：刚跑的 26 次数据不可用，有两个 bug

**这是本轮最重要的发现。** 矩阵已经在跑（目录结构、token 留痕都合规），但跑出来的东西有问题：

#### bug 一：H2 传给工具的参数被套了三层壳（99% 的调用都中）

正常应该是这样：

```
{"query": "aqueous solubility criteria"}
```

实际是这样：

```
{"arguments": "{\"arguments\": \"{\\\"query\\\": \\\"aqueous solubility...
```

**参数被反复打包成字符串，工具拆不出真正要查什么。**

| 项 | H1 | H2 |
|---|---|---|
| 工具调用次数 | 955 | 247 |
| **参数被套壳** | **0 次** | **244 次（99%）** |
| 成功率 | 48.7% | **33.6%** |
| `INVALID_ARGUMENT` 报错 | 0 | **54 次（全在 H2）** |

**结论：这是 H2 那条链路（CLI → adapter → 工具）的打包 bug，H1 没有。**

#### bug 二：agent 老是查库里不存在的性质名（H1/H2 都有）

`UNKNOWN_PROPERTY` 报错 **418 次**，是所有错误里最多的（H1 342 次 + H2 76 次）。H1 的参数格式是好的，所以这不是打包问题，而是 **agent 猜了一个库里没有的性质名去查**。

库里实际有的性质名（前 8 个）：

```
tc(13870)  family(13870)  structure_in_db(13870)  condition(13869)
logS(2299)  bbb(757)  logD(604)  half_life(523)
```

**要查清 agent 到底在查什么名字**——如果是工具说明书里没列清"有哪些性质可查"，那就是我们的问题，不是模型的问题。

#### 连带后果：答卷里 86% 是旧 ID

agent 提交的候选里，**302 个是旧 mock 的 `aa`/`ab`/`ac`，只有 51 个是新库的 `z000374` 格式**。旧 ID 跟新库的答案对不上，**判分会全错**。

这条要查是不是 `search_candidates` 还在返回旧 mock 的数据（`get_entity` 已经切到新库了，但检索这条路可能没切）。

## 四、这轮纠正的偏差

### 4.1 一个规律：越简单的一步越容易没人做

三次同型漂移，都是我的排期失误：

| 时间 | 漏了什么 | 为什么漏 |
|---|---|---|
| 08-07 | fixed 的 90 道题 | "只是多造题"，没技术难度 |
| 08-08 上午 | H2 真实框架 | 挂着"二期目标"的标签 |
| 08-08 下午 | **"跑矩阵"本身** | 准备工作做得越细，越容易把"执行"当成自然会发生的事 |

**已定的规矩**：派活前不光看"各类完成度"，还要看**要交的那个东西是不是真的产出来了**——框架、脚本、设计文档都不算。

### 4.2 一次流程断链

E1 的文档里写「监工已裁定方案 B」，而我检索完整对话记录，**「方案 B」出现 0 次**。它备战完整套手术（要删 486 行数据）在等我通知，而我不知道要通知。

**已定的规矩**：「监工裁定」只以对话里的明确答复为准；删改已入库数据这类动作，必须显式裁定后才能执行。

### 4.3 我自己的探针反复出错

本轮就错了四次：字段取 `final_text`（实际在 `response`）、gt 取 `id`（实际是 `entity_ref`）、grep 限在 `src/`（引用者在 `task/`）、搜占位漏了 `†`。

**每次都是"差点误判工程师"**。已登记 PR-36 并总结成五条约束，本轮再加一条：**报"某项为 0/为空"之前，先确认自己取的字段名和范围是对的。**
