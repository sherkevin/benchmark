### ✅ 第 1 项 · 旧 mock 条目霸占查询结果 —— 方案定：删数据 + 提默认返回量

**根因（三次更正后的最终结论）**：

不是"工具连着旧库"（我第一次的判断，错），也不是"旧数据占 86%"（第二次，错）。真实原因：

| 事实 | 数据 |
|---|---|
| 工具已切到新库 | A 全集 **92,193** 个实体 |
| 旧 mock 条目 | **只有 40 个（0.04%）** |
| 但检索是按 ID 字符串排序 | `'aa' < 'ab' < … < 'c00001' < … < 'z000001'` |
| 默认只返回前 10 个 | ⇒ agent 每次只看到 `aa`~`aj` 这 10 个旧条目 |

**方案（分两步）**：

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | **删掉 backend 库里那 40 个旧 mock 条目** | 删前先查依赖：`mock_tools.py`、`test_ab_isolation.py`、`ingest_gate.py` 等在引用，要同步改 |
| 2 | **默认返回量 `k` 从 10 提高** | 具体值见下 |

**`k` 的定值**：与 PR-17 的查询预算一并考虑（见第五组）。

**归属**：E3
**验收**：抽一道题实跑，`search_candidates` 返回 ID 全为 `z`/`c` 新库格式；该题的合格候选在返回集内。

### ✅ 第 2、3 项 · 合并 · agent 不会用工具 —— 方案定：补全说明书 + 错误信息带提示

**两项同源，合并处置。** 实测三个坑，agent 一个都不知道：

| 坑 | 实证 |
|---|---|
| 同义词 | agent 写 `molecular_weight`（库里叫 `mw`）、`solubility`（库里叫 `logS`） |
| 有些性质只能过滤不能查值 | `mw`/`logp`/`tpsa` 写进筛选条件可以，用 `get_property` 查值被拒（F2 裁定），**说明书一个字没提** |
| 参数结构 | `constraints` 要 `[{property, op, threshold}]`，agent 传了字符串数组；字段叫 `props` 不叫 `properties` |

后果：`UNKNOWN_PROPERTY` **418 次**（H1 342 + H2 76）+ `INVALID_ARGUMENT` **54 次**，工具调用成功率仅 **48.7%**。

**方案（两件一起做）**：

| # | 动作 |
|---|---|
| 1 | **9 个工具的 schema description 里写清三样**：①可查性质完整清单（含哪三个只能过滤不能查值）②参数的确切结构 ③每个工具一个可直接照抄的调用示例 |
| 2 | **错误信息带可用清单**：被拒时返回"性质 X 不存在，可用的有：…" |

**明确不做**：不做同义词模糊匹配（`molecular_weight` → `mw` 自动纠正）。理由：会让 trace 变脏，判分时分不清 agent 的真实意图。

**owner 已拍定的一条原则**：**"猜字段名"不属于 benchmark 该考的能力**。现在 49% 的失败调用是试错参数，把 agent 的真实推理能力盖住了。

**关于"H2 三层套壳"**：经查是**我看 trace 时的误判**。CLI 实际发的是 2 层（`{"arguments": "{真参数}"}`，符合 MCP schema），trace 里多的第 3 层是 adapter 记日志时加的，**不影响实际调用**。归 E4 顺手清理日志冗余，不是 bug。

**归属**：E3（工具定义）；E4（清 adapter 日志冗余）
**验收**：重跑后 `UNKNOWN_PROPERTY` 与 `INVALID_ARGUMENT` 显著下降，工具成功率明显高于 48.7%。
