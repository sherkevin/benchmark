# 根因盘查：29 天、548 提交、1178 个 run，为什么一道能用的题都没出来

> owner 2026-08-27 问：*"我们一直在原地打转，一道有用的问题都没构建出来，这到底是因为什么？
> 我希望你仔细盘查一下我们的过往经验和教训，总结一下当前的痛点。"*
>
> 本文只做诊断，**不新增任何规矩**（再加规矩正是痛点四）。所有数字来自 `git log` 与仓库实测，
> 命令写在每条后面，可复算。

---

## §1 一句话结论

**我们一直是"先造题、再定标准"，而每一版标准都是从上一批题的失败里长出来的
⇒ 任何一批题在出生时就注定不合下一版标准。**
叠加第二层：题目形态一直是"答案 = 一个数值/一个分子，用打分公式判"，
这种形态**在算术上不可能**满足"判别关离散零超参"（闸4）⇒ 换多少道题都死在同一处。

所以不是数据不够，也不是模型不行，是**标准与形态这两件事没有先固定下来**。

### 痛点二：作废的 run 全是"跑完才发现的设计缺陷"，不是运气

归档 run **1,178** 个，其中住在 `*_deprecated` 目录里的 **537 个 = 45.6%**。
目录名本身就是一张缺陷清单：

| 作废目录 | run 数 | 缺陷是什么 | 跑前能不能查出来 |
|---|---|---|---|
| `runs_hinted_deprecated` | **300** | 题面把答案线索给了出去 | **能**——读一遍题面 |
| `runs_pureExtrap_deprecated` | 90 | 题型退化成纯外推 | **能**——闸0 第③问 |
| `runs_budget17_deprecated` | 90 | 改预算旋钮重跑 | **能**——坑⑨ |
| `runs_freeDiscovery_deprecated` | 37 | open 侧发现口径不成立 | **能**——判据④ |
| `runs_v1/v2*_deprecated` | 12 | 题面迭代 | 能 |
| `runs_probe_freetext_deprecated` | 6 | 从自由文本里抽答案 | **能**——§6.0 规则二 |
| `runs_badToolName_deprecated` | 2 | 工具名写错 | **能**——一次冒烟 |

⇒ **七类作废，七类都能在零 API 代价下查出来。** `preflight.py` 到 08-22 才出现，
那时已经烧掉一千多个 run。

### 痛点三：单题深挖，没有批量，也没有快速判死

| 事实 | 数字 |
|---|---|
| `qed_01` 一道题吃掉 **857 个 run**（占全部归档 run 的 **73%**），22 次提交，6 个目录副本，6 个作废批次 | 一道题重设计 ≥6 次 |
| `layer_01` 花 **123 run** 之后才发现裸答基线 0.952 | 裸答基线是零机时可测的 |
| `triage_01` 花 **126 run** 之后才发现方差由抽样主导 | 组内 SD > 组间 SD，同样零机时可算 |
| 14 个唯一 case_id，只有 **1 个**封存；25 个判分器里只有 **9 个**有 `baselines()` | `grep -rln "def baselines" cases` |

⇒ owner 要的是**批量构建题面**，我们做的是**一次一道往死里挖**。
一道题挖到底的代价 ≈ 造 20 道题再筛掉 19 道。

### 痛点四：力气花在写规矩，不在造题

| 类别 | 提交数 |
|---|---|
| 治理 / 规范 / TODO / 方法论文档 | **225** |
| 题面 + 判分器（cases 下 py + runner） | **51** |

比例 **4.4 : 1**。现存规矩正文 **1,832 行**（`BENCH_SPEC` 425 + `实验规范` 701 +
`DECISIONS` 239 + 路线图 260 + `ACTION_RULES` 207），`BENCH_SPEC` 里"闸"字出现 **45 次**。

附带证据：目录骨架先按 3 域 × atom/chain × 6 档 = 36 格全建好，
里面只有 14 道真题；而且 `cases/material/` 与 `cases/materials/` **两个目录同时存在**
（一个错别字级的重复活到今天）⇒ 结构先行、内容后填，结构本身还带噪声。

### 痛点五：判别关一直挂在旋钮上 —— 这是题目形态问题，不是调参手艺问题

- 全库唯一与独立能力排序显著对齐的检查点是 `cp_layer`（rho=+0.812），**它也是唯一零超参的**；
  **同一天被裸答基线 0.952 推翻**（它对齐的是背书能力）。
- 其余全部挂超参：`cp_tc`(tol 7.775→scale 3.888)、`qed_01` 权重 0.5/0.3/0.2、
  `triage_01`(预算 8 / 池 20 / 合格 6)。
- 更早的账：全项目 7,315 run ≈ 610 机时，**作废原因 55% 是调参**（`sweep_ws.py:17-18`）。

⇒ **只要答案是"一个值/一个分子 + 打分公式"，就必然要引入 tol/scale/权重来平滑，
必然踩闸4。** 出路是 08-23 已经裁定过的形态：**目标级产物 + 逐条离散核对**
（交出一个分子集，逐约束核实测值，对就是对）。**但至今没有一道题是照这个形态造的**
——`aedit_01` 交的还是"方向预判"，本质仍是实验级。

## §5 讨论记录（2026-08-27 owner 复盘，两版方案均被否）

盘查完痛点后我提了两版下一步方案，**两版都被 owner 否掉**。记在这里，因为被否的理由
比方案本身有价值。

### 5.1 第一版方案 & 它的两个错

方案：① 把 7 类历史死因写成 preflight 断言 + 冻结标准；② 拿 **T1 抹除分子题**当标杆；
③ 参数化成生成器批量出题；④ 往前接站组装长链。

| 错 | 说明 | 谁发现 |
|---|---|---|
| **错一：又在写规矩** | "把 7 类死因写成 7 条断言"＝拿旧错误的形状去挡新错误，而且写断言就是写规矩，**正撞痛点四** | 自查 |
| **错二（硬错）：标杆题选错——T1 抹除形态在药物侧结构上就是背诵题** | 答案分子从视图抹除，而 `ViewedBackendReader` 按设计让工具**到不了视图外**（白名单外一律 `UNKNOWN_ENTITY`）⇒ 模型要"点名"一个视图外的真实分子，**唯一来源是它自己的记忆**，工具帮不上忙 ⇒ **裸答基线与带工具基线天然相等**，与 `layer_01` 死于裸答 0.952 同病 | 自查（零机时判死，不必跑） |

**错二的附带价值**：判死它靠的不是断言，是**把判分逻辑想到底**。这是下面 5.2 的由来。

### 5.2 方法层共识（这部分 owner 认可，保留）

**一、顺序倒过来：先写判分器，再写题面。**
现行顺序是「题面 → 跑 → 判分 → 发现题不成立」，改成
「**判分器 → 假选手离线打一遍 → 打不出梯度就换题 → 才写题面 → 才跑 agent**」。

"假选手"＝几个纯 Python 笨策略，不调模型、零 API：

| 假选手 | 怎么答 | 好题应给它多少 |
|---|---|---|
| 背书哥 | 凭记忆硬报 | ≈ 0 |
| 撒网哥 | 全部候选都提交 | ≈ 0 |
| 死磕哥 | 预算内能测的全测、只交测到的 | 中等偏低 |
| 真外推 | 测几个 → 归纳规律 → 外推没测的 | 明显最高 |

四个分数不严格递增 ⇒ 这题不成立，**在写题面之前就知道**。
不需要新规矩：`preflight` 里已有「闸门5 策略收益差自检」雏形，把它挪到造题第一步即可。

**二、批量＝一张参数表 × 一个离线筛子。** 经验不落文档，落在筛子里：参数表列出候选题
（性质 / 系列 / 窗口 / 预算），筛子把每行喂给四个假选手，只有梯度干净的行才生成题面 +
判分器 + 真值、才允许开 ≤9 run。**造 20 道题的成本 ≈ 跑一次筛子**，死掉 19 道不心疼。

**三、判分器可以自己把捷径掐死，不用靠调参。** 第二版举的例子（形态思路保留，选题作废）：
判别关＝提交集合 **① 无假阳性**（逐条核实测值）**且 ② 至少 N 个成员从未被测量过**
（工具账本核验）⇒ 背诵/撒网必出假阳性挂 ①；穷举全靠测挂 ②；一次调用两条都挂。
**"必须外推"这件事写进了判分器本身**，而不是靠 tol / 权重 / 预算制造区分度。

### 5.3 第二版方案被否的理由（owner 原话，最重要的一条）

> "**你还是在根据本身数据库里已有的数据来造问题，这本身就是一个不好的习惯。我们的出发点
> 应该是先确定一个长程任务，然后把这个长任务拆分成若干个原子任务，针对这些原子任务造题，
> 并且我们是可以来扩充我们的数据库的，不要被数据库所限制。如果说我们需要的数据数据库里
> 没有，我们可以新增。如果每道题面它不需要某个数据，我们可以写一个隔离层，去把数据库里
> 这部分数据给隔离掉，从而为它造一个专属于这个题面的数据库。**"

第二版的病灶：我把标杆题选成"logS 有 2,272 个分子 / 132 个同系列对，所以拿 logS 造归纳题"
—— **出发点是"库里哪个性质数据最多"，不是"长程链这一站需要什么"**。这就是坑④ 倒着造题，
只不过换了个更体面的说法。

**这条决议早就存在，我是连续第三次违反：**

| 次 | 当天动作 | 违反的决议 |
|---|---|---|
| 1 | 用"库里唯一可查的画像"去判 T1 闸2 死刑 | §2.5 题库按题面构造、数据不够就补 |
| 2 | 把"没有蛋白质数据"当成方向层待裁问题上报 | 同上（owner：数据缺口不是卡点） |
| 3 | 按"logS 数据最多"选标杆题 | §2.6 top-down 铁律（08-26 已立） |

⇒ 缺的不是规则，是**动手前那一句自问**：这道题的数据需求，是从长程链推下来的，
还是从库里现成有什么挑出来的？（已补进 `DECISIONS.md` 坑④ 守则）

## §6 留给下一轮讨论的开放问题（owner 指定下一步谈"出发点的逻辑"）

1. **长程任务定成什么**：现有八站链（`长程任务_路线图.md` §2）是"先导化合物优化"，
   但 owner 08-27 重申的例子是"发现一个治疗癌症的药物"，含**靶点 / 活性 / 蛋白质**——
   库里这三类数据实测为 **0**（仅 molecule 74,901 + crystal 17,252，12 个性质字段无一是活性）。
   **按新出发点，这不是砍腿的理由，而是"要新增哪些数据"的清单。** 先定链，再列数据缺口。
2. **拆成哪些原子**：每站的入口/出口（交接件）要定死，否则串不起来。
3. **每站需要什么数据 → 缺什么 → 怎么补**：新增（造数据/接外部源）还是隔离（从总库摘出
   专属题库）逐站定。已有机制：`per_case_view.py`（`ViewedBackendReader` 白名单）＋
   `predict_admet` mock 注入。
4. **补数据的工程边界**：动 `dag_poc/data/backend/` 需重生成 `CHECKSUMS.json` 并留 changelog；
   25 个封存文件不含 backend 数据，故补库不触发 `preflight` 闸门5。
