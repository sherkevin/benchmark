# 行动规范（ACTION_RULES）

> 适用于本仓库中所有 agent 与人工操作。每次行动前必须先阅读本文件。
> 文档冲突时的**权威顺序唯一正文在 [`governance/DECISIONS.md`](governance/DECISIONS.md) 开头**，本文不重述。
> **做 benchmark（造题 / 跑批 / 判分 / 下结论）必须先读 [`BENCH_SPEC.md`](BENCH_SPEC.md)**——本文件只管通用行动规范。

## 1. 行动循环（每次行动必须走完）

1. **对齐目标**：读根目录 `goal.md`（v3.0.1），确认本次行动服务于最终目标且不违反约束条件。
2. **查决议**：读 [`governance/DECISIONS.md`](governance/DECISIONS.md)。**动任何判分口径、工具面、题面、真值之前，必须先查清"这一条当初是谁定的、为什么"**——查不到出处就说明决议没落盘，**先补台账，不得先改实现**（理由见 §8）。**并对照十一类坑自查表**（精简版 [`BENCH_SPEC.md`](BENCH_SPEC.md) §11、完整留痕 `DECISIONS.md` §6）：造题 / 改判分 / 下任何负面结论前，确认自己没在"没有据的地方擅自加一层判断"（臆想前提 / 过度升级 / 塞进未来阶段 / 倒推 / 跳过已有结论 / 跳过核对原始样本 / 小样本断言必然 / 只降方差不验信号 / 调旋钮凑结果 / 拿代理当判据 / **臆想一个"不可能"**）。
3. **锚定任务**：确认当前 task（`task/{task_name}/task.md`）。无 task 不动手：先写 task，再拆 todo。
4. **执行**：每完成一个动作，立即更新 `TODO.md` 账本对应行的状态与交付物链接。
   ⚠️ **这一条光写在这里挡不住**：实测账本自 T-243（08-24）起断了 **76 个提交 / 4 天**，
   期间 `T-244` 已被 4 处引用而那一行从来没写过 —— 引得到、查不着，正是 §8 要防的。
   故加机器兜底 **`tools/check_ledger_refs.py`**（零超参，判存在/不存在）：
   凡被引用的 `T-xx` / `U-xx` / `PR-xx` 必须能在台账里查到定义，悬空即 exit 1。
   **补台账，不要删引用**——编号背后那件事真发生过。
5. **收口**：task 完成时写 `task/{task_name}/report.md`，并将 todo 中对应各行标记 ✅；**本轮达成的决议同步追加进 `governance/DECISIONS.md`**（§8）；**跑一次 `tools/check_ledger_refs.py`**，本轮新写的编号引用不许悬空。
6. **可回退**：任何变更执行前，确保当前工作区已 commit（先 commit 再执行）。

## 3. Todo 账本规则

- 表格形式，一行一个 todo，每行含编号（T-xx）、状态、交付物相对路径链接。
- 账本为 log：可更新状态与补充信息，**禁止删除任何行**。
- 状态：⬜ 未开始 / ⚡️ 进行中 / ✅ 完成 / ⛔️ 被阻塞（阻塞项必须注明原因并回链 `problems.md` 的 PR-xx）。
- 交付物必须落盘为文档并给出链接；无落盘交付物的 todo 不得标记 ✅。

## 4. 写作与证据规范

- 论文正文按最终交稿状态撰写，禁止预测性措辞（"we expect" / "[TBD]" 等）。
- 不引用已作废的历史数值作为证据；图表必须由机器可读 metrics 自动生成。
- 调研结论必须回链 `reference/` 中的采样说明、真实 case 或论文阅读报告，不凭记忆断言。
- 论文的 venue/year 一律以 DBLP 或官方 proceedings 为准，禁止凭记忆断言某篇论文中了哪个会。
- benchmark 分析必须基于本地落盘的真实数据，不凭二手转述。

## 5. 汇报规范

- 所有汇报与 report 采用金字塔原则：先结论后论据，逐层递归。
- report 必须回答四件事：做了什么、结论是什么、证据在哪（路径链接）、遗留问题是什么。

## 7. LLM 实验的留痕规范（**跑任何 LLM 都必须遵守**）

> **owner 要求（2026-08-07）**：做 LLM 测试时必须把中间结果完整留下来（完整 JSON log）。后续算指标、查 case 都要用，**没留痕就只能重跑，代价极高**。

### 7.1 每次 LLM 调用必须落盘的字段

以 `src/benchmark/agent_harness.py` 现有的 trace 格式为基准（E4 已达标，其余线对齐）：

| 字段 | 内容 | 少了它就算不了 |
|---|---|---|
| `request.model` / `temperature` / `max_tokens` | 请求参数原样 | 无法复现、无法解释模型间差异 |
| `request.messages` | **完整 prompt 原文** | 查 case 时看不到题面究竟怎么问的 |
| `request.tools` / `tool_choice` | 给了哪些工具 | 无法区分"没工具可用"与"有工具不用" |
| `response.usage` | token 用量（prompt/completion/total） | 算不了成本与效率指标 |
| `response.choices[].finish_reason` | 停止原因 | **区分不了"答完了"与"被 max_tokens 截断"**——截断会让结论解释完全错 |
| `response.choices[].message` | **完整消息体，含 `reasoning_content`** | 见 §7.3 的实测坑 |
| `latency_ms` | 单次耗时 | 算不了耗时分布 |
| `attempt` | 第几次尝试（重试计数） | 异常无法解释；重试次数本身是指标 |
| `seq` / `timestamp` | 序号与时间戳 | `no_path_violation` 判据依赖真实时序 |
| `trace_id` / `case_id` / `model` | 索引三元组 | 无法按 case×model 聚合 |
| `code_version` | 跑这批时的 git hash | 结果无法追溯到代码版本 |

### 7.2 三条硬要求

1. **原始响应必须原样保留**，不得只存解析后的结果——解析逻辑会改，原始数据不会；
2. **失败与重试也要落盘**，不是只留成功的那次；
3. **落盘目录写在自己 task 目录下**，不要写进 `dag_poc/traces/`（PR-35：该目录会被外部进程 git 还原，交付物会丢）。

### 7.3 已实测的两个坑（照抄即可避免）

| 坑 | 实测 | 处置 |
|---|---|---|
| **kimi-k3 的正文不在 `content` 里** | `content` 为空字符串，实际内容在 `raw_message.reasoning_content` | 必须存完整 `message` 对象；E6 已用 `empty_content_final` 标记该情况 |
| **kimi-k3 不接受 temperature=0** | 返 HTTP 400 MPE-001 | 统一调 `agent_harness.temperature_for(model)`，不要各处各写判断 |

### 7.5 日志必须"可汇总"，不只是"留下来"（owner 2026-08-08 追加）

owner 原话：「标明使用的 token 数量，中间的 log json 等，以留可追溯的中间结果和日志，方便后续核查和根据其来改进方案」

留字段是底线，**能按维度求和才算达标**。凡批量跑测（≥50 次调用），须一并交付：

| 要求 | 说明 |
|---|---|
| 汇总表 | 总 token（prompt/completion/total 分列）+ 按模型 / 按 harness / 按 template 类型分组 + 单题分布（中位数、最大值、超长题清单）+ 缓存命中率 + 重试与失败分布 |
| 生成脚本 | 汇总数字必须由脚本从落盘日志算出、可重跑复现。**手记的数字不算** |
| 成本 | 按 token 与单价分模型折算；若某模型贵到影响排期，在 report 里直接指出 |
| 落盘结构 | 按 (模型, harness, case, 重复轮次) 可定位，不要全塞一个目录 |
| 层级说明 | `usage`/`finish_reason` 的实际嵌套层级写进 README 或 schema 注释——实测这两个字段常在 `call_log[].response` 而非顶层，不写清楚后来人（含判分脚本）会取错 |

**理由**：数字不可复算就无法据以改进方案；日志散落无法按维度求和，等于没留。

## 8. 决议落盘规范（owner 2026-08-21 立）

> **owner 原话**：「我们每次达成的决议需要及时的落决议文档，保证后续工程师参与进来的话
> 能快速了解现状，不必再出现重复出错的情况。」

**唯一台账**：[`governance/DECISIONS.md`](governance/DECISIONS.md)。它是索引——一句话 + 出处，
论据留在被索引的原文档。

### 8.1 四条规则

1. **决议一达成就落盘，在同一个工作单元内完成**，不许"下次再补"。
2. 落盘 = **台账追加一行** + 原文进权威落点。三者分工不混：

   | 内容 | 去哪 |
   |---|---|
   | 设计取舍、架构切分、范围声明、不变量 | **写 ADR**（`governance/adr/`），并**同步追加索引行**到 `adr/README.md` |
   | 流程细则、判分口径、实验纪律 | `cases/_methodology/实验规范.md` 或本文件 |
   | 单步任务进度 | `TODO.md`（T-xx） |
   | owner 本人才能做的事 | `USER_TODO.md`（U-xx） |

3. 每条须能回答**四件事：谁定的、什么时候、管什么、原文在哪。** 缺一项不算落盘。
4. 决议被推翻时**移入台账 §4「已作废」并写清为什么废**，不静默删除——决策史本身有价值
   （同 ADR 的 `Superseded by` 纪律）。

### 8.2 两条硬约束

**① 动实现之前先查决议出处。** 动任何**判分口径、工具面、题面、真值**之前，必须先在台账
查清这一条当初是谁定的、为了解决什么。**查不到出处 ⇒ 决议没落盘 ⇒ 先补台账，不得先改实现。**

**② 机械闸门的报警不是决议，不能作为改动依据。** `preflight.py`、`verify_isolation.py` 这类
闸门输出的是**信号**，不是判断。信号要先与决议对照，才知道它是真缺陷还是工具自身的识别边界。

### 8.3 为什么要有这一条（实测代价）

2026-08-21：执行方看到 `preflight.py` 报 `cp_lead_value` 饱和，**直接算了一版"把这一关移出
总分"并写成"待 owner 裁定"**，还写进了清单与四份 README。

复盘：那一关是**堵背答案的门**，饱和恰是它应有的行为（preflight 自己的注释就写着这句）；
而 owner 定义的"中间值"是**另一关**（`cp_conditions`）。执行方读了代码和闸门输出，
**却没读创造这一关的决议**——因为它只存在于 `TODO.md` 一个巨型单元格（T-184）里，检索不到。

**这不是纪律问题，是决议没落在能被查到的地方。** 同期还发现 `governance/adr/README.md` 索引漏了
8 个 ADR（0018–0022、0024–0026），其中 **0026 正是定义"第一组"的那一份**——
决议存在但找不到，等于没有。

若不立此规范，后续每个接手的工程师都会在同一处重犯：**读得懂代码，读不到意图。**
