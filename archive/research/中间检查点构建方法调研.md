## 读前必备的一个区分

讨论前必须先分清三件常被混为一谈的事，否则整篇会看糊：

| 叫法 | 实际在判什么 | 代表 |
|---|---|---|
| **过程量评测** | 这一步**做对了没有** | SciCode、AgentBoard、我方 |
| **进度度量** | 离终点**还有多远** | RE-Bench、SVGym |
| **轨迹验真** | 这份记录**是不是真的** | The Playground |

三者判的对象根本不同。 后两者常被称作"过程评测"，但它们回答不了"这一步是否正确"。本文只讨论第一类；第二类作为可借用的技术单列一节；第三类的分析另见 `research/Playground平台造题与判分机制.md`。

## 一、造检查点的五条路

先交代一件容易混的事：这五家的任务形态差别很大，卡点方法能不能搬到我们这儿，很大程度上取决于这个。

四家的 agent 是在写代码。AgentBoard 的 agent 在一个仿真环境里发动作，交的是一串动作而不是代码——这一家跟我们最像。我们的 agent 是调工具在候选库里挑分子，交的是一组 ID。

| 代表 | agent 干什么 | 交什么 | 写代码吗 |
|---|---|---|---|
| AgentBoard | 在仿真环境里搬东西、开关门 | 一串动作 | 不写 |
| SUPER | 把指定的 GitHub 仓库跑起来 | 一个数值 | 要写（改配置、跑脚本） |
| SciCode | 把科学公式写成 Python 函数 | 函数代码 | 纯写代码 |
| RE-Bench | 把一段已有代码优化得更快 | 优化后的代码 | 纯写代码 |
| PaperBench | 从零复现一篇论文的全部实验 | 代码仓库加结果 | 纯写代码 |
| 我们 | 调工具在候选库里挑分子 | 一组 ID | 不写 |

所以读下面几条的时候，方法可以学，任务形态别拿来直接类比。

### 第一条路：把目标写成条件，每个条件自动就是一个卡点

代表是 AgentBoard。先把链路走一遍：

```
出题：写一个仿真环境  →  把任务目标写成几个并列条件
答题：agent 发一条自然语言指令  →  仿真器解成动作  →  更新内部状态清单
判分：拿目标条件去状态清单里数，对上几个算几个
```

**环境这一层是关键，它不是纯文本题，是一个带状态的活程序。** 仿真器内部维护一份机器可读的世界状态清单，记的是“一号球在 A 房间”“手里没拿东西”这类条目。agent 发的自然语言指令会先被解成一个标准动作，合法就真的改状态，不合法就默默拒了。agent 看到的文字描述只是这份清单渲染出来的界面，**判分永远查底层那份清单，不读文字。**

卡点就是从目标里拆出来的。它有一道题是让 agent 把四个球都搬到 B 房间，这个目标写下来就是四个条件并列：一号球在 B 房间、二号球在 B 房间、三号、四号。拆开之后每个条件就是一个卡点，没人一条一条去写。 搬到两个球就是一半分。

$$\text{progress} = \frac{\text{已满足的条件数}}{\text{目标条件总数}}$$

其中已满足的条件数是拿目标条件逐条去状态清单里对，对上一条算一条，由仿真器演算得出而不是 agent 自报；分母是这道题拆出来的条件个数，上面那道题是四个。

这条路便宜在人只需要定骨架，具体实例靠往骨架里填东西生成。AgentBoard 用六种骨架覆盖了一百三十多个任务，平均一个骨架管二十来道题。

它有两个限制。一是目标必须能写成这种条件并列的形式，写不成的话这条路根本用不上。二是四个条件之间是并列关系，先搬哪个球都行，**所以它管不了顺序**。

### 第二条路：先自己跑通一遍，把日志里必然出现的字串当路标

代表是 SUPER。先把链路走一遍：

```
出题：挑一个 GitHub 仓库并钉死 commit  →  出题人自己把题跑通一遍
        →  从标准输出里挑几行写成正则，存进题目
答题：agent 拉仓库、装依赖、改配置、跑脚本  →  产出一堆执行日志 + 一个数值
判分：拿那几条正则去日志里搜（过程分）+ 比那个数值对不对（终态分）
```

它的题不是复现论文，而是把某个指定的 GitHub 仓库在给定数据上跑起来，最后报一个数。仓库地址、commit、超参数全都钉死了。比如那道 ColBERT 题，要求用指定分支训练一个检索模型，batch size 十六、相似函数用 L2、文档最长一百八十，最后把 loss 报回来，标准答案就是一个具体的浮点数。

它的卡点叫路标，就是解题过程中日志里必定会冒出来的那几行字。 那道题只挑了两条：一条是加载预训练权重时框架必然打印的警告，一条是训练第零步打出 loss 数值的那行。四十五道题平均每题只挑两三条，最少一条，最多六条。

**路标不是设计出来的**，是出题人先自己把题跑通一遍，然后从标准输出里挑出“只要做对就一定会出现”的行，抄成正则。 每道题的数据里都存着一份专家解法，就是为了支持这一步。

判分分两块。过程分是拿那几条正则去 agent 的执行日志里搜，搜到几条算几条；终态分是拿 agent 报的那个数值与标准答案做精确比对。两块都不过大模型。

$$\text{过程分} = \frac{\text{命中的路标数}}{\text{路标总数}}$$

其中命中数是逐条正则在日志全文里做子串匹配的结果；分母是这道题一共挑了几条，大多是两三条。

这里有个关键问题：专家挑的字串，凭什么 agent 一定会输出？

答案是**挑的全都是框架自己打印的东西，不是 agent 能决定的**。那条警告是 HuggingFace 加载权重时写死在源码里的；换成别的题，路标是 fairseq 命令行工具的固定输出、或是某个训练框架收尾时的固定日志行。agent 想完成任务就必须调那个脚本，调了框架就会打印，打印了日志里就搜得到。反过来说，搜不到那行，就说明它根本没跑那一步。

这也决定了这招的适用范围：**它成立的前提是这道题只有一条路可走。** SUPER 靠钉死仓库和 commit 做到了这点。要是换成一道允许多种实现的题，agent 用别的库达到同样效果，日志里就没那行字，正则会漏，明明做对了却判零分——这一点它自己在论文里也承认了。

这条路最适合规模化，因为路标能按任务族复用。只要是“用 HuggingFace 加载模型再训练”这一类题，那两条正则几乎原样能用，造一次同族题全覆盖。

### 第三条路：人工把大题拆成子题，每个子题配一组断言

代表是 SciCode。先把链路走一遍：

```
出题：科学家拿一道大题，把它拆成按依赖排序的子题
        →  每个子题写三样东西：任务描述、函数签名、一组测试用例
答题：agent 拿到签名和描述  →  把函数体写出来
判分：拿预存的测试用例跑它写的函数  →  比输出对不对
```

它的题面第一句就是“写一个脚本”，agent 交的就是 Python 函数代码。

拿它那道分子动力学的题举例。主题是实现一个恒温器算法，被拆成十二个子题，按依赖顺序排：先写一个处理周期边界的函数，后面算力的函数才能调它。整个题库是八十道主题拆成三百三十八道子题。

一个子题具体长什么样： 题面给一句描述（“实现一个叫 wrap 的函数，把粒子坐标折回到立方形盒子内”），给一个带完整参数说明的函数签名，再给一组测试用例。测试用例就是预存好的输入加一个期望输出，判分时拿输入跑 agent 写的函数，看返回值跟期望对不对（浮点数允许小误差）。

卡点是科学家一条一条人工拆出来的。 一个子题的全部断言都过了，这个卡点才得分；全部子题都过才算解决主题。全程不过大模型。

它拆出来的效果很能说明问题：主题解决率只有百分之十四到二十八，但子题通过率远高于此。也就是说 agent 常常做出了有意义的部分进展，只是败在某一步上，**而只看终态根本看不出这一点**。 这正是我们做过程卡点的同一个动机。

它自己承认的短板是拆解太依赖专家判断，三百多个子题很难自动化生成。另外子题之间虽然有依赖关系，判分时却是各自独立断言的，**并不检查 agent 实际的执行先后**。

### 第四条路：不设离散卡点，给一个随时能算的分数函数

代表是 RE-Bench。先把链路走一遍：

```
出题：写一个能跑的起始代码  →  配一个可执行的评分函数
答题：agent 改代码  →  随时自己调评分函数看当前得分  →  反复提交
判分：历史所有提交里取最高分
```

它给 agent 一段能跑的起始代码，要求把它优化得更快或更准，交的就是优化后的代码。

**它根本不设卡点。** 取而代之的是一个从任意中间状态都能算的质量函数，七个环境用三类度量：比耗时（如取微调脚本跑完一遍的耗时对数）、比 loss（取测试集上 loss 的对数）、比能力（取在留出题上的解题百分比）。**关键是这三类全是拿一个真跑出来的数，不是人工标签。**

有三个设计值得记。每个环境都先给一个能跑的起始解，而且刻意留了一些容易的优化空间，光调调超参就能涨一点分，这样部分进展能很快产生信号。允许反复提交并且当场看到分数，所以 agent 可以把它当反馈信号用。最终成绩取历史最高值。

不过有一个例外值得记：那道 scaling law 题为了防 agent 拿评分函数乱猜，只取“起始解分”与“最终提交分”两者的高值，而且不当场回示分数。

但必须说清一件事：**这测的是进度，不是过程正确性。** 它回答“离目标还有多远”，回答不了“这一步做对了没有”。SVGym 就是这条路的反面教材——它每步给分，但判的是候选质量。一个 agent 候选质量高但流程全错的时候，它给高分，我们判零分。

### 第五条路：跟论文作者一起搭一棵评分树

代表是 PaperBench。这条路的机制最复杂，所以下面按数据流走一遍——从出题到判分，每个环节经过什么、每个环节具体怎么做的。

#### 整条链路先看一眼

出题这一侧是一次性的准备工作，做完之后所有人共用：

```
挑论文  →  找原作者一起把"复现成功"拆成一棵树  →  连同论文、附录、黑名单打包成一道题
```

答题和判分这一侧，每来一份提交就走一遍：

```
容器一：agent 读论文，写出一个代码仓库
    ↓
容器二：把这个仓库真跑一遍（带 GPU），得到"跑完的提交"
    ↓
容器三：判分器拿着树，对着"跑完的提交"逐条问，最后算出一个总分
```

下面逐个环节说。

#### 环节一：挑论文，配四样东西

题库是二十篇 ICML 2024 的 Spotlight 和 Oral 论文。每篇论文除了 PDF 和 Markdown 正文，还配四样东西：

一份给 agent 看的附录，写的是原作者补充的复现须知，比如某个超参论文里没写清楚。一个资源目录，放论文里的图表等必要素材。一份黑名单，列出禁止访问的网址——最重要的是原作者自己的代码仓库被列进去了，不然 agent 直接克隆一份就通关了。还有一份只给判分器看的说明，交代判分时需要知道的背景，这份不是每篇论文都有。

#### 环节二：把"复现成功"拆成一棵树

这是最费人力的一步，也是"叶子"这个词的来源。

这棵树就是一个嵌套的清单。 最上面一层是一句总要求，往下每一层把上层的要求拆细，一直拆到具体得能直接判定为止。**拆到最底下、没法再往下拆的那一条，就叫叶子。**

拿那篇作为例子的论文，从上往下走一遍，看每层长什么样：

| 层 | 这一层的要求写的是什么 | 权重 | 还有子项吗 |
|---|---|---|---|
| 根 | 论文的核心贡献已被复现 | 1 | 有，9 个 |
| 第二层（其中一个） | 第 4.1 节和附录 C.2 里那些实验用的环境已经搭好 | 1 | 有，2 个 |
| 再往下（走到底） | 任何版本的那个仿真环境都被正确装好、能初始化、能用来跑实验 | 3 | **没有了，这就是叶子** |

最底下那一条就是一个叶子。它带四样信息：一句可判定的要求、一个权重、一个大类标签（这条属于"代码实现"类）、一个细类标签（这条属于"环境与基础设施搭建"）。

那篇论文最后拆出四百八十九个节点，其中三百六十一个是叶子。判分只判叶子，中间节点的分数是从下面的叶子算上来的。

三百六十一个叶子按大类分成三堆：一百七十八个查代码里有没有写对某个东西，一百七十个查那段代码有没有真跑出东西来，只有十三个查跑出来的结果跟论文对不对得上。**所以它百分之九十六的分数给的是过程做没做，不是结论对不对。**

三类叶子的要求写法差别很大。查代码实现的那类很硬，比如"环境版本必须是某个特定版本"，权重一分；查执行的那类也硬，比如"每个环境都真的预训练出了一个策略网络"，权重两分。但到了查结果的那类，措辞就变成"某节的保真度分数在各环境下大体可比"——“大体可比”这种说法没法写成程序判定，**这直接决定了整套判分只能交给大模型**。

#### 环节三：agent 在第一个容器里写代码

agent 拿到论文、附录和黑名单，在一个 Ubuntu 容器里干活，产出是一个代码仓库。它得自己决定怎么组织代码、装什么依赖、怎么复现那些实验。

#### 环节四：在第二个容器里把代码真跑一遍

这一步是整条链路里最关键的设计。 agent 交上来的仓库不是直接拿去判，而是先扔进一个全新的、带 GPU 的容器里执行一遍，跑完的产物连同原代码一起打包，官方叫它"跑完的提交"。

为什么必须有这一步：因为有一百七十个叶子查的是"代码有没有真跑出东西来"。光看静态代码判不了这个——跑完之后目录里有没有那个权重文件，是摆在那儿的，一看就知道。

这一步也是整套流程最贵的地方，因为要占 GPU 真跑实验。

#### 环节五：判分器在第三个容器里逐条判

判分器是一个跑在独立容器里、内部包着一个 OpenAI 模型的程序。底层用哪个模型可以换，论文正文用的是 o3-mini。它有自己单独的 API key，跟 agent 用的模型完全分开。

它的工作方式是逐个叶子问一遍：拿这个叶子的那句要求，配上"跑完的提交"，问大模型"这条满足了吗"，得到一个是或否。三百六十一个叶子就问三百六十一次。判完落一个结果文件。

#### 环节六：从三百六十一个是非题算出一个总分

叶子有了零一分之后，往上一层层加权平均：

$$\text{score}(\text{父}) = \frac{\sum_i w_i \cdot \text{score}(\text{子}_i)}{\sum_i w_i}$$

其中 $w_i$ 是第 $i$ 个子节点的权重，由出题人和论文原作者一起拍定，比的是重要性不是难度；$\text{score}(\text{子}_i)$ 在叶子那层就是大模型给的零或一，在中间节点是它下面那棵子树递归算出来的；一直算到根节点，根节点的值就是这道题的最终分，落在零到一之间。

这样天然支持部分得分——环境装对了但模型没训出来，前面那些叶子的分能拿到，后面的拿不到。

#### 一个绕不过去的问题：专家写死的三百六十一条，凭什么跟 agent 的自由输出对得上

这是整套机制最要紧的地方。答案是它压根不要求 agent 去匹配这些条目，**而是让判分器主动去仓库里找证据**。

跟第二条路的 SUPER 正好相反。SUPER 的卡点是一条正则，要求 agent 必须产出特定字串，靠框架必然打印那行来保证对得上。PaperBench 的卡点是一句自然语言，靠大模型能读懂不同写法都算满足。

它靠三件事做到这一点。

第一，条目刻意写得宽。回头看那条真实要求——"任何版本的那个环境被正确装好且能初始化"。它描述的是目标状态，不是实现方式。装在哪个目录、变量叫什么名、怎么封装，全不管。所以 agent 怎么写都不算跑偏，只要那件事真做成了。

第二，就是环节四那一步，先真跑一遍再判。判分器面对的是跑完的产物而不是静态代码，所以"有没有真跑出东西"这类要求才查得动。

第三，黑名单堵掉了抄答案的路。

所以“agent 不会瞎输出”靠的不是约束输出格式，**而是两头夹**。 上头是题目本身就是复现这篇论文，论文写死了要做哪些实验，agent 想得分就必须去做那些实验；下头是判分器不比字符串、只问这件事成不成，写法不同不影响得分。agent 当然可以瞎输出，但瞎输出一分也拿不到，因为三百六十一条里没有一条会被满足。

#### 它自己也不信任这套判分，所以另外评了一遍判分器

作者清楚大模型判分不可靠，专门做了一个辅助评测量判分器本身准不准。这跟我们“判分器要过断言、要抽题验分”是同一个意识——**判分工具本身就是一个需要被验证的对象**。

#### 这套流程有多贵：贵到官方出了一个简版

三个容器、其中一个占 GPU 真跑实验、再让大模型问三百六十一遍，成本压不下来。官方为此出了个简版，做法是只判那**一百七十八个查代码实现的叶子**，把查执行和查结果的那两类跳过去。

跳过之后不需要 GPU 了，因为环节四那一步整个省掉；判分成本也降了大约百分之八十五，因为要问的叶子少了一半多，而且不用等实验跑完。官方自己把这个简版形容为更便宜但不那么严谨。

一个评测基准需要专门出个简版来降判分成本，**说明大模型判分的开销已经到了碍事的程度**。

### 五条路的横向对比

| 路径 | 检查点从哪来 | 单题人工成本 | 可规模化 | 判定硬度 | 前置条件 |
|---|---|---|---|---|---|
| 一 形式化目标拆解 | 目标谓词自动拆 | **低**（只定骨架） | **高** | 硬 | 目标可形式化 |
| 二 金标准轨迹挖掘 | 正确执行的输出 | **低**（跑一遍收集） | **最高** | 硬 | 执行流可预期 |
| 三 约束函数库 | 逐条写判定函数 | 中 | 高 | 硬 | 约束可独立判 |
| 四 连续质量函数 | 不设离散点 | **最低** | 高 | 硬 | 目标可量化，**但只测进度不测正确性** |
| 五 分层 rubric | 专家共建 | **最高** | **低** | 软 | 有专家可投入 |
| **我方 cp1–cp6** | **懂化学的人逐条定** | **高** | **低** | **硬** | 领域专家 |

这张表是本次调研最重要的产出：我方在"硬度"上是最好的一档，但在"成本/可规模化"上和 PaperBench 一样处在最差的一档。

## 二、逐个 benchmark 的五问表

对每个对象问五件事：检查点从哪来 / 怎么判 / 有无顺序约束 / 分数怎么合成 / 自己承认的局限。

| # | Benchmark | 检查点从哪来 | 判定方式 | 顺序约束 | 分数合成 | 自承局限 |
|---|---|---|---|---|---|---|
| 1 | **SciCode** [5] | 科学家把科研编程题拆成 12–20 个有依赖的子问题（共 338 个） | Python `assert` 单元测试 | 有依赖，**但判分时各自独立断言** | 子问题通过率 = 过程分，全过 = 主问题解决 | 拆解依赖专家判断，难以大规模自动化 |
| 2 | **AgentBoard** [4] | 任务族子目标模板（6 种骨架覆盖 134 任务） | 正则匹配环境反馈 | **集合，只数个数不管先后** | 进展率 = 最大达成比例 | 未涉及偏序约束 |
| 3 | **SUPER** [23] | 执行的确定性 stdout 输出 | 正则匹配执行日志 | 无显式依赖，按时间自然捕获 | landmark 命中率 | landmark 依赖对执行流的稳定预期 |
| 4 | **MDArena** [2] | 分子动力学协议分解 | 摘要未披露具体机制 | 未知 | **strict-pass 与 process reward 双报** | 过程分判定硬度未公开 |

| 6 | **RE-Bench** [24] | 终态质量函数的连续采样 | 可执行 scoring function，agent 可随时调 | 无顺序约束 | 取历史最优，归一到 [0,1] | 需目标可量化，不适多目标权衡 |
| 7 | **PowerAgentBench** [18] | 七步工作流（选工具→筛故障→提措施→验证→证据链） | **隐藏评估器**重算物理有效性 | 隐式（工具调用先于结论） | 多维组合：evidence-backed recall + false-safe penalty + severity regret | 缺验证预算约束，衡量不了"高效取证" |
| 8 | **SpatialBench-Long** [39] | 生物分析的 key analysis chokepoints | 终答硬判（受控词表）+ **过程 rubric 软判** | 分析流程隐含先后 | 终答确定性分 + 过程 rubric 分 | 过程为软判；不规定方法导致变体过多 |

| 10 | **TravelPlanner** [9] | 逐条写约束函数 | 约束谓词判定 | **无，独立谓词** | 通过比例 | 约束平铺，查不出跳步 |
| 11 | **Commit0** [8] | 库的单元测试 | 测试过不过 | 无 | 测试通过率 | 只在编程域 |
| 12 | **TRAIL** [38] | 从冻结 trace **事后人工标注**错误 | 人工标注三类错误及 span 位置 | 仅定位最早错误步 | 二元准确性 | 纯事后标注；SOTA 仅 11% |
| 13 | **ProcessBench** [37] | 从数学推理链标注最早错误步 | 人工步级标注 | 推理链顺序 | 二元错误检测 | 人工成本不可持续 |
| 14 | **PRM800K** [36] | **80 万条**人工步级标注 | 过程监督 label | 推理链顺序 | 过程监督 vs 结果监督对比 | 成本极高；不评 agent 实时决策 |
| 15 | **BPOP** [56] | **从 agent 轨迹反推**潜在偏序（贝叶斯） | conformance checking：线性扩展 vs DAG | **真偏序，允许多条合法路径** | MCMC 近似 | **枚举线性扩展是 #P-hard** |
| 16 | **卒中诊疗符合性检查** [57] | 从医疗指南抽取 50 条规范规则 | 文本抽轨迹 → 规则译成可执行脚本 → 算符合度 | **业务流程偏序** | 符合度指标（实测 86% 符合） | 需医学知识映射规则；规则完备性待验 |
| 17 | **Skill Learning w/ Process Mining** [58] | 从执行日志 mining 技能模式 | conformance checking，**明确支持并行** | **偏序，支持并行执行** | 技能检索准确率 | 依赖大量高质量执行日志 |
| 18 | **The Playground** [66] | 终态输出字段拆细 | 重放执行 + 数值公式 | **无** | 结果分 × 轨迹折扣 | **不测过程正确性**，轨迹分只验真伪 |

## 三、顺序判定专项

这一节对应实现点 2。

### 3.0 先说清一件事：这一节里大部分不是 benchmark

先把性质分清，否则容易把“方法”当成“评测基准”看：

| 工作 | 它到底是什么 | 它的目的是什么 |
|---|---|---|
| **BPOP** [56] | **一个推断方法** | 从轨迹反推依赖图，编译成执行器以**省 token 与时间** —— **不是打分** |
| **卒中诊疗符合性检查** [57] | **一个医疗应用系统** | 查真实患者的诊疗过程合不合临床指南，**判的是医生不是 agent** |
| **Skill Learning w/ PM** [58] | **一个技能检索方法** | 把挖出的流程图当技能库，提升计划生成 —— **不是评测** |
| **EnvTrace** [59] | **一个代码评估方法** | 判 LLM 写的代码与参考实现是否语义等价（算半个评测方法，但无题库） |
| Desktop-Delta [6] | **是 benchmark** ✅ | 463 道题，让模型给三帧截图排序 |
| FukuyamaBench [7] | **是 benchmark** ✅ | 判化学反应机理的步骤序列 |

**也就是说：六个里只有两个是 benchmark。**

#### 为什么把非 benchmark 的也纳进来

因为“判 agent 执行顺序”这件事，**在 AI benchmark 领域几乎是空白的**。

前面那 18 个有中间检查点的 benchmark，没有一个判 agent 自己跑出来的顺序：AgentBoard 的子目标是集合、SciCode 子题各自独立断言、TravelPlanner 是独立谓词。

而上面那两个真 benchmark，判的也不是 agent 的执行顺序：

- Desktop-Delta 把顺序做成了题目 —— 给模型三帧图让它排序，模型是答题者，不是被审查的一方
- FukuyamaBench 判的是化学反应本身的步骤序列（自然界的顺序，客观唯一），不是 agent 工作流的顺序

所以想学“怎么判执行顺序”，**只能到 benchmark 圈外去找** —— 那些方法与应用虽然不是评测基准，但它们的判定技术是现成的。

而这一条本身就是本次调研最有价值的发现之一：判顺序在 AI 评测里是空白，成熟做法全在业务流程管理（BPM）领域。**我方要取经得去 BPM 文献**，而不是在 AI benchmark 里找同类。

> 必须承认的一句：判顺序在 BPM 领域叫 conformance checking（符合性检查），已有几十年积累，比我方成熟。我们做的是把它适配到化学发现任务上，不是提出了新方法。

### 3.1 BPOP：从轨迹反推偏序（方法，非 benchmark）

它做的事比我方难一个量级。

- 把 agent 轨迹建模为 DAG 的线性扩展（linear extension，即拓扑排序的标准数学名称）
- 用 MCMC 从轨迹反推潜在的 DAG 结构
- **关键理论结论：枚举线性扩展是 #P-hard**，所以只能 MCMC 近似

**与我方的关系：方向相反。** 我方是"预先给定 DAG，判轨迹合不合规"，复杂度 $O(|E|)$；它是"从轨迹反推 DAG"，#P-hard。

这条对我方的价值：它反向证明了我方的方向是可计算的 —— 给定 DAG 判轨迹是多项式时间，不必担心复杂度。

### 3.2 卒中诊疗符合性检查：流程与我方几乎同构（应用系统，非 benchmark）

四步，和我方一一对应：

| 它的步骤 | 我方对应 |
|---|---|
| 从文本抽取患者实际轨迹 | 从网关录像抽取 agent 轨迹 |
| 从医疗指南抽取规范规则（50 条） | 从化学逻辑定 CP_DAG_EDGES |
| **把规则翻译成可执行脚本** | checkpoint 断言 |
| 算符合度指标 | 顺序合规判定 |

**实测：50 条规则测数百条轨迹，86% 符合。**

唯一实质差别是它的规则来自现成的医疗指南文档，**我方的边必须由懂化学的人从头定**。这正是我方成本高的根源——化学发现没有一份“指南”可抽。

### 3.3 Skill Learning w/ Process Mining：为偏序设计提供理论支撑（方法，非 benchmark）

它明确支持并行执行的 conformance checking —— 也就是偏序，不只是全序。

这条对我方的直接意义：证明"只绑真实依赖、不约束无依赖步骤"在方法论上是站得住的，不是我方为了宽容而放松标准。

### 3.4 EnvTrace：执行轨迹对齐（评估方法，无题库）

对 LLM 生成的代码构造执行轨迹，与参考实现做语义等价对齐，配数字孪生环境验证。侧重"语义等价"而非严格顺序。

### 3.5 顺序判定技术栈对比

| 技术 | 代表 | 复杂度 | 适用 |
|---|---|---|---|
| 拓扑排序（给定 DAG） | **我方** | $O(\|E\|)$ | 偏序约束验证 |
| 线性扩展枚举 | BPOP | **#P-hard** | 反推 DAG |
| Conformance checking | 卒中诊疗、Skill Mining | 多项式 | 业务流程符合性 |
| 执行轨迹对齐 | EnvTrace | 取决于对齐算法 | 代码语义等价 |

### 3.6 明确不判顺序的

AgentBoard（子目标是集合）、SciCode（有依赖但独立断言）、TravelPlanner（独立谓词）、The Playground（编号只是叙述顺序）。

## 四、五条可直接借鉴的具体做法

按"能不能真用上"排序，每条给出怎么做、以及在我方的落点。

### 借鉴一 · 用环境状态谓词代替执行日志正则

来自 AgentBoard-PDDL [4]。它不在轨迹文本里搜正则，而是在环境维护的符号状态里查谓词真值，判定退化成一个集合包含关系的判断。

这么做更好的理由很直接：正则匹配的是“agent 说了什么”，状态谓词查的是“世界变成了什么”，后者不可能被话术绕过。

我方已经在做类似的事（真值从工具调用记录反查，不采信自报），但查的是“调用记录里有没有这条”，不是“世界状态是否满足谓词”。前者仍是日志检索，后者是状态查询。可考虑让网关内部维护一份“已查证实体 × 已知性质”的结构化状态，卡点直接查这份状态。

### 借鉴二 · 双报严格通过率与过程分

来自 MDArena [2]。它的观察与我方动机一字对应：**过程分显著高于严格成功率**，说明 agent 常做出有意义的部分进展却败在细节上。

我方的总分已用门控公式（有关卡不过则压在 0.3 以下），但对外只报一个合成分。建议改为始终并列报两个数：六关全过率、过程分均值。因为合成分恰好掩盖了“部分进展”这个最有信息量的现象。

### 借鉴三 · 自洽校验：用两个必须一致的产物互相验证

来自 The Playground [66]。它要求 agent 同时交一条曲线和一个从曲线导出的标量，判分器去曲线上重算该标量，与所报值比（该平台用的容差是 0.015 nm，不符直接零分）。

**这招值得学的地方是它不需要标准答案。** 抄了论文数字但曲线是编的，两者必然对不上；要对上就得真算出曲线。而且它比查执行顺序更难绕——顺序可以伪造，两个产物的数值一致性很难伪造。

我方目前 cp3 是覆盖性检查，该查的都查了就给分。可加一条自洽约束：要求 agent 在答案里同时给出候选 ID 与其排序依据值，判分器拿 ID 去工具记录里取真值重算排序，与 agent 声称的排序比。这样“没真查却蒙对排序”会被抓出来。

### 借鉴四 · 连续质量函数作为过程量的补充维度

来自 RE-Bench [24]，做法是给一个从任意中间状态都能算的质量函数，全程可采样，取历史最优。

它不能替代 cp1 到 cp6，但可以当一个独立的报告维度。我方任务有天然的质量函数（当前候选池里最优候选与真答案的差距），可在轨迹上逐步采样，画出一条逼近曲线。这对论文的分析章节是好素材，能看出 agent 是稳步收敛还是瞎撞。

边界必须写明：这是进度度量，不是正确性度量。SVGym 的教训就在这里——候选质量高但流程全错时它给高分，所以这条维度绝不能进总分。

### 借鉴五 · 隐藏评估器加有证据支撑的召回率

来自 PowerAgentBench [18]。它的指标 evidence-backed recall（有证据支撑的召回率）在语义上就是我方的 cp3。它还额外测两件我方没测的：验证预算怎么用、有没有重复验证。

我方已有调用上限 50 次，但没有把预算效率做成指标。可低成本加一项：达成同等卡点分数所用的调用次数。这能区分高效取证与暴力穷举。

## 五、我方相对这些工作的不足（诚实清单）

### 不足一 · 检查点的来源最贵，且没有规模化路径

这是最大的短板。 我方 cp1–cp6 靠懂化学的人逐条定，与 PaperBench 同处成本最高档，而 PaperBench 自己已承认这条路不可持续。

对照下来，两条便宜的路我方都没试：

- **形式化目标自动拆解**：我方的题目形态其实**有形式化基础** —— 题目就是"满足性质约束 $C$ 且指标 $m$ 最优"，这本身是谓词合取。是否能像 AgentBoard 那样定几种骨架、实例靠填槽自动生成检查点，**未评估过**。
- **金标准轨迹挖掘**：我方有正确解法（出题时就知道答案与路径），理论上可以跑一遍正确流程、**把必经的工具调用序列挖成路标**，未尝试过。

### 不足二 · 顺序判定的偏序设计尚未真正落地

已登记的既有问题：当前边集是一条链（cp1→…→cp6），实测拓扑排序数 = **1**，事实上退化成唯一全序。**"允许多条合法路径"这个设计意图目前是空的。**

而 BPOP、Skill Mining 都已实现真正的偏序（支持并行）。

### 不足三 · cp3 只做覆盖性检查，不检查"用对了没有"

三条外部证据都指向这个缺口：

- Re²Math [50]：最好的 ToolAcc 只有 7.0%，而 grounding 率高得多 —— **"查到了"和"查到的东西用对了"是两件事**
- LayerRAG-Bench [51]：只看 groundedness 在过期证据下会产生大量假阳性
- OpenBioRQ [46]：引用 99% 能打开，但 15.9% 链向错误的论文

我方的缓解条件是闭合快照库（工具返回值恒等于快照真值，不存在过期证据），**但这个论证必须在论文里写明，不能默认成立**。

### 不足四 · 过程量只有一个维度

对照 PowerAgentBench 的多维组合（evidence-backed recall + false-safe penalty + severity regret）与 ToolMATH 的三轴（Adaptability / Robustness / Tool Connectivity），**我方只有 cp 通过率一条轴**。缺的至少有：预算效率、重复验证、错误恢复能力。

### 不足五 · 没有跑间方差数据

`AgenticBenchFlaws` [21] 与 `BenchmarkingBenchmarks` [22] 都把这一项列为 benchmark 效度的必检项，后者实测同配置重复 23 次分数跨度 **18.9 个百分点**，足以改变排行榜结论。我方是 3 轮，**没测过自己的方差**。已登记。

## 七、结论与下一步

### 三条核心发现

**第一，造检查点的成本差两个数量级**，而成本几乎完全由“目标能否形式化”决定。 能形式化 → 自动拆解（AgentBoard 6 个骨架覆盖 134 任务）；不能 → 只能人工（PaperBench 361 个叶子靠专家共建）。

**第二，判 agent 执行顺序这件事在 AI benchmark 领域是空白的。** 前面 18 个有中间检查点的 benchmark **没有一个**判 agent 自己跑出来的顺序（AgentBoard 子目标是集合、SciCode 子题各自独立断言、TravelPlanner 是独立谓词）。顺序判定专项里那六个工作，**只有两个是 benchmark**（Desktop-Delta、FukuyamaBench），且这两个判的也不是 agent 的执行顺序 —— 一个把顺序做成了题目让模型排序，一个判的是化学反应本身的步骤。**其余四个是方法或应用系统，不是评测基准。** 这既是我方的机会，也说明我方该去 BPM 文献里取经，而不是在 AI benchmark 里找同类。

**第三，"过程评测"这个词被严重滥用。** 三类完全不同的东西都自称过程评测：判正确性、测进度、验真伪。The Playground 属第三类，SVGym 属第二类，只有 SciCode / AgentBoard / 我方属第一类。**论文里必须把这个区分讲清，否则审稿人会认为我方与它们雷同。**
