# 实验矩阵（最终实验 · 待填数据总表）

> **这份文档就是最终实验的成绩单。** 用一个运动会类比贯穿：**Harness 是跑鞋（用什么壳子），Backbone 是运动员（用什么模型），Case 是比赛项目，统计数据是成绩 + 用时 + 心率。** 目标：让每个"跑鞋 × 运动员 × 项目"组合都跑一次，把格子填满。
> 用法：跑完一个实验点（= 一个 Harness × Backbone × Case），就在 §三明细表对应行填数；每凑齐一列（同一 Harness × Backbone 的 6 个 case），就汇总进 §四总矩阵。
> 状态标记：⬜ 待跑 / ⚡ 已有 trace 待评分 / ✅ 已填 / ⛔ 缺前置条件（注明缺什么）。
> 依据：壳子与模型选择、口径要求均来自《测试Agent调研总报告》（本文引用其章节号）。

## 全景结论

**矩阵 = 3 个 Harness × 3 个 Backbone × 6 个 Case，每个实验点填三组数：判分（cp1–cp6 + task_score）、资源（token + 成本 + 时延）、过程（LLM 次数 + 工具次数）。** 波次 0（自建薄壳 × 3 模型 × 6 case = 18 点）的 trace 已在手且 15/18 已评分，仅 P06/P12/P18（open_superconductor × B2/B3）缺 trace；波次 1（Claude Code + QoderCLI，2 个商用厚壳 × 6 case = 24 点）待跑。Codex CLI / Kimi Code / Hermes Agent 本机不可用（区域限制/安装失败），已排除。**填表前有 4 个工程缺口必须先补**（见 §五），否则 token、成本、时延、task_score 四列填不出来。

## 二、统计数据的指标口径（填表前先对齐定义）

**为什么要先定口径：调研发现"调用次数"在各论文里口径混乱（一步的定义不同、是否去重不同），Terminal-Bench 2.0 只对自家壳子报数（调研报告 §3.5）。我们把口径钉死在这里，填表时不许偏离。**

### 2.1 判分类（每个实验点 9 个数）

| 指标 | 含义（大白话） | 从哪来 |
|---|---|---|
| cp1 文献检索 | 检索次数够不够（≥2 次满分）× 找到的不重复论文够不够（≥3 篇满分） | trace 里的 literature_search 调用 |
| cp2 候选建池 | 推荐的候选是不是真从工具里查到的（不许瞎编）× 有没有包含 GT | response.ranked ∩ trace 检索集 |
| cp3 性质查证覆盖 | 每个候选 × 每条约束性质，查没查到（格子级） | trace 里 predict_admet 返回 |
| cp4 筛选正确性 | 按工具返回的真值重算谁合格，和 agent 给的名单比 F1 | trace 重算 vs response |
| cp5 排序正确性 | agent 的排序 vs 用真值重算的排序，逐位比对 | 同上（⚠️ 空集给满分是已知 bug，T-37） |
| cp6 最终推荐 | 第一名是不是 GT（命中 1.0 / 在合格集 0.5 / 不在 0） | response[0] vs gt.id |
| process | 6 个 checkpoint 的加权平均 | 公式见下 |
| gate | 6 个 checkpoint 是否全部过线 | 公式见下 |
| task_score | 最终分（过线才给满分档） | 公式见下 |

\[ \text{process} = \frac{\sum_{i=1}^{6} w_i \cdot s_i}{\sum_{i=1}^{6} w_i}, \qquad \text{gate} = \prod_{i=1}^{6} \mathbf{1}[s_i \ge t_i], \qquad \text{task\_score} = \begin{cases} 0.5 \cdot \text{process} + 0.5 & \text{gate}=1 \\ \min(0.3,\; 0.5 \cdot \text{process}) & \text{gate}=0 \end{cases} \]

其中：

- \(s_i\) = 第 \(i\) 个 checkpoint 的得分，\(s_i = \text{clamp01}(\text{eval}(\text{reward}_i))\)，即把该 checkpoint 的 reward 表达式算出来再截断到 \([0,1]\)；
- \(w_i\) = 第 \(i\) 个 checkpoint 的权重（template 中 cp1=1, cp2=2, cp3=2, cp4=2, cp5=1, cp6=2）；
- \(t_i\) = 第 \(i\) 个 checkpoint 的及格线 `pass_threshold`（cp1=0.6, cp3=0.8, 其余=1.0）；
- \(\mathbf{1}[\cdot]\) = 指示函数，条件成立为 1 否则为 0；gate=1 表示 6 个 checkpoint 全部过线；
- 含义：全过线 → 过程分占一半再加 0.5 保底（满分档）；有任一不过线 → 最多 0.3（封顶，防止"答错但过程热闹"拿高分）。

### 2.2 资源类（每个实验点 5 个数）

| 指标 | 定义 | 从哪来 | 现状 |
|---|---|---|---|
| input_tokens | 所有 LLM 调用的 prompt tokens 之和（**不含 cache 读**） | API 返回 `usage.prompt_tokens` | ⛔ harness 未记，待补 |
| output_tokens | 所有 LLM 调用的 completion tokens 之和 | API 返回 `usage.completion_tokens` | ⛔ 同上 |
| cache_read_tokens | 命中缓存的读取量（**单列，不计入 input**） | `usage.input_token_details` | ⛔ 同上 |
| 成本（USD） | 按模型单价折算（照 Harbor 用 `litellm.cost_per_token`） | 上面三项 × 价目 | ⛔ 依赖上两行 |
| 总时延（秒） | 一个实验点从发起到交卷的 wall time | harness 记 run 起止 | ⛔ 未记，待补（trace 里的 `latency_ms` 只是工具时延，可单列参考） |

### 2.3 过程类（每个实验点 3 个数）

| 指标 | 定义（口径钉死） | 从哪来 |
|---|---|---|
| LLM 调用次数 | harness 发起 `llm_chat` 的总次数（= HTTP 请求数） | response json 的 `steps` 字段（已有） |
| 工具调用次数 | trace jsonl 的数据行数（一条 = 一次工具执行） | `tool_calls_total` / 数 jsonl 行（已有） |
| 步数 | **我们定义：一步 = 一次工具调用**（细粒度）。跨壳对比时必须说明对方口径 | = 工具调用次数 |

> **三条铁律**（来自调研报告 §3.5）：① 报数必须同时声明"一步的定义"；② 我们**不去重**（同一工具同参数调两次算两次），与 Terminal-Bench 的 block 去重不同，对比时注明；③ LLM 调用次数与工具调用次数**分开报**（并行工具调用会让两者不等）。

## 六、防坑清单（每个实验点开跑前自查）

1. **版本钉死**：厚壳记录版本 + checksum（H5 额外记 commit hash）；薄壳记录 git commit；
2. **实验卫生**：禁遥测、session 目录隔离、模型别名对齐同一模型、按公式禁用 prompt caching 时记为独立档（照 Harbor，调研报告 §四·三）；
3. **context 钉对**：Kimi 1M、GLM 钉正窗口，钉错会让模型提前截断、分数被人为压低；
4. **compaction 记录**：厚壳若触发 compaction，记为该实验点的元数据（它是解释分数的关键变量）；
5. **口径一致**：严格按 §二定义填，不另立口径；跨壳对比先对齐"一步"和"去重"口径；
6. **不编造**：⬜/⚡/⛔ 如实标注，缺前置条件就写缺什么，不预填估计值。
