## §0 四条铁律

1. **一律用 claude code 真 agent 跑**，每个 run 一个独立隔离 workspace。禁止用单次 chat completion 冒充 agent。
2. **开跑前先过隔离验证**：`python src/probe_headless/verify_isolation.py`，**A~G 七组 25 条断言全过**才能跑正式实验。
   隔离已经被证伪过三次（工具白名单挡不住、cwd 关不住、`.claude_cfg` 放 ws 里泄露 AK），
   靠人眼看输出不可靠。
3. **跑之前先读 trace**，写明"看到什么问题 → 假设 → 改什么"，再改再跑。禁止盲跑。
4. **跑完立刻落结论**，不许"先跑下一批再回来分析"。

> ⚠️ **本规范曾被违反**：2026-08-17 那一轮我用自写 harness（`census_runner.py` /
> `chain_harness_stream.py`，走 idealab OpenAI 端点）跑了 ~600 run，累计踩了 12 个
> harness 自身的 bug（含限流伪装成模型回答、账本互相覆盖等）。这些 bug 全部是
> **自写 harness 独有的**，用 claude code 范式根本不会出现。教训：不要重新发明 agent 循环。

## §1 运行环境（锁定，不得改）

| 项 | 值 | 理由 |
|---|---|---|
| agent | `claude -p`（无头模式）| 单次 API 调用会撞输出 token 上限（glm 曾思考 26 万字符、正文 0 字节、5/5 全败）；agent 循环把思考与答案分开落盘，天然无此问题 |
| 端点 | `ANTHROPIC_BASE_URL=https://idealab.alibaba-inc.com/api/code` | Anthropic 兼容端点，写在 `~/.claude/settings.json` |
| 模型指定 | `ANTHROPIC_MODEL=<模型名>` 环境变量 | 无需 sonnet/opus 别名 |
| 模型池 | 见 §1.1（**必须用真实 claude code 启动测出来**，不能用裸 API 测）| 裸 API 能回 `hi` 的模型，在 claude code 里可能直接 400 |
| 温度 | 默认（不显式设）| claude CLI 不提供该参数 |
| 超时 | 3600s（`run_agent` 自带）| macOS 无 `timeout` 命令，别在脚本里用 |

### §1.1 模型池（已用真实 claude code 启动验证，2026-08-17）

**测法纪律：能不能进池，只能用 `probe_claude_models.py` 判（真跑一次 claude code）。**
裸 API 打 `hi` 的测法已被证伪：`qwen-turbo` 裸 API 返回 200 正常，
在 claude code 里 **直接 400「模型提供方错误」**——因为 claude code 一次请求要带
十几个工具定义 + 长系统 prompt，弱模型撑不住。

| 模型 | 能跑 agent | 说明 |
|---|---|---|
| `qwen3.7-max` | ✓ | 旗舰 |
| `bailian/glm-5.2` | ✓ | 旗舰 |
| `qwen3-coder-plus` | ✓ | |
| `deepseek-v3.2` | ✓ | |
| `DeepSeek-V3-671B` | ✓ | 开源权重，便于外部复现 |
| `qwen3.5-plus` | ✓ | |
| `qwen-turbo` | **✗** | 400：工具定义太多撑不住 |
| `qwen3-coder-flash` | **✗** | 不会原生工具调用，把调用当文本吐：`<function=Write>…` |
| `DeepSeek-R1-671B` | **✗** | 同上，吐成 ```json[{"name":"Write"…}]``` |
| GPT 系 / gemini / llama3 / kimi | ✗ | `/api/code` 根本不路由（`PRE-005` 参数类型错误，换参数重试无效）|

**重要后果：低档模型在 claude code 范式下不存在。**
能跑完一个 claude code agent 本身就是能力门槛（需要原生工具调用 + 长上下文），
所以可用的 6 个全是中高档。“高/中/低三档分层”这个预期在本环境下无法实现，
尺子的区分度只能靠**题目难度**拉开，不能靠模型强弱差拉开。

**模型池不得为了调均值而增删**。想扩池只能因为端点真的放行了新模型。

## §2 一次实验 = 一个独立 workspace

### 2.1 启动一次 run 只需选四样东西

唯一入口是 `ws_isolation.run_case()`：

```python
r = iso.run_case(
    model="deepseek-v3.2",                       # ① model name
    tools=["mcp__matlab__measure_tc"],           # ② given tools（必须是 list）
    prompt="Read TASK.md and complete the task...",   # ③ init prompt
    files={"TASK.md": ..., "data/x.txt": ...},    # ④ workspace 下要有的文件
    mcp_server=SERVER, mcp_env={"PY": ..., "CASE_FILE": 真值路径},
    archive_to=RUNS, round_id="r1")
```

各 case 的 `ws_runner_*.py` 只剩一个 `build_files()`，负责"这道题的题面长什么样"；
隔离、鉴权、启动、轨迹、失败分类、归档全在 `run_case()` 里，调用方不管。

### 2.2 目录分层：run 容器 vs workspace

```
<临时目录>/bench_runs/<随机 12 位 id>/    ← run 容器，agent **看不到这一层**
├── ws/                     ← agent 的 cwd，它眼里的整个世界
│   ├── TASK.md             题面
│   ├── data/               输入清单（fixed 给候选；open 不给）
│   ├── answer.json         ✅ agent 写的结构化答案 —— 唯一判分依据
│   ├── tool_calls.jsonl    ✅ MCP server 记的工具账本 —— 防 agent 自报
│   └── notes.md            ❌ agent 自述推理（只给人看，不判分）
├── .cfg/                   CLAUDE_CONFIG_DIR（**内含 AK**）
├── mcp.json               MCP 配置
├── trace.jsonl            claude code 全轨迹
├── stderr.txt
└── meta.json              随机 id → (model, round) 映射
```

跑完拷到 `cases/<domain>/<side>/case_<id>/runs/<model>__<round>__<ts>/` 留档
（带 trace/stderr/meta，**不带 `.cfg`**）。

> 注：macOS 上 `tempfile.gettempdir()` 不是 `/tmp`，而是 `/var/folders/.../T`。
> 查跑中的 run：`python3 -c "import tempfile;print(tempfile.gettempdir())"`。

### 2.3 四条硬约束

**① 基础设施文件必须在 ws 之外。**
曾把 `.claude_cfg` 放进 workspace，实测 agent 列目录直接看到了
`settings.json`（**AK 明文**）与 `projects/*.jsonl`（会话记录）；
`trace.jsonl` 在 ws 里时 agent 还能读自己的轨迹。现在这些全在父目录，
而父目录属于"cwd 之外"→ claude code 自动拒绝访问。

**② run 目录名必须是无意义随机串。**
agent 能准确报出自己的 cwd 绝对路径（实测它说出了 `/private/tmp/probe_info`）。
若目录名写成 `qwen3.7-max__r3__…`，就等于告诉它"你是 qwen3.7-max、这是第 3 轮、
你正在被评测"。可读名字只出现在归档阶段与 ws 外的 `meta.json` 里。
（附带实测结论：agent 自报模型是 "Claude (Anthropic)"，本身并不知道真实模型名。）

**③ 每次 run 的 workspace 不得相同。**
`uuid4().hex[:12]` + `mkdir(exist_ok=False)`：撞名即报错，绝不静默覆盖。

**④ 判分侧在 ws 之外，与 ws 内容合起来才是一个完整 run case。**

| 在 ws 内（agent 可见）| 在 ws 外（agent 不可见）|
|---|---|
| 题面 `TASK.md`、输入 `data/` | 真值 `artifacts/ground_truth.json` |
| agent 产出 `answer.json` / `notes.md` | 判分器 `judge_*.py` |
| 工具账本 `tool_calls.jsonl` | MCP server 脚本、AK、轨迹 |

真值**只**交给 MCP server 子进程（它不受 agent 权限约束），由它按题意返回受控信息
（如 `measure_tc` 只对已合成样品返回 Tc）。判分**不信 agent 自报**：
数值一律与离线真值逐点比，测量次数从工具账本数。

**两类产出都要留档，互不冲突**：
- `answer.json` + 工具账本 = **做了什么**（可机器硬判的事实）
- `notes.md` + trace 里的 thinking = **为什么这么做**（推理链，诊断哪一步想错）

**没有 `submit_answer` 工具**——答案由 agent 写文件。这比塞进一次工具调用更接近真实科研产出，
也消除了"答案挤在单个回复里"这个 token 上限来源。

## §3 隔离三根支柱（代码在 `src/probe_headless/ws_isolation.py`）

**原则：要真隔离，不要 deny 兜底。** deny 是"看得见但执行时拦"——工具照样出现在
tool list 里占 context、照样告诉模型"有 web-search 这种东西存在"，路径也照样可枚举。
干净的做法是让 agent **认为世界里只有 workspace 和那几个工具**。

| 支柱 | 机制 | 作用 |
|---|---|---|
| 1 基础设施在 ws 之外（ws 只是 run 容器里的一层） | `new_run_dir()` 建 `<run_root>/<随机id>/ws`，AK/轨迹/mcp.json 放在 ws 的**父目录**；跑完 `_archive()` 拷回仓库。**`run_root` 生产默认是仓库内的 `.bench_runs/`**（owner 08-24：所有工作都在 benchmark 目录下，不放系统 /tmp、不碰别人目录），已 gitignore | claude code 原生把 cwd 外的路径全拦（无头模式无人授权）→ **真值、别的 run、AK、轨迹全部不可达，零 deny 规则**。⚠️ **已知覆盖缺口（08-25）**：`verify_isolation.py` 的 run 根目录设在**仓库外** `/tmp/bench_verify`，所以**越狱断言 F 项从未在 `.bench_runs/` 这个生产布局上跑过**——而历史那次逃逸（agent 写出 `<仓库根>/ESCAPED.txt`）恰恰是"父目录链在仓库内"造成的。补法见 `BENCH_SPEC.md` §9.2 |
| 2 `--tools` 限定暴露集 | `--tools "Read,Write,Edit,Grep,Glob"` + `--disable-slash-commands` + 干净 `CLAUDE_CONFIG_DIR` | agent **认为自己只有这几个工具**（不是禁止执行）|
| 3 `--allowedTools` 只给 MCP | `--allowedTools "mcp__matlab__measure_tc"`，**绝不含 Read/Write/Edit** | 领域工具免批准；文件工具走默认规则（cwd 内允许、cwd 外需批准即被拒）|

### 三个参数语义完全不同，混用就开后门

| 参数 | 语义 | 混用的后果 |
|---|---|---|
| `--tools` | 内置工具的**暴露集** | 不给 → 暴露 23–27 个工具，含能联网的 `Skill` |
| `--allowedTools` | **免批准**清单 | 把 `Read` 放进去 → Read 任何路径都免批准，**实测 agent 成功读到 `ground_truth.json`** |
| `--disallowedTools` | 执行期**拦截** | 只拦执行，工具仍在列表里 → 不干净，已弃用 |

### 三个被实测证伪的旧说法

**1. "`--allowedTools` 白名单 → 其余全 mask" —— 错。**
给 4 个白名单时 `init` 事件仍暴露 **23 个**工具，多出 `Skill`、`Workflow`、`Cron*`、
`EnterWorktree` 等。其中 **`Skill` 能调 `web-search` / `deep-research` / `scholar-search`**，
等于联网查真值的后门。换 `--tools` 后暴露数降到 **5**。

**2. "`cwd=workspace` 就能把 agent 关住" —— 错。**
`qwen3.7-max` 用绝对路径成功写出 `<仓库根>/ESCAPED.txt`，它自己还在回复里写了
"Write succeeded — the workspace isolation d…"。根因是 workspace 在仓库内。

**3. "那些多余工具是插件注入的，换干净配置就没了" —— 也不对。**
`CLAUDE_CONFIG_DIR` 换成空目录后 `plugins` 归零，但 `Skill`/`Workflow`/`Cron*` 仍在——
它们是这个内网版 claude code 的**内置工具**。所以必须靠 `--tools` 挑，光换配置不够。

### 不要用 `--safe-mode`

它会把 **MCP servers 一起禁掉**（实测 `mcp_servers` 变成 `[]`），领域工具进不来。
屏蔽全局 plugins/hooks/CLAUDE.md 用 `CLAUDE_CONFIG_DIR` 指向干净目录即可。

### 红队验证：每次改隔离相关代码都必须跑

```bash
python src/probe_headless/verify_isolation.py [模型名]
```

**A~G 七组共 25 条机器断言**（脚本自己打印的通过数；`grep -c 'check('` 数出 32 是
把 `def check` 和 C/D 两组 try/except 里互斥的分支重复计了，实跑只可能命中一条），
失败则 `exit 1` 并打印
"**隔离未通过验证，不得开跑正式实验**"。
前 4 组不花 API 额度，后 3 组起一次真 agent（同一个 prompt 里同时让它做
合法的事与六种未授权访问尝试，一次跑完全部验证）：

| 组 | 验证什么 |
|---|---|
| A 目录布局 | ws 是 run 容器的子目录（基础设施才能待在 ws 之外）；新 ws 干净、不继承别的 run 的产出；run 目录名不含模型与轮次 |
| B workspace 独立 | 连开 20 个 run，目录互不重名、20 条 ws 路径互不嵌套（谁也不在谁里面） |
| C 类型断言 | `tools` 传字符串必须报 `TypeError` |
| D 模型池校验 | 不在 `MODEL_POOL` 的模型必须报 `ValueError` |
| E 工具面干净 | `init` 暴露数 == 内置数+MCP 数；agent 自述工具里无 Bash/Skill/Task/Web* |
| F 未授权访问全失败 | 读真值 / 写仓库 / 列仓库目录 / 读 ws 父目录（含 AK）/ **读别的 run 的 ws / 写别的 run 的 ws** → 全部 BLOCKED；且事后独立核验：别的 run 的 ws 未被写入、它的密文没被抄进被测 ws |
| G 该给的能用 | MCP 工具返回真值、账本有记录、ws 内文件写得进、归档无 AK 泄露 |

**断言口径（owner 2026-08-30 裁定）**：**不查 ws 在不在本项目目录下**。ws 该在本项目下是布局约定、
是必然的，但那不是隔离判据——换个项目名这条断言就失效，压根不是检验器该管的事。只查
**每个 ws 独立** 与 **agent 只在自己 ws 里干活、互不干扰**。

**实测结果**：`deepseek-v3.2` 与 `bailian/glm-5.2` 2026-08-17 全过（当时 19 条）；
2026-08-30 按新口径重写并复跑 `deepseek-v3.2`，**25 通过 / 0 失败**。

**08-25 记下的"F 项从未在生产布局上跑过"已闭合**：run 根改到与生产同一条码路的
`.bench_runs/_verify/`（放哪儿不影响任何断言，就图走同一条码路）。跨 run 那两条不只信 agent
自报——翻轨迹它**真的调了** `Read <另一个run>/ws/secret.txt` 与 `Write <另一个run>/ws/INTRUDED.txt`，
两次都收到 "requested permissions … but you haven't granted it yet"；事后那个 run 的 ws 仍只有
`data`+`secret.txt`，全盘无 `INTRUDED.txt`，密文 `OTHER_RUN_SECRET` 不出现在被测 ws 的任何产出里。
**自检产物开跑前清、跑完不清**——FAIL 时那些产出就是回查证据。

> 一个仍然成立的观察：曾把自检 run 根误设在 `src/probe_headless/logs/` 下，那一次
> **F 组五项尝试仍全部被拒**——说明支柱2/3（`--tools` 与 `--allowedTools`）不依赖支柱1 就能生效，
> 三根支柱是叠起来的双层防护。但支柱1 不可省：当初 `ESCAPED.txt` 那次真逃逸，
> 出自 ws 放在 `cases/<case>/runs/` 下、把整个仓库带成了受信目录。

### 维护纪律

claude code 升版会加新内置工具。`run_agent()` 返回 `n_tools`，
**每个 run 都要核对它等于"内置工具数 + MCP 工具数"**——不等就是有新工具漏进来了。
这次就是靠这个数（23 vs 4）发现问题的。

### 启动命令（`run_case()` 实际拼出来的）

```bash
CLAUDE_CONFIG_DIR=<run>/.cfg \
ANTHROPIC_MODEL=<model> \
claude -p "<prompt>" --model "<model>" \
  --output-format stream-json --verbose \
  --tools "Read,Write,Edit,Grep,Glob" \
  --allowedTools "mcp__matlab__<领域工具>" \
  --disable-slash-commands \
  --mcp-config <run>/mcp.json --strict-mcp-config \
  --permission-mode acceptEdits
# cwd = <run>/ws（仓库外），stdout → <run>/trace.jsonl
```

**四个坑写在这里以免重踩**：
1. `--allowedTools` 里绝不能出现 `Read`/`Write`/`Edit`；
2. 不用 `--safe-mode`（会禁 MCP）；
3. 没有 `--settings`、没有任何 deny 规则；
4. **`tools` 必须传 list**——传字符串不报错而是默默算错：
   `",".join("mcp__x")` 会逐字符拆开，导致**所有工具调用被拒**，
   同时 `len()` 把字符数当工具数→ 误报 `tool_leak`。已实测踩过，
   现在 `run_case()` 开头有 `isinstance` 断言拦住。

**不要手写这串参数**——一律调 `iso.run_case()`，只在一处维护。

**不设 `--max-turns`**：预算用完工具会拒绝再测，agent 自然停下交答。

### 批量启动

```bash
# 统一入口：model 池 × 轮次，并发与模型池都从 ws_isolation 读，不在脚本里写死
python src/probe_headless/sweep_ws.py <runner 脚本名> <轮次数> [轮次前缀]
# 例：6 模型 × 5 轮 = 30 run，轮次标 r1..r5
python src/probe_headless/sweep_ws.py ws_runner_dopant.py 5 r
```

**并发固定为 `iso.MAX_WORKERS`（=4）**。一个 run = 一个 claude 进程（实测各占 300–400 MB）
\+ 一个 MCP server 子进程；并发失控不是限流问题而是**本机资源**问题。
旧的 `sweep_dopant*.py` 写成 `max_workers=len(jobs)`（=20），已删除。

轮次外层、模型内层下发 → 同一时刻并发的几个 run 落在不同模型上，
摊薄单模型被提供方限流的风险（实测见过 `MPE-429 模型提供方限流`）。

**两个必须看的报警字段**（每条 run 的输出里都有）：

| 字段 | 含义 | 处理 |
|---|---|---|
| `api_error: true` | 基础设施失败（限流/超时/网关），workspace 里有 `api_error.json` | 判分时**整条剔除**，不算能力 0 分 |
| `tool_leak: true` | 工具暴露数 ≠ 预期，workspace 里有 `tool_leak.json` | **本批结果不可引用**，sweep 会自动停批 |

## §4 工具面（不多不少）

| 类别 | 给什么 | 为什么 |
|---|---|---|
| 领域工具（MCP）| 如 `measure_tc`（做实验）、`search_db`（open 档查库发现）| 只提供必要的外部观测手段，推理全归 agent。真值只有 MCP server 子进程能读（不受 agent 权限约束）|
| 文件读写 | `Read` / `Write` / `Edit` / `Grep` / `Glob` | **故意放开**——agent 必须能落盘迭代、查自己笔记，这才是 agent。靠支柱1（workspace 在仓库外）限制它们只能在 workspace 内生效 |
| 其余内置工具 | **不暴露**（`--tools` 里不列）| 不是“禁止执行”而是“不存在”。`Bash` 可 cat 真值/自算、`Skill` 能联网、`Task`/`Workflow` 能起子 agent——全部不进暴露集 |

工具档随难度配：basic 只给最基本的；some/enough 才追加便捷工具（**便捷工具清单待困难档失败分析后导出，不预设**，ADR-0026 §3）。

## §5 防真值泄露

- 真值放 `artifacts/ground_truth.json`，它在仓库内，而 workspace 在仓库外——claude code 原生就把 cwd 外的路径全拦（支柱1），无需任何 deny 规则；
- 真值只有 **MCP server 子进程**能读（它不受 agent 权限约束），按题意返回受控信息（如 `measure_tc` 只对已合成样品返 Tc）；
- 判分**不信 agent 自报**：真值一律来自离线 `ground_truth.json`，测量次数从工具账本数。

红队验证（`verify_isolation.py` F 组）实测确认：让 agent 直接 `Read <真值绝对路径>` → BLOCKED。

### 6.0-pre 原子问题的判分口径：只判最终答案的多个指标，**不专门衡量中间结果**（owner 2026-08-22 澄清；综合分 08-25 降为记录量）

这一条先于 §6.0，因为它决定"我们到底在判什么"。**容易被 `goal.md §1` 的项目级表述误导**：
那里写的是"不只看最终分子对不对，更看它寻找分子的过程对不对"——那是**项目级雄心**，
**不是当前原子问题的实际做法**。

**原子问题的实际口径**：

> 把**最终答案**分成若干个指标分别打分。
> **没有任何一项去专门衡量中间结果。**
>
> **加权合成的综合分只是记录量（08-25 改）**：判这题成不成立、判模型强弱，
> 一律看**单个零超参的离散判别关**，不看综合分。理由见 `BENCH_SPEC.md §4 闸4`——
> 权重就是旋钮，换一批模型要重调 ⇒ 测的是旋钮不是能力。

以 `case_dr_qed_01` 为例，三个指标全部读自最终 `answer.json` 的固定 key。
⚠️ **这张表现在是反面例子**，权重列保留只为留痕：

| 指标 | 读哪个 key | ~~权重~~（已降为记录量） | 实测下场 |
|---|---|---|---|
| 外推精度 | `target_qed` | ~~0.5~~ | 尺度靠 tol→scale，含超参 |
| 联合约束满足度（owner 定义的"中间值"） | `lead_mol_id` 逐条对照三约束 | ~~0.3~~ | 与 `lead_qed_measured` **54/54 run 完全共线**，等于一半权重压在同一个二值协议门上，该门与能力 rho=0.000 |
| 实测值一致性（堵背答案） | `lead_qed_measured` | ~~0.2~~ | 同上 |

（同类留痕：`layer_01` 的 0.9·`cp_tc`+0.1·`cp_layer` 把唯一有信号的关压到 1/10。
两例都说明：**权重一旦可调，结论就是调出来的**。）

**账本（`tool_calls.jsonl`）的作用是"门"，不是过程分**：它只用来验证"报的实测值确实来自真调用"
（防伪造），以及记录关（`cp_focus_*`）的诊断量。**它不产生任何计分。**

**"中间值"这个词的正确含义**（owner 2026-08-21 定，别误读成"中间步骤"）：
query 里写下若干个小的限制条件，**由同一个最终答案联合满足**，判分时逐条对照——
那些逐条得分就是"中间值"。**它衡量的仍是最终答案，只是拆成了多个角度。**

⇒ **写报告与论文时的纪律**：谈原子问题时**不得声称"我们评过程/评中间产物"**。
真正的过程量评测（路径拓扑、逐步 checkpoint）属链式题与项目后续方向，不在原子问题上成立。
⚠️ **这一条只管原子问题，不许放大成"永远不许声称评过程"**——后者是执行方两次升级出来的，
owner 已于 08-28 撤销：长程任务本来就是若干验证点拼起来，逐站产出关是合法的
（见 `governance/决议_20260828_原子问题定义与长程组装.md` §3）。

### 6.0 交付契约（两条硬规则，先于一切判分口径）

**规则一：agent 在 workspace 里干活，产物落在 workspace。** 不是"回答问题"，是"完成任务
并交付文件"。

**判分与诊断吃两套不同输入，别混**：

| 用途 | 读什么 | 不读什么 |
|---|---|---|
| **判分**（出分数） | 只读 `answer.json` 的固定 key + `tool_calls.jsonl` 账本 | notes.md、trace、模型在对话里说的话 |
| **诊断**（找问题、定该改什么） | **必须读 agent 的全部工作产物与思考过程**：`notes.md`、`trace.jsonl`、workspace 里它写的其它文件、工具调用顺序 | — |

**为什么诊断必须看思考过程**：光看分数只知道"错了"，不知道"为什么错、当前配置下该改什么"。
三件事只能从思考过程里找依据、不能靠猜分数：

1. **失败归因**——是没看懂题、工具没会用、预算花错地方，还是推理方式不对？
   （实测例：三个模型都写对了"n=3 有峰后下降"，但下降段按直线外推 ⇒ 问题在外推方法，
   不在题目难度，所以不该动预算。）
2. **判断配置该不该改**——预算是不是真瓶颈、题面有没有歧义、工具语义有没有说清。
   （实测例：赢的 run 把 8 次预算用满且用得有道理、弱的只用 5 次就自停 ⇒ 瓶颈是推理
   不是预算，预算不动。）
3. **按 ADR-0026 §3 从 basic 档的失败模式导出便捷工具**——便捷工具不预设，
   只能看 basic 档实际卡在哪里才知道该给什么。

**规则二：凡是要判的量，必须是 `answer.json` 里一个固定 key 的 value。**
judge 一律按 key 取值，**禁止从自由文本里抽答案**——包括 `notes.md`、报告体段落、
模型 stdout、trace 里的自然语言。

**为什么这条不可让**：自由文本的措辞每次都不一样（"预计约 0.55"／"QED ≈ 0.55 左右"／
"介于 0.5 与 0.6 之间"），判分器不可能穷尽所有写法。一旦开始抽文本，**判分口径就随模型
措辞漂移**，同一份能力会因为"话怎么说"拿到不同分数，题目也就不可比了。
题面里写"交一份报告"就是违反本条——**要判的每个量都必须在题面里给出确定的 key 名**。

配套要求：

| 项 | 要求 |
|---|---|
| 题面 | **不靠提示词讲格式**：`answer.json` 由 runner **预先放进 workspace**（合法 JSON、字段齐全、值留空），题面只指向该文件说"填值、别改结构"。模板用 `answer_schema.blank_answer()` 从 `answer_schema.json` 生成 ⇒ 与判分器读的字段同一真源、不会漂移 |
| 预放模板的理由 | owner 2026-08-21 裁定。格式只写在提示词里，模型可能扫过去——实测出现过**答案内容对、末尾多写一个花括号**导致 JSON 坏判 0 分。那种 0 分测的是"会不会数括号"，不是科学推理，属 harness 不稳。摆一份待填文件后模型只改值不碰结构，**这时它还填错，才确属它自己的问题** |
| 空模板视同未作答 | 模板原封不动交回来 = 没干活，`classify()` 必须判 `no_answer`（计 0 分入分布）。否则"文件存在"会让零工作蒙混过关 |
| 字段声明 | `artifacts/answer_schema.json` 声明字段名、类型、是否必填 |
| 校验 | `preflight.py` 闸门4 检查"judge 用到的字段均已声明"，不过不许开批 |
| 缺字段 | 按 §6.1 记 `contract_mismatch`／`bad_json`，**计 0 分入分布**（不是剔除） |
| `notes.md` | **不参与打分，但诊断时必须读**（见上表）。题面必须要求 agent 边做边写——它不写，事后就无从归因 |

**唯一允许的解析**：某个 key 的 value 本身就是结构化标识（化学式、组成式、分子 id），
可以按固定格式解析它内部的结构——例如从 `"O7Cu3Ba2Pr0.150Gd0.850"` 里取 Pr 含量。
这与"从自由文本里找答案"性质不同：前者格式由真值侧定义、可枚举；后者由模型措辞决定。

### 6.1 失败分类（口径 B，不可修改）

| 类型 | 标志 | 处理 |
|---|---|---|
| **基础设施失败** | `api_error.json` 存在（限流/超时/网关错）| **整条剔除**，不计入分布 |
| **工具面不干净** | `tool_leak.json` 存在（暴露工具数 ≠ 预期）| **整条剔除**，结果不可引用 |
| **能力失败（协议）** | 没写 `answer.json` / JSON 坏 / 字段缺 | **计 0 分**入分布 |
| **能力失败（答错）** | 交了但数值偏差大 | 按公式正常打分 |

- 把前两类混进后两类 → 把限流算成能力差 → 系统性压低请求数多的一侧（open 要翻页）→ 伪造 fixed>open 假效应；
- 把后两类剔除（口径 A）→ 生存者偏差，"不敢交卷反而不扣分"。**census_01 曾靠剔 3 个零把 0.598 变成 0.640，错报达标。**

**实现分工**：`api_error.json` 与 `tool_leak.json` 由 `iso.run_agent()` 自动落盘；
各 case 的判分器必须在 `validate()` 里认这两个文件并剔除。
参照实现：`case_sc_dopant_01/judge_dopant.py`（已改完并验证）。

### 6.2 给分形态按关的身份分开定（**08-25 改**）

> ~~原文：判分必须连续给分，不留 0/1 二值关卡。~~ **已被 `BENCH_SPEC.md §4 闸4` 推翻**——
> 平滑给分要靠 tol→scale，那是旋钮；实测三题里含超参的检查点无一与独立能力排序对齐。

| 关的身份 | 给分形态 | 理由 |
|---|---|---|
| **判别关**（进总分、决定这题成不成立） | **必须离散可验证、零超参**（对了就是对了，如"最优层型是不是 Cu=3"） | 闸4 硬要求；连续化必然引入 tol/scale，换一批模型就要重调 ⇒ 测的是旋钮不是能力 |
| **记录关**（`NOT_IN_MEAN`，只作诊断） | 可以连续给分 | 不进总分，旋钮不影响结论 |
| **门**（`GATES`，乘性） | 二值 | 本就是通/不通 |

**严禁按结果回调容差**（MEAN_TOL 已固化）——这一条不变，且对记录关的 scale 同样适用。

### 6.3 判分器必须自己能跑

判分器 `__main__` 必须能直接执行出完整结果。**曾出现 `judge_census.py` 打印早已删除的字段
导致 `KeyError` 崩溃、那组"达标"数字只能靠临时脚本产出——等于无法复现，视为没做。**

## §11 验收判据与定稿流程

### 11.1 判据主体是**相对关系**，绝对值只是参考区间

owner 定调（2026-08-18）：「不必局限于 credit，只要分数大致符合预期就好，
最重要的是把相对分数测对」、「两个尺子可以不必定这么死」。

**硬判据（必须成立，且逐批复现）**：

| # | 判据 | 验收方式 |
|---|---|---|
| ② | fixed 优于 open，差值显著 | 置换检验 p<0.05（Bonferroni 按批数校正），**逐批方向一致** |
| ④ | 发现有后果 | open 侧覆盖率非恒 1.0，且低覆盖组分数显著低于高覆盖组 |
| ⑤ | 答案不可背 | 裸答基线 k≥5 明显低于 with-tools |
| ⑥ | 模型区分度 | **逐检查点**看，不看聚合总分（见 11.2）|

**参考区间（不作阻断项）**：fixed 均值 ≈ 0.6–0.8、open 均值 ≈ 0.3–0.6、
最强模型不宜满分。偏离要在文档里说明原因，但**不因此判不达标**。

> 为何放宽（算术依据）：四关等权时「最强模型<0.85」要求四关之和<3.40。而 cpA/cpD
> 对强模型恒为 1.000（都是"测完即可确定"的关）、cpB 也可满分 → 三关锁死 3.0，
> 只剩 cpC（可学天花板 6/7=0.857），最好情况仍是 0.964。即此项在当前题型结构下
> **算术上不可达**，除非把推理关做到不公平。

### 11.2 模型区分度必须看逐检查点，不能看总分

chain_01 三批 n=80 实测：

| 指标 | 总分口径 | cpC 单关口径 |
|---|---|---|
| 模型间信号 | 0.093 | **0.178** |
| 信噪比 | 0.65 | **0.91** |
| 最强vs最弱 | p=0.34 ✗ | **p=0.0002 ✓** |

原因：饱和关（cpA 满分率 96%）把信号稀释掉了。**定稿时必须指名本题的判别性检查点。**

两条配套纪律：
1. **分档必须用身份先验**（外部、任务无关的独立能力估计），不得用同一批数据既排序又检验（循环论证）。
   ⚠️ **"厂商定位"这一先验已被实测否证**（2026-08-24）：被标"强"的 DeepSeek-V3-671B 在外部工具调用基准**垫底**、被标"弱"的 qwen3.5-plus **并列第一**，两组标签名次完全交错、零预测力。
   改用**实测的任务无关排序**做先验，首份见 `refbench_tooluse_FINDINGS.md`（BFCL 工具调用三档分层，glm-5.2 锚点与 SWE-rebench 一致）。
   注意边界：该排序测**单轮函数调用**、非长程推理，只作**独立身份先验**、**不作各题能力真值**。
2. **协议失败不是能力失败**。实测：未交卷 run 逐批递减时，非旗舰模型总分随之
   追平旗舰（deepseek-v3.2 0.770→0.942）——说明那些"区分度"其实是"谁更容易忘写 answer.json"。

### 11.3 定稿流程

硬判据在**两个独立批次**上均成立、且两侧同一判分口径时：

1. 更新两侧 README（含最终数字、判别性检查点、复现命令）；
2. 更新《第一组 case 清单》；
3. `git add -A && git commit`；
4. **参数冻结**：不得再改预算/PAGE_SIZE/容差/产物定义。

### 11.4 检查点三分法：一个关是否计分，由零成本基线实测决定，不由设计意图决定

**为什么要有这条（根因）**：我们按《agent action 全量枚举》挑要测的能力，但那张表
回答的是"科学发现里有哪些推理动作"，**它不回答"这个动作对当代模型是否还构成难度"**。
后者是经验问题，只能实测。设计时把一个已经免费的动作单开一关并计分，该关必然饱和，
后果不是"多一条信息"而是**稀释总分**——§11.2 里 chain_01 的 cpA 满分率 96%，
把最强 vs 最弱的 p 值从 0.0002 拖到 0.34。

所以：**关的取舍必须由实测定，且必须在开满批之前定。**

| 类 | 判定标准 | 处置 | 实例 |
|---|---|---|---|
| **能力关（= 判别关）** | 三条零成本基线都打不满，**且离散可验证、零超参**（`BENCH_SPEC.md §4 闸4`）。⚠️ **原标准"真实小切片上取值有梯度"已删**：要梯度就得连续化，连续化就得挂 tol→scale = 旋钮；且"小切片"通常只有几个 run，不足以断言（坑⑦） | 计入总分 | ⚠️ **原例 `case_dr_qed_01.cp_qed`（6 run 铺开 0.074–0.915）已作废**：该检查点是 v1 的、现判分器里已不存在（今为 `cp_extrap`/`cp_conditions`/`cp_lead_value`），且它本身是 scale 型连续关 ⇒ 按闸4 只能作记录关。**全库目前没有一个合格实例**——这正是要重造题的原因 |
| **记录关** | 任一零成本基线就能打满，或真实 run 上饱和，**或含超参**（scale / 权重 / 候选数 / 预算） | **移出总分**，留在 `details` 里作诊断量 | `dopant.cp3/cp4`（离散网格→阶梯门）；`constraint_02.cp_extrap`；`qed_01.cp_extrap`（tol→scale，08-25 降级）。（旧例 `cp_series` 同属 v1，已不存在） |
| **门** | 不满足则整题归零（不是扣分） | 不计分，只作闸 | grounding（账本里没有成功测量 ⇒ 总分 0）；交卷 |

#### 判定用的三条零成本基线（0 机时，写在 judge 旁的自测里）

1. **裸答基线**：只给题面、不给任何工具结果，直接填答案。**只认实测留痕，不得合成**（见下）。
2. **零工具基线**：账本为空但答案字段完整（"背答案"的极端形态）。
3. **撒网基线**：所有集合关全报、所有数值关填池中位数或量程端点（合成约定全库共用一份，见下）。

任一基线把某关打到 **≥0.9**，该关即降级为记录关。三条基线全部打不满，才允许计分。

#### 这三条基线由代码执行，不靠自觉（2026-08-25 工具化）

本节自 08-22 写下后**一直只是文档**：全库判分器里检索不到一处基线自测，于是
`case_sc_layer_01` 带着一个**裸答就能拿 1.000** 的计分关 `cp_layer` 跑掉 123 个 run，
到跑完复盘才发现"最优层型 Cu=3"是教科书结论。闸门2 的饱和检查救不了这种题——
它要 ≥6 个真实 run 才起判，那时机时已经花掉了。

所以基线改为**判分器的一个函数 + 开批前的一道闸**：

| 位置 | 义务 |
|---|---|
| `judge.py` 的 `baselines()` | 返回 `{"撒网": (total, details), "零工具": ..., "裸答": (total, details) 或 None}`；分数一律由本判分器 `score()` 实算，**禁止手填数字** |
| `preflight.py` 闸门6 | 缺 `baselines()`、裸答取值为 `None`（没留痕）、任一计分关在裸答/撒网 ≥0.9、零工具 `total > 0`（门失效）、或计分关被全部打掉 ⇒ **FAIL，拒绝开批** |

**三条基线里只有两条可以由代码合成**——这一条是本闸自己栽出来的（08-25 当天）：

撒网与零工具**没有自由常数**：整池、池序前缀、池中位数、真值，都由真值文件唯一确定，
换个人来写结果一样。裸答不是这样——它是"一个只会背书的模型会答什么"，取决于先验怎么挑。
执行方给 `dopant_01` 挑了"92 K 线性衰减到 x=0.55"，算出 `cp2_numeric` **0.825**（逼近降级线）；
而同题真跑过的 k=5 裸答**实测最高只有 0.436**。一倍的差距纯粹来自挑的那两个常数。
**判据取决于谁来挑常数，就不是判据**（坑⑨）。故：**裸答只认实测留痕**
（k≥5 真跑、逐条答卷落盘、由该题判分器重判），没跑过就填 `None`，闸门6 判 FAIL —— 如实报缺，
不许合成顶替。全库现状：只有 `naked_baseline_layer_opt.json` 落了逐条答卷，
其余四个 `naked_baseline_*.py` 都只把数字写进 README ⇒ 那些题的裸答一律 `None`。

**撒网的合成约定全库共用一份**（写在 `preflight.gate6_baselines()` 的 docstring 里，
不许按题另挑——按题挑就是拿约定换结论）：集合类字段报整池；有预算的测量花在**池序前缀**；
数值类字段抄实测中位数或量程端点；"选一个最好的"类 id 报测到的最优者；
二值标签一律报肯定的那一侧。于是"撒网打满某关"读作：**顺序暴力测一遍、不做任何推理就满分**。

**这道闸的边界要说清**：它只回答"这关是不是免费的"，**不回答"这题成不成立"**。
`case_dr_triage_01` 三条基线全过（裸答 0.000、撒网 0.167、零工具被门归零），
实测仍不成立——组内 SD 0.151 压过模型间 0.086。**方差那一面归闸门5，两闸不互相背书。**

#### 回填实测：7 道已跑过的题，没有一道当初该开批（2026-08-25）

owner 点头回填后给全部在库题补了 `baselines()`。**结果不是"补完就过"，而是逐题查出病灶**：

| 题 | 免费的计分关（撒网/裸答实测） | 零工具门 | 病灶 |
|---|---|---|---|
| `layer_01` | `cp_layer` 裸答 **0.952**（21 条落盘答卷重判，20/21 命中）、撒网 1.000 | 拦住 | 那正是此前认定"唯一有效判别点"的关 —— 它有效是因为**可背**，见下 |
| `chain_01` | `cpA` 撒网 **1.000** | **失效（1.000）** | 顺序把预算测完报最高峰即满分；`cpA` 本就是"抄测量值"关 |
| `constraint_02` | `cp_objective` 撒网 **1.000** | **失效（1.000）** | `min(1.0, tc/best)` 封顶 ⇒ 报出 123 K 的五元素陷阱反而满分，陷阱只被门拦、检查点却给满分 |
| `satisfy_02` | `cp_excluded` 撒网 **1.000** | **失效（1.000）** | 纯召回率、无精确率惩罚 ⇒ 报整池必满分 |
| `edit_01` | `cp_best` 与 `cp_conditions` 撒网**双 1.000** | 拦住 | ① 真最优 `e08` 正落在池序第 8 位 = 预算 8 之内；② QED 最大者本身满足两条免费约束 ⇒ 三约束不咬人。**两个计分关全被打满 = 这题没有判别关** |
| `dopant_01` | 无（撒网 0.857 / 0.651，过） | **失效（1.000）** | 缺账本门：11 点全填真值、一次不测也满分 |
| `qedgen_01` | 无（撒网 0.000，过） | 拦住 | 唯一逐关全过的题（仅缺裸答留痕）。附带查出：撒网把 anchor 原样交回可让 grounding 三条全过，靠 hit 是独立门才没出事 |

两条横向结论：

1. **零工具门失效是系统性的**（4/7）：这些题的"门"只管字段合法性（元素数、契约），
   不管账本里到底测过没有。**门必须挂在账本上**，否则背答案者拿满分。
   `edit_01`/`layer_01`/`triage_01`/`qedgen_01` 有账本门，就拦住了。
2. **零超参 ≠ 有判别力**（修正 08-25 早先的说法）：闸4 曾拿 `cp_layer` 当"离散可验证、
   零超参"的正面样板，理由是它与独立能力排序显著对齐（rho=+0.812）。现在实测查明
   **它裸答就能拿 0.952** —— 对齐的是**背书能力**，不是工具使用能力。
   零超参是必要条件，**过三条基线才是充分条件**，两道要求都得满足。

`case_dr_qed_01` 是唯一没回填的题：它的 `judge.py` 连同 5 个配置薄壳都在
`governance/sealed/qed01.json` 里有 sha256 逐字节记录（owner 08-23 封存）。
加 `baselines()` 必然改哈希、破封，闸门5 会同时对 6 个格子报警。**破封须 owner 明确点头**
（或走 `tools/seal.py` 重新签封），故挂起不动。

#### 三条配套纪律

1. **降级必须留痕**：judge 里用 `NOT_IN_MEAN` 显式声明，并在注释写明**是哪条基线、
   实测取值多少**。禁止"悄悄不算"——那会让后来人无法判断分数口径变过。
2. **预登记时就要答（§8 配套义务）**：每个打算计分的关必须写清 ① 它考枚举表里哪个
   action；② **哪条基线证明它不免费**。第 ② 项写不出来，就不该单开这一关。
3. **已降级的关不得靠"它有语义价值"复活**。语义价值放 `details` 里同样体现得到。
   只有把题目本身改到该关不再饱和（例如把辨识做难），才能带着**新的基线实测**重新升级。

#### 记录关不是垃圾桶：它的用途是分型

饱和关做不了打分，但做得了诊断。以 `case_dr_qed_01` **v1** 的两关组合为例
（⚠️ `cp_series` / `cp_qed` 均已不存在于现判分器，此处只留方法论）：

| cp_series | cp_qed | 说明 |
|---|---|---|
| 高 | 低 | 系列认对了，但趋势没拟好（当时的主要失败型） |
| 低 | 低 | 系列就认错了，测的是别人的曲线 |

**这也是"多角度验证"落地的正确姿势**：角度用来分型，不一定用来加权。
一个免费的角度不是角度，是格式检查。

#### 口径变更的成本分级（决定要不要重跑）

| 变了什么 | 处置 |
|---|---|
| 关的计分归属、给分公式、失败分类 | **只需重判**，历史 run 可复用 |
| 题面、工具面、预算、真值、隔离机制 | **必须重跑**，历史 run 作废 |

把关移出总分属于前者。`case_dr_qed_01` 的 6 个冒烟 run 就是原样重判的
（fixed 极差从 0.589 拉到 0.841）。

## §12 已知坑

| 坑 | 处理 |
|---|---|
| glm 思考溢出 | 偶尔超时或不写 answer.json → 记协议失败或重跑，不当能力 0 分混入 |
