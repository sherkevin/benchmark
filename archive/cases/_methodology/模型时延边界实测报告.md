# 强推理模型时延边界实测报告

**结论先行：不是模型出问题，是我们的传输方式没设对。** 网关对**非流式**请求有一道
**~310 秒硬性空闲超时**；而这 3 个推理模型做归纳题需要 **数百到上千秒**。
改用**流式（stream=True）**让 token 持续回传、连接不空闲，即可越过这道墙——qwen3.7-max
在流式下**成功跑完，758.3 秒**。

---

## 实测数据（客户端超时统一设 1500s，确保限制来自网关/模型而非客户端）

### A. 基线：简单问题（非流式）——证明模型活着且很快
| 模型 | 结果 |
|---|---|
| qwen-turbo | OK 0.6s |
| qwen3.7-max | **OK 2.8s** |
| glm-5.2 | HTTP 400 @ 4.2s（瞬时，后续流式正常发起）|
| kimi-k3 | **OK 3.9s** |

→ 推理模型在简单问题上**秒级返回**，模型本身健康。

### B. 归纳题（非流式）——复现 504，测出网关墙钟
| 模型 | 结果 |
|---|---|
| qwen-turbo | OK 1.6s（不做长思维链）|
| qwen3.7-max | **HTTP 504 @ 310.2s** |
| glm-5.2 | **HTTP 504 @ 310.2s** |
| kimi-k3 | **HTTP 504 @ 310.2s** |

→ 三个模型 504 时刻**完全一致 310.2s**，说明是网关的固定超时配置，与模型无关。

### C. 归纳题（流式）——关键验证
| 模型 | 结果 |
|---|---|
| qwen-turbo | OK total=1.6s ttft=0.6s chars=223 |
| **qwen3.7-max** | **OK total=758.3s ttft=0.8s chars=90140** |
| **glm-5.2** | **OK total=983.1s ttft=1.2s chars=144403** |
| **kimi-k3** | **OK total=988.4s ttft=4.0s chars=93736** |

→ **三个推理模型流式下全部成功跑完**：首 token 均在 4s 内（连接立即活跃），
总计 758~988s，输出 9~14.4 万字符（海量思维链）。**流式全部越过 310s 墙**。

---

## 为什么流式能解决（机理）

| | 非流式 | 流式 |
|---|---|---|
| 连接上的数据流动 | 模型推理期间**完全静默**，直到全部生成完才回传 | 每个 token 立刻回传，**连接持续活跃** |
| 网关视角 | 静默超过 ~310s → 判为死连接 → 504 | 一直有数据 → 不触发空闲超时 |
| 对推理模型 | 思维链越长越容易被掐 | ttft 仅 0.8s，之后一路吐 |

关键量化：qwen3.7-max 需要 758s，是网关 310s 墙钟的 **2.4 倍**——非流式下必挂。

---

## 各模型在归纳题上的时延画像

| 模型 | 类型 | 归纳题耗时 | 非流式可行性 |
|---|---|---|---|
| qwen-turbo | 非推理 | 1.6s | 可行 |
| qwen-plus / gpt-4.1 | 非推理 | 数十秒内（此前均正常完成）| 可行 |
| qwen3.7-max | 重推理 | **758.3s** | 必 504（需流式）|
| glm-5.2 | 重推理 | **983.1s** | 必 504（需流式）|
| kimi-k3 | 重推理 | **988.4s** | 必 504（需流式）|

**推理模型需 758~988s，是网关 310s 墙钟的 2.4~3.2 倍**——非流式下 100% 挂。

## 直接后果：规则归纳路线解锁

此前判断的"3 个推理模型无法测归纳题"**是错的**——错因是全部尝试（chat/max_tokens/
强制 tool_choice/多轮）都用了**非流式**。正确解法是**流式**。

**下一步**：把 `rule_runner.py` 改为流式，重测这 3 个推理模型，拿到 6 模型完整分布，
即可判定规则归纳 case 是否满足"好 case 四条标准"。

**同时须给单模型墙钟预算**（如 1200s）——用于给"超时未完成"定性，而不再是基础设施缺陷。

## 排除"prompt 过长被截断"这一假设

`prompt_case8.txt` 仅 **28 行 / 1079 字节（约 1KB）**，不存在截断可能。
问题在**输出侧**：模型自身吐 9~14.4 万字符思维链，是输入的 100 倍以上。
即"卡"的从来不是输入长度，而是模型在开放式归纳上的思考时长，
而非流式会把这段静默期当成死连接掐断。

## 为什么 Claude Code 这类工具从不"卡死"

1. **全程流式**——token 持续回传，连接永不空闲，不触发网关空闲超时。
2. **每轮短**——agent 循环里每轮只吐一个简短 tool_call，单轮远低于 310s。
   实证：同样这 3 个模型在我们的链式 tool-calling 任务里各跑 40~55 轮，**从未 504**。
   只有"一次性开放归纳"才会吐十几万字符。

## 后续测试三条规矩（已落实到 rule_runner_stream.py）

1. **一律流式**（stream=True）。
2. **保持每轮短**：能拆成多轮 tool-calling 的就拆，别让单次响应无限长。
3. **设墙钟预算**（当前 WALL_BUDGET=1200s）：超预算才判该模型未完成——
   这是模型能力/效率问题，而非基础设施缺陷。
