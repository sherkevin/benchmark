## ⚠️ 真实并行度（不要以为六条都能立刻全速跑）

**能"同时开六个会话"≠"六条都能全速产出"。** 诚实分档：

| 档 | 线 | 状态 |
|---|---|---|
| **全速**（3 条） | **E3、E2、E1** | 零依赖，Day-1 就能出实质产出 |
| **半速**（2 条） | **E4、E6** | 各有一块零依赖工作可做（E4 的 trace 契约与执行骨架；E6 的跑测管道，可用现有 37 case 调通），**但核心交付要等上游** |
| **先做准备**（1 条） | **E5** | template 骨架需 E2 风格规范 + E3 桩；**case 实例化必须等 E1 后端库**。首日应读文档+做设计，不要空转 |

### 一个结构性风险（分发者必须知道）

**E5 是工作量最大的一条，却排在最后开工**（目标第 4–5 周），而 ICLR 摘要截止 9/18 只剩约 6 周。若 E2/E3/E1 任一延期，**E5 会被压缩到 1 周做最重的活**。

**对策**：① 盯死 E3 的 Day-1 桩与 E2 的风格规范（这两个一到，E5 就能动 template）；② 给 E5 配更多人做路内分片（每 template 一人）；③ 实在赶不上按 T-29 的 Plan B 降级（如 open 类推第二版）。

## 六条线的写作区隔离（**防止并行互相覆盖**）

每份 prompt 的 **§零** 已写死各自的写作区。关键纪律：

- **六条线都禁止写** `TODO.md`、`problems.md`、`task/_并行路总览.md`、`goal.md`、`governance/adr/**`；
- 每条线只写**自己的 `task/E*/` 目录**与**自己的仓根产出物**（各线产出物已核验无交叠）；
- 进度与阻塞写进各自的 **`task/E*/progress.md`**，由**监工统一汇总**进账本。

> 若不做这层隔离，六个 agent 会同时改同三个账本文件并互相覆盖——这是并行最容易崩的地方。

## 关键调度提示（给分发者）

1. **E3 必须最先启动**——它的 `tools_schema.json` 桩同时卡住 E1（建哪些库）与 E4（接什么工具）。要求它 **Day-1 出桩**，不要等实现写完。
2. **E2 第一天就要把专家审题发出去**——外部专家 lead time 最长，晚发就赶不上。
3. **没有一条线应该整体空等**：每份 prompt 里都写明了"哪部分零依赖可先做"与"被卡住时用桩继续 + 立 PR + 标 ⛔️"。
4. **四个曾无人负责的交付物已指派**：`no_path_violation`→E3、专家审题→E2、防污染（设计 E2 / 实施 E5 / 跑测 E6）、T-55 修 SMILES→独立 task（E5 硬前置）。
5. **硬 deadline**：ICLR 2027 摘要 9/18、正文 9/25。排期倒推见 [`../_并行路总览.md`](../_并行路总览.md) §8。

## 六份 prompt 的共同约定（已写入每份，此处备查）

- **唯一纲领是 `goal.md`**——与它冲突时以它为准；认为它有问题**报监工，不要自行偏离**；
- **三条硬边界**：单 agent、一次性输入、hard 中间 checkpoint（不用 LLM judge）；
- **红线**：不出只看终答的退化版、不拿通用 agent 任务凑数、不用 LLM 凭知识硬判、不跳调研直接造题、不用训练分布内热门分子当答案而不防污染；
- **判分零联网**：权威库只在造题阶段用，发布时冻结为离线快照；
- **工作流**：无 task 不动手 → 一个 task 只做一件事 → 范围外发现另立 task（不顺手做）→ 完成写 `report.md` 收口 + 更新 `TODO.md`；
- **契约纪律**：跨线交付必须落**机器可读文件**（schema）而非仅 markdown；冻结参数变更须立 ADR + 立 PR + 通知下游。
