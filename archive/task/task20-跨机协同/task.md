## 一句话目标

> 把「本地写代码、云端跑 agent」这套分工固定成一条可查证的通道，
> 让任何一批实验的命令、环境、原始字段、判分结果、判废理由都能在本目录里追溯到，
> 不依赖任何一端的聊天记录或口头交代。

## 1. 背景

本地 mac 上 `claude --version` 直接 `zsh: killed`，跑批全灭 30 个 run。
排查结论是本地二进制被内网诊断器杀掉，与 idealab 网关、模型、判分链路都无关。
云端开发机上 `claude 2.1.159` 正常，因此实跑移到云端，本地保留零 API 成本的工作
（写 runner、改判分器、设计题面）。

两端一旦分开，最大的风险不是技术问题，是**口径漂移**：

- 本地报「`runs/` 里有 8 个 run」，云端全新克隆后是空的（`cases/**/runs/` 被 gitignore）
- 本地写「`.venv` 里有 mcp（py3.12）」，云端是 py3.10 且 `.venv` 根本不入库
- 同一条 `sweep_ws.py` 命令，两端 HEAD 不同就跑出不可比的结果

本项目已经因为「把基础设施失败当成模型能力失败」伪造过一次 fixed > open 的假效应。
跨机之后这类混同的概率只会上升，所以通道规范必须先立。

## 3. 为什么落在 `task/` 而不是 `governance/` 或根目录

- `ACTION_RULES.md` §2 落点表把「任务定义与完成汇报」定在 `task/{task_name}/`，
  并明写「禁止在根目录或上表之外的位置新建文件」。
- `.gitignore` 里排除跑批日志那几行的注释写着「**结论写进 `task/` 与 `cases/_methodology/`**，
  日志本身不入库」——本目录装的正是结论。
- `governance/` 是决议与审查（ADR）。本目录是**执行层通道**，不是决议；
  真需要决议时另立 ADR，本目录只回链。
- 原先根目录的 `调试机跑批指南.md` 既违反落点表，又自称「本文件是双方协同的唯一口径」，
  与本目录的定位直接冲突。已 `git mv` 移入本目录消除冲突，历史可追。
