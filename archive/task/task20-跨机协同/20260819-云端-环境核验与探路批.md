## 1. 环境搭建：仓库怎么拉的

云端 `benchmark/` 目录原先只有 `.qoder/`，且它的父目录 `/mnt/ai4sci_develop_fast/jingwu`
本身是一个没有任何 commit 的空 git 仓库（应该是误 `git init`，云端没动它）。
直接 `git clone` 会在非空目录里失败，且会嵌套出 `benchmark/benchmark`。
所以走的是 init + fetch：

```bash
cd /mnt/ai4sci_develop_fast/jingwu/benchmark
git init -b master
git remote add origin git@gitlab.alibaba-inc.com:jingwu.jw/benchmark.git
git fetch origin master && git checkout -B master FETCH_HEAD
git fetch --unshallow origin        # 补全历史，便于查 commit
```

结果：HEAD = `8eb52af`（`判分体系通用化 + 全库重判：34%→71.7%`），与本地推上去的一致。
`.qoder/` 保住了，没有嵌套目录。

## 4. 三个发现，按要紧程度排

### 4.1 `sweep_ws.py` 汇总行恒报「交卷 0」——字段名笔误

汇总行印的是 `# 汇总 3 run：交卷 0，api_error 0`，**而三个 run 全都交卷了**。

根因：

- `ws_isolation.py:252` 写出的字段名是 **`answer_exists`**
- `sweep_ws.py:128` 读的是 **`answer_json_exists`**：`n_ans = sum(1 for r in results if r.get("answer_json_exists"))`
- 全仓只有 `ws_runner.py:164` 用旧名 `answer_json_exists`

所以凡是走 `ws_isolation.run_agent` 的 runner（`ws_runner_dopant_open.py`、`ws_runner_chain.py`、
`ws_runner_constraint.py` 等全部），汇总行的交卷数**恒为 0**。

**为什么必须修**：这个数字正是判断「整批是不是全灭」的第一眼指标。一批真的全灭和一批全交卷，
汇总行长得一模一样。改一行即可，云端没动手，等本地认领——改判分/跑批链路的代码归写它的人更稳。

### 4.2 缺 `requirements.txt`，下一台机器还会踩 `mcp` 2.0 的坑

见 §2.1。建议落一份最小的 `requirements.txt`：

```
mcp<2
matplotlib
```

**理由不是洁癖**：`mcp` 已经发生了破坏性升级，`pip install mcp` 在今天装到的是跑不起来的版本。
不钉版本，「换台机器重建环境」这件事就每次都要重新排查一遍——云端这次花掉的排查时间全在这上面。

### 4.3 cp3 / cp4 在 Pr 尾部网格上退化成阶梯门，区分不出模型

这条是探路批最有价值的产出，比环境结论重要。

**现象**：cp1 三个模型全是 `0.857`，cp3 三个模型全是 `0.200`。四关里两关不区分模型。

**cp3 为什么全是 0.200**。cp3 判「预测 Tc≥80K 的最大 Pr」，真值 `HIGH_TH_TRUTH=0.078`，
柯西尺度 `PR_SCALE=0.024`。三个模型的 `predictions` 里，Pr=0.078 那点的预测值分别是
79.9 / 62.0 / 75.6 —— **全部低于 80**，于是三家的曲线里只有 Pr=0.030 一个点过线，
`h` 全部落在 0.030，偏差 `d = 0.048 = 2×PR_SCALE`，柯西分 `1/(1+2²) = 0.200`。三家同分。

其中 qwen3.7-max 那点是 **79.9**，差 0.1K 越线。它答得明显比另两家准（cp2 = 0.651 对 0.527 / 0.533），
但 cp3 一分没多拿。**cp3 的取值只能落在 11 个 Pr 网格点上，实际是个阶梯函数，不是它设计意图的平滑分。**

**cp4 更严重**。cp4 判「仍超导（>0.5K）的最大 Pr」，真值 `CRIT=0.400`，尺度还是 0.024。
但 Pr 网格前密后疏——`0.030 / 0.078 / 0.150 / 0.200 / 0.300` 之后就是 `0.400 / 0.500 / … / 0.900`，
**尾部间距 0.1 是 `PR_SCALE` 的 4 倍多**。后果：

| 模型 | 预测的临界 Pr | 与真值 0.400 的差 | cp4 |
|---|---|---|---|
| qwen3.5-plus | 0.300 | 0.100（一格） | 0.054 |
| deepseek-v3.2 | 0.700 | 0.300（三格） | 0.006 |
| qwen3.7-max | 0.700 | 0.300（三格） | 0.006 |

**错一格就掉到 0.054，错三格掉到 0.006。** cp4 事实上不是「越接近越好」的平滑分，
而是「恰好答对 0.400 才有分」的二值门。这和 task19 复盘里那条「loss 是阶梯不是平滑曲线」
是同一类病，只是这次出在 Pr 轴的尺度上而不是 Tc 轴。

**对本批目的的影响**（本地下发时写明，跑这批是为了验证「尺子② fixed 优于 open」那个
`+0.014` 的差值是真偏小还是样本太少）：cp1 与 cp3 不区分模型，cp4 近乎全零，
**四关里只有 cp2 在真正承载区分度**。若尺度不改，30 run 跑完，`total` 的方差主要来自 cp2 一关，
`+0.014` 这个量级的差值很可能仍然淹在噪声里——**样本量不是主要矛盾，判分尺度是**。

云端只报现象和推算，不擅自改判分器：改 `PR_SCALE` 会动到 fixed 侧的同一份
`judge.py`（open 侧全量转发 fixed 侧口径），影响已入库的历史分数，属于口径变更，
按 `ACTION_RULES.md` 归 owner 裁定或本地设计者定。
