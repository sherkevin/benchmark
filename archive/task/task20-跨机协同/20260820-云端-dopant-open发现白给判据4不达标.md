## 速读

复盘 `dopant_01·open` 那 30 个 d 批 run 的**工具账本**（不是看分数）时查到一个结构性问题：

**它的 `search_db` 免费且不分页，一次查询就返回全库 30 个候选，agent 对目标 Gd 系的
发现覆盖率中位 1.000、29/30 个 run 恒为 1.0——"自己发现候选"这个 open 的唯一考点，
实际上白送。**

后果有两条，都是硬判据层面的：

1. **规范 §11.1 判据 ④「发现有后果」直接不达标**——它要求 open 侧覆盖率**非恒 1.0**，
   且低覆盖组分数显著低于高覆盖组。实测 29/30 恒为 1.0，**连"低覆盖组"都不存在**，无法检验。
2. **这解释了尺子② 为什么只有 0.012（噪声级）**——fixed 与 open 的唯一合法差是
   "候选可见性"，但发现免费又不分页时，open 拿到的信息量和 fixed 给清单几乎等价，
   那个变量实际没生效。之前把这 0.012 解读为"fixed 略优但在噪声内"，
   **真实原因是这道题的 open 配置没有真正成立**。

而且这不是新问题：`第一组case定义与预期_草案v0.1.md` 的「发现 C」早已写明
「open 方案 A 太轻，不加难度：`search_db("Gd")` 一次枚举全部候选，发现步对强模型白给」，
`第一组case定义与预期` 的 open 三条设计铁律第 1 条也明写「**search 必须分页**——
否则一次查询就枚举全库、发现步白给（dopant open 方案A 的死因）」。
**这个已知缺陷一直没修，而我们刚刚还在它上面跑了 30 个 run。**

## 1. 证据（离线复算，零机时）

数据源：`cases/materials/atom/open_basic_tools/case_sc_dopant_01/runs/*__d[1-5]__*`（30 run 的 `tool_calls.jsonl`）。

| 指标 | 实测 |
|---|---|
| 目标 Gd 系规模 | 11 个（全库 30 个） |
| 单次 `search_db` 返回数 | **中位 30、最大 30**（= 一次返回全库） |
| 对 Gd 系的发现覆盖率 | **中位 1.000** |
| 覆盖率恒为 1.0 的 run | **29 / 30** |
| `search_db` 返回字段 | `{query, count, compositions}` —— **无 `has_more`、无 `budget_used`、无分页参数** |

对照我本轮新写的两个 open MCP server（`constraint02_open` / `satisfy02_open`）：
它们的 `search_db` 是 `PAGE_SIZE=4` 分页 + **每翻一页扣 1 个测量预算**，返回
`{query, page, total_matches, results, has_more, budget_used, budget}`。
**两套 open 语义不一致**——同一个"open 配置"在不同题上强度不同，跨题不可比。

### 1.1 横向排查：dopant 是 4 个 open server 里唯一的异类

对全部 4 个 open MCP server 逐个检查发现机制（`grep` 计数，实测）：

| open MCP server | 分页 `PAGE_SIZE` | 翻页扣预算 | 返回 `has_more` | 结论 |
|---|---|---|---|---|
| `ws_mcp_server_dopant_open.py` | **0 处** | **无** | **无** | ❌ **发现白给** |
| `ws_mcp_server_chain_open.py` | 9 处 | 有 | 有 | ✅ 分页且扣预算 |
| `ws_mcp_server_constraint02_open.py` | 7 处 | 有 | 有 | ✅（本轮新写） |
| `ws_mcp_server_satisfy02_open.py` | 6 处 | 有 | 有 | ✅（本轮新写） |

**这坐实了两件事**：① dopant open 的免费全量 `search_db` 是**遗留的"方案 A"**，
不是有意的设计选择——chain_open 早就用分页了，说明项目的既定做法就是分页；
② 修它**风险低**，有 3 个同类实现可直接参照语义（分页 + 共用预算 + `has_more`）。

## 2. 为什么这必须修（不是洁癖）

- 判据 ④ 是 §11.1 四条硬判据之一，**恒 1.0 意味着它永远无法通过**，不修则 dopant open 永远不达标；
- 判据 ② 的 0.012 差值在当前配置下**没有解释力**——不能据此说"这道题 fixed 不优于 open"，
  只能说"这道题的 open 还没真正做出来"；
- 若带着这个缺陷继续铺开，会把"open 白给"复制到后续所有 open 题（第一组是 few-shot 范例，错了会被放大）。

## 3. 已知的设计约束（改的时候必须遵守，来自实测教训）

`第一组case定义与预期_草案v0.1.md` 的三条 open 铁律 + 一条反例铁律，都是踩坑得出的：

1. **search 必须分页**（否则发现白给）；
2. **"发现难度"与"交互预算"是不同旋钮**——分页 4→6 曾使 p 从 0.0022 掉到 0.147；
   测量预算 20→30 曾使强模型 open 反超 fixed。**放宽发现难度会直接削弱 open 效应**；
3. **乘法 grounding 与 open 不兼容**（constraint_02 曾因此均值掉到 0.287），实测锚点应设为独立加法关；
4. 反例铁律：**含"从自己发现的集合里选最优"终选关的题不能直接 open 化**——
   发现不全反而缩小候选池、减少干扰项，会**奖励**发现不全（chain_01 实测 cpD 从 0.350 升到 0.750）。

dopant 判的是"预测整条 Gd 曲线"（不是从发现集里选最优），所以**不触发第 4 条反例**，可以 open 化。
