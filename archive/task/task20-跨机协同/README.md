# 跨机协同规范：云端调试机 ↔ 本地 mac

> **本目录是两端之间唯一有效的指令与汇报通道。** 不在本目录落盘的东西一律不作数——
> 口头交代、聊天记录、别的目录下的文件、commit message 里的交代，都不算指令。
>
> 双方每次开工的第一个动作：读本文件 → 读下面「状态看板」→ 读最新一份对方的文件。

## 速读

- **通道**：`task/task20-跨机协同/`，双向。云端 = 开发机（Linux，`/mnt/ai4sci_develop_fast/jingwu/benchmark`，跑 Qoder CLI）；本地 = jingwu 的 mac（跑 Claude Code）。
- **分工现状**：本地的 `claude` 二进制被内网诊断器 SIGKILL，**跑不了批**；云端 `claude 2.1.159` 正常，**所有 agent 实跑在云端**。本地做零 API 成本的活（写 runner、改判分器、设计题面）。
- **文件命名**：`YYYYMMDD-<云端|本地>-<主题>.md`，按文件名排序即时间线。
- **同步媒介**：GitLab `master`（`git@gitlab.alibaba-inc.com:jingwu.jw/benchmark.git`）。写完必须 commit + push，对方 pull 才看得见。**只写不推等于没写。**
- **节奏**：一次一批，跑完停下来写文件，不自主连跑下一批（承 `调试机跑批指南.md` §7 纪律 1）。

## 1. 一份文件的固定格式

每份文件开头必须是这张表，缺项不受理：

| 字段 | 填法 |
|---|---|
| 日期 | `2026-08-19` |
| 发件方 | `云端` 或 `本地` |
| 类型 | `指令` / `报告` / `裁定` |
| 关联 commit | 写这份文件时的 `git rev-parse --short HEAD`，让对方能对齐代码版本 |
| 需对方做什么 | 一句话。没有就写「无，仅备案」 |
| 回执状态 | `⬜ 待回执` / `✅ 已回执（→ 文件名）` |

**为什么要「关联 commit」**：两端代码版本不一致时，同一条命令跑出的结果不可比。
云端已实测过一次——本地报「`runs/` 里有 8 个 run」，云端全新克隆后 `runs/` 是空的，
因为 `cases/**/runs/` 在 `.gitignore` 里。不写 commit 就查不出这类差异。

## 2. 报告必答四件事

承 `ACTION_RULES.md` §5，一条不许省：

1. **做了什么**（命令原文，可直接复制粘贴执行的那种）
2. **结论是什么**（先写结论，再写论据）
3. **证据在哪**（仓库内相对路径；仓库外的路径要注明在哪台机器上）
4. **遗留问题是什么**（含需要对方或 owner 裁定的事项）

## 3. 跑批报告的附加字段（跑了 agent 才需要）

承 `ACTION_RULES.md` §7 留痕规范。缺哪项，对方就没法离线诊断，只能重跑：

| 字段 | 为什么少不了 |
|---|---|
| 命令原文 + 轮次前缀 | 前缀是数据的唯一分组键，重名会把两批数据混在一起 |
| `git rev-parse --short HEAD` | 结果追溯到代码版本 |
| 模型池 + `MAX_WORKERS` | 模型池变了分数就不可比；并发数决定资源竞争 |
| 逐 run 的 `run_id` / `returncode` / `seconds` / `api_error` / `tool_leak` / `answer_exists` / `tool_calls` | 这七个字段决定一批数据能不能用，见 §5 判废口径 |
| 判分表（逐 run 逐关分数 + n/均值） | 结论的直接论据 |
| 失败 run 的 `trace.jsonl` 尾部 50 行 | 唯一能定位失败原因的东西 |

## 4. 大文件与不入库产物怎么传

`.gitignore` 已排除 `cases/**/runs/`、`src/probe_headless/logs/`、`src/probe_headless/*.jsonl`、
`.venv/`。这些东西**不要想办法塞进仓库**，也不要贴全文。做法：

- **结论与摘要**写进本目录的 md（判分表、字段汇总、失败分类）。
- **原始日志**留在产出机器上，在报告里写清绝对路径 + 机器名，对方需要时点名要哪一段。
- **需要对方复算**时，把能复算的最小输入贴进 md（例如三份 `answer.json` 的 `predictions` 字典），
  而不是整个 run 目录。

## 5. 判批次成败的口径（两端必须用同一套，否则会伪造效应）

承 `调试机跑批指南.md` §6，不重复展开，只强调最容易出错的一条：

| 现象 | 含义 | 处置 |
|---|---|---|
| `returncode: -9` + 耗时 <15 秒 + `tool_calls: 0` | 进程被杀，环境问题 | 整批作废，**不算能力失败** |
| `api_error: true` | 限流/超时 | 判分时剔除，不计入分布 |
| `answer_exists: false` 且耗时正常 | agent 真的没交卷 | 计 0 分入分布（口径 B） |
| `tool_leak: true` | 工具面不干净 | 本批不可引用，停批 |

**别把前两类当成「模型能力差」。** 本项目已因混同这两类而伪造过 fixed > open 的假效应。

## 6. 冲突裁决顺序

最新 accepted ADR > `ACTION_RULES.md` > 本文件 > 本目录内单份报告 > 其他文档。

需要 owner 本人裁定的（取舍、预算、口径认定），按 `ACTION_RULES.md` 的规则登记到
`USER_TODO.md`（U-xx），**不许只写在某份报告的遗留段里**——那样会被埋掉。

## 7. 越界清单（做了就是违规）

1. 一端擅自 `git push --force`、`reset --hard`、删对方分支。
2. 绕过 preflight 开批（`--no-preflight`）。
3. 改了参数不先用 `--probe` 探 3 run 就上满批。
4. 把 `runs/`、`.venv/`、日志文件塞进 commit。
5. 在本目录之外下发跨机指令。
