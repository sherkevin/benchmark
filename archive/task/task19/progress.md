## 过程中发现并修掉的 4 个问题

### 1. 我把"答错"误判成"没答"（我引入的 bug）

`classify()` 里把 `qualifying: []`（空列表）当成字段缺失而拒判。但空列表是模型
**真实作答的内容**（它认为筛选后无材料合格），完全可以判分（F1=0）。

**后果**：20 个本该计 0 分的 run 被从分布里拿掉，均值被人为抬高。
这是"报错话术骗人"的反向版本——把能力失败洗成协议失败。

**修法**：`classify()` 只拦"没法判"（无答案 / JSON 坏 / 契约完全不符），不拦"答得差"。

### 2. 判分器只认写文件交卷，漏了工具交卷（普适性缺口）

`chain_01` 有 11 个 run 目录里**只有 `tool_calls.jsonl`**，答案在 `submit_answer`
调用参数里（旧 harness 范式）。只读 `answer.json` 会把它们当"未交卷"。

**为何这不是历史包裹**：对方的 harness 也可能用工具交卷。契约必须覆盖两种形态。

**修法**：`judge_contract.load()` 优先读 `answer.json`，读不到则 fallback 到账本里
最后一次 `submit_answer`。修完 `bad_json` 那 1 个也被救回。

### 3. 平滑 loss 不该套在"抄测量值"的量上（修正我的默认做法）

`peak_tc` 的 401 个真实答案：**392 个误差恰好为 0**，9 个误差是 4.0 或 34.5~35.0
（选错了峰），**没有一个落在 0~0.5 之间**。

这种量要么抄对、要么选错对象，中间态不存在——给它平滑等于**给"选错峰"的答案发同情分**。

**结论**：平滑 loss 只用于**需要估计的量**（均值、中位数、外推预测）。
`peak_tc` 保持精确比对，容差 0.5 是**报数精度**（真值 1 位小数四舍五入上限），不是拍的。

### 4. 我的闸门自己按旧接口调判分器（第三次自伤）

`preflight.py` 闸门 2 调 `mod.measured_ids(ws)`（旧接口）、且不带参数跑 `__main__`
（新版路径从参数来）。两处都误报成"判分器坏了"。

**修法**：优先用 `judge_one(ws)`，兼容旧接口；跑 `__main__` 时把批次目录传进去。

**这是离线工具第三次在首次运行时误报**（前两次：抽样偏差、门/关混淆）。
已成模式：**离线工具本身必须用已知的好/坏样例验证，不能写完就信。**
