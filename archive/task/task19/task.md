---

## 1. 背景与由来

全项目已跑 **7371 个 run**，但复盘发现只有 34% 能正常判分。逐层排查暴露的问题链：

判分器崩溃 → 幽灵字段（判分器读题面没要求的字段，静默恒 0）→ 一个 case 混了两代题面
→ loss 是阶梯不是平滑曲线 → 尺度用全库规模而非每个量自己的尺度

**根因不是这些 bug 本身，是两件事没做：**

1. 造 query 时没说清"这道题测哪几个 action"——所以题目浅、区分度差时找不到原因
2. 判分器没有统一契约——所以每道题各写一套，错法各不相同

owner 明确纠正：**能力维度不是先定清单再造题，而是造 query 时必须标明测哪几个 action，
两者互相印证**（`research/agent_action_全量枚举.md`：infer 29 个要测 + acquire 9 个 + 固有 6 个不测）。

## 2. 目标（GOAL）

### 2.1 核心问题

1. 现有 6 道 case 各测哪几个 action？说不清的判死。
2. 判分器改成通用版后，历史 run 能判出多少、分数分布是否合理？
3. 哪些 case 能进第一组？

### 2.2 子问题

1. `census` 系（3300+ run）是否真的对不上任何 infer action？若是，它只测"会不会用工具遍历"，
   不测科学推理，不该进第一组。
2. `constraint_02`/`satisfy_02` 的 open 侧零分率 100%（191+343 run），是判分器对不上还是真全错？

**本 task 完成的标准 = 六项全部达成：**

| # | 标准 | 验收方式 |
|---|---|---|
| ① | 6 道 case 每道都有一张 action 归位表（测哪几个 infer/acquire） | `result.md` 里逐题列出，说不清的标"判死" |
| ② | 每道 case 只有一个判分器 | `ls judge*.py` 每个 case 目录只剩 1 个 |
| ③ | 判分器只吃两个路径，不含硬编码 runs 目录 | `grep -c 'HERE.*runs' judge*.py` 为 0 |
| ④ | loss 平滑：柯西型，无硬截断、无尾部退化 | 实测退化为 0 的占比 = 0.0% |
| ⑤ | 尺度按每个量自己导出，无人工拍的容差 | 源码里无 `TOL = <常数>` 用于判分 |
| ⑥ | 历史 run 全量重判，每道题一张分数分布图 | `logs/score_distribution.png` + CSV |

## 6. 约束与约定

- **不盲跑**：先离线诊断（读 `answer.json` / `tool_calls.jsonl`），改完再验证。
- **一次一停**：跑批必须一次一批，跑完停下来报结果，禁止自主连续迭代。
- **修根源不修症状**：每个 bug 要问"为什么会出现"，并加上防再犯的机器断言。
- **结论要有实测证据**：不采信推理，每个数字都要能指到落盘文件。
- **自查四问**（本项目已因此反复推翻结论）：是不是用 tol 凑档？是不是循环论证？
  是不是跑到显著就停？是不是过度宣称？
