## 一、造题第一步：先说清测哪几个 action

owner 定的纪律：**造 query 时必须标明这道题测哪几个 action，两者互相印证**——
不是先定能力清单再造题，也不是造完题再硬套一个能力标签。

依据 `research/agent_action_全量枚举.md`：infer 29 个（要测）+ acquire 9 个 + 固有 6 个（不测）。

**说不清 infer action 的题必须判死。** 实证：`census_01` 跑了 2397 个可判分的 run、
数据干净、尺子②也过，但它要做的三件事（数库里有多少个、数超阈值的有几个、算均值中位数）
**全部是 acquire #29 + 算术**，没有一步需要科学推理。

这解释了一个长期困惑：我一直觉得 census 浅但说不出为什么——
**因为它测的东西根本不在能力清单里**。四把数值尺子全过 ≠ 题目合格。

反过来，**凭印象归位会误杀好题**：我曾以为 `constraint_02`/`satisfy_02` 只测约束推理，
读 README 后发现它们还测 #8 family 归类 + #5 趋势外推，是三 infer 的好题。
归位必须读设计说明，不能凭印象。

## 三、防可背：唯一有效的机制是"必须报出实测派生的中间产物"

这是本项目最贵的一条教训，反复付过学费。

### 无效的做法

**❌ 靠答案难猜**。`constraint_02` v2 只要求交 1 个 `final`，裸答 gpt-4.1 直接拿 **0.97**
——凭"汞系铜氧化物 Tc 高"的教科书常识就猜中 Hg-1201。
`satisfy_01` 同理，裸答最高 0.673、判别性硬关 5/5 全过（满足集 9 个、蒙中率 100%）。
`constraint_01` 是同一个单产物结构，因此**不需重测就可判死**。

**❌ 靠匿名化**。`explore_01` 一度把 Hg→Jc 做等价匿名"救"它，
实测确实见效（turbo/coder 归零、max 从 0.9 掉到 0.658，证明旧梯度是化学记忆）。
但 owner 明确否决：**"材料 benchmark 不做匿名，否则测的是数学不是材料"**。
匿名把材料题变成纯符号搜索。该题最终退役。

**❌ 靠扩大候选池**。命中式判据（报满足集/选最优）在扩池后**分数反而升高**：
`satisfy_02` 池 24→65 时 fixed 均值 0.728 **升到** 0.899；
`constraint_02` 池 24→68 时 0.710 **升到** 0.974。
原因是命中式只要"找对那一个"就满分，池子越大越容易撞见明显最优者。

### 有效的做法

**✅ 多产物 + 实测锚点**。同样答案是 Hg-1201，`chain_01` 要交 5 个实测派生产物，
裸答只 **0.279**。差别不在答案难猜，在**必须报出大量实测派生的中间产物**。

**✅ 工具拒答，逼纯推理**。`constraint_02`/`satisfy_02` 的真最优被工具拒答
（"暂未探测到"），必须先从可测项归纳规律再外推才敢提交。

**✅ 目标不可测（最干净）**。`dopant_01` 的整条目标曲线**没有样品**，
`measure_tc` 如实返回 `sample_available: false`——科学上唯一站得住的"测不到"理由
是没有实物。没有任何绕过推理的捷径。这是最纯的一道题。

**造新题时优先用「目标不可测」机制**：它最难被绕过，且理由在科学上完全站得住。

## 四、判分：loss 的形状与尺度

### 平滑 loss 只用于"需要估计的量"

单项形式：

$$\text{score} = \frac{1}{1 + \left(\frac{\hat{y} - y}{s}\right)^2}$$

柯西型，处处可导、尾部按 $1/x^2$ 衰减。

**不用阶梯 `max(0, 1-|err|/tol)`**：在容差处硬截断。实测真值 41.79K、容差 10K 时，
答 52 与答 120 同为 0 分——"错一点"与"错到离谱"分不开。

**不用高斯 `exp(-x²)`**：尾部衰减太快，2397 个真实答案里有 **3.2% 退化到 0**
（彼此无法区分、导数为 0）。柯西在同样位置给 0.162/0.047/0.020，退化占比 **0.0%**。

**不用拉普拉斯 `exp(-|x|)`**：0 点不可导（有尖角）。

### 但"抄测量值"的量不该套平滑

`chain_01` 的 `peak_tc` 是 agent 直接测出来的：401 个真实答案里 **392 个误差恰好为 0**，
9 个误差是 4.0 或 34.5~35.0（选错了峰），**没有一个落在 0~0.5 之间**。

这种量要么抄对、要么选错对象，中间态不存在——**给它平滑等于给"选错峰"发同情分**。

判据：这个量是 agent **估计**出来的（均值、中位数、外推预测）还是**抄**来的（实测读数）？
前者用平滑，后者精确比对。

### 尺度必须从真值导出，不能拍

| 量的类型 | 尺度 | 依据 |
|---|---|---|
| 计数 | $\sqrt{y}$（该量自己的真值） | 计数的泊松波动 |
| 分布中心（均值/中位数） | $\sigma/\sqrt{B}$ | σ 从真值算、B 是题面给的测量预算 |
| 插值预测 | 边界带宽 / 2 | 只会"取中点"的 agent 的误差上限 |
| 网格位置 | 最小网格间距 | 错一个格点就该扣分 |

**踩过的坑 1**：计数关统一用全库规模 $\sqrt{N}$。
则 `total_count`(真70) 差 5 与 `high_count`(真15) 差 5 同得 0.700，
而相对误差是 7% vs 33%——显然不该同分。必须用**该量自己的真值**。

**踩过的坑 2**：拿 2397 个答案的得分分布去挑参照抽样量（挑了 20）。
那是**按结果回调容差**，规范明令禁止。改用题面给的 `measurement_budget`。

**踩过的坑 3（最隐蔽）**：直接把旧阶梯的 `tol` 当柯西的 `scale`。
两者含义不同——`tol` 是"衰减到 **0 分**的误差"，`scale` 是"衰减到 **0.5 分**的误差"。
直接换会让 `census_02` 均值从 0.468 飙到 **0.784**。
正解 `scale = tol / 2`：在原容差处得 $1/(1+2^2) = 0.2$，
既去掉硬截断，又不把"刚好错到边缘"当半对。

## 五、难度：两端都会毁掉区分度

分数**贴底**和**饱和**是同一个问题的两端，都让区分度消失。

| case | fixed 均值 | 问题 |
|---|---|---|
| `satisfy_02` | **0.108** | 五关全趴底，尺子② 甚至**反向**（fixed 0.108 < open 0.113） |
| `constraint_02` | 0.254 | 偏难，批间极差 **0.721** 波动极大 |
| `chain_01` | 0.757 | 略高于参考区间，但批间极差 0.197 最小、尺子②差 +0.220 最大 |
| `census_02` | 0.631 | 落在参考区间内 |

**造新题的目标区间**：均值 0.5–0.75、批间极差 < 0.25。
绝对带只作参考，硬判据是**方向正确 + 显著 + 批间稳定**。

**关键警示**：饱和关会稀释信号，但**去掉饱和关不一定更好**。
实测 `census_01` 的 `cp_total_count` 满分率 62.2%（看似白送），
但去掉它后旗舰-弱模型差值从 **+0.154 掉到 +0.088**——
因为弱模型连"数清楚有多少个"都做不到（<0.1 占 17.4%），这一关恰恰筛掉了最弱的。
**不要凭直觉删关，要用数据验证。**

### 5.1 均值落在区间里也可能没有区分度：方差比档间差更致命

`case_dr_triage_01` 正式批（120 run）各项指标**看着都健康**：
均值 **0.421**（落在参考区间）、不饱和不地板（0.167–0.833）、测量中位 **8** 用满预算、
零 tool_leak、精确率高（说明模型不乱报）。

**但判据⑥ 不成立**：强档 vs 弱档（身份先验分档）差只有 **+0.069**，
而**组内离散 0.172** —— 按 `goal.md §7.5` 噪声门，差值小于离散度就**不得声称差异**。

根因诊断（过了 125 个 run 的账本）：

| 现象 | 数据 |
|---|---|
| 8 次预算里测中几个合格者（决定召回上限） | 1 个:23 run / 2 个:30 / 3 个:57 / 4 个:11 / 5 个:4 —— **无一 run 测中全部 6 个** |
| 候选选择高度集中 | 热门 `z001999` 105 次、`z002003` 108 次、`z002170` 103 次 / 共 125 run |
| 三个合格者被系统性冷落 | `z002216` 26 次、`z001510` 19 次、`z002730` 14 次 |
| 冷落的原因 | 这三个恰好 **cLogP 偏低**（−1.04 / 0.09 / 0.86），所有模型都按"cLogP 中等偏高才像药"挑 |

⇒ **所有模型犯同一个错**，档间差就被压平了。

**可复用的守则**：

1. **均值达标只是必要条件，不是充分条件。** 还要问：**正确策略与错误策略的收益差，是否大于预期方差？**
2. 开批前就能估这件事：把"正确优先级策略"与"典型错误策略"各算一遍得分，差值 < 0.15 就别开批。
3. **若合格解在某个关键免费线索上分布集中，模型会集体同向犯错** —— 这时档间差必然被压平。
   造池时要让合格解在关键线索上**分布够宽**，否则区分度从设计上就没了。
4. **这种缺陷补样本救不了**：差值不随 n 变大，只是置信区间变窄。要改的是池，改池就得走新预登记。

## 六、判分器的工程契约（对外交付的前提）

**一个 query 一个判分器**，只吃两个文件路径：

    answer.json       agent 的结构化答案（读不到则 fallback 到账本里的 submit_answer）
    tool_calls.jsonl  工具账本，每行 {"tool":..,"args":..,"result":..}

与 workspace 在哪、跑第几次、什么版本都无关。必须实现：

    classify(sub, ledger) -> str | None    失败分类，None 表示可正常判分
    score(sub, ledger)    -> (total, det)  纯函数
    judge_one(run_dir)    -> (total, det, status)
    CHECKPOINTS, NOT_IN_MEAN               声明式元信息

**不要版本号字段**。版本是"我们改过题"的开发痕迹，与"答案对不对"无关，
不该进 `ground_truth.json`。真正的纪律是：**一道 query 一个目录，绝不原地改**。
改了问法就是另一道 query，另开目录、另配判分器。

反例：`census_01` 曾原地换过问法（早期问 `total_count`、后来问 `low_count`，
且 `low+high≠total` 说明是两个不同的量），判分器跟着改，
导致早期 19 个批次约 2278 个 run 全被判成 `missing_low_count`
——看起来像"模型漏答字段"，实际是"这批数据答的是另一道题"。

### 失败分类的话术必须准确

| 分类 | 含义 | 处置 |
|---|---|---|
| `api_error` | 限流/超时，基础设施失败 | **剔除**，不计入分布 |
| `no_answer` | 没交卷 | **计 0 分入分布** |
| `contract_mismatch` | 这份答案不属于本 query | 剔除并报告 |
| 正常 | 可判分 | 计分 |

**只拦"没法判"，不拦"答得差"**。我曾把 `qualifying: []`（空列表）当字段缺失拒判，
但空列表是模型**真实作答的内容**（它认为筛选后无材料合格），完全可以判分（F1=0）。
拒判等于把**答错**洗成**协议失败**，会把 20 个本该计 0 分的 run 从分布里拿掉、
把均值人为抬高。

## 七、离线工具本身必须验证（我付了四次学费）

`preflight.py`（开批前自检）在首次运行时误报了**四次**：

1. **抽样偏差**——按目录名取前 12 个，结果全是强模型，误报两关"100% 满分"。
   修：每个模型分层各取 4 个。
2. **门/关混淆**——把乘性门 `cp_constraint` 当"关"，它 100% 通过是应有行为。
   修：识别不进均值的项。
3. **单样本判饱和**——1 个 run 全对时每关满分率必然 100%。修：样本 <6 不判。
4. **正则过度匹配**——扫全文的 `f"prefix_{` 把判分器构造错误信息的字符串
   （`f"missing_{k}"`）当成字段读取，在 4 道题上全部误报。
   修：只认 `sub.get(f"...")` 上下文。

还有两次是"识别方式依赖源码"导致的：
判分器写成 `gate = ...; total = gate * (...)`（局部变量）就匹配不到；
**open 侧判分器是转发薄壳，文件里根本没有判分源码，怎么扫都扫不到**。
最终改成**声明式**：判分器自己导出 `NOT_IN_MEAN`，工具直接读。

**结论：离线工具必须用「已知的好样例 + 已知的坏样例」注入验证，不能写完就信。**
实践做法：故意注入一个已知缺陷（如把判分器改回读幽灵字段），确认闸门能拦住，再还原。

## 八、开批前的强制闸门（零 API 成本）

`src/probe_headless/preflight.py` 四道闸门，不过不得开批：

| 闸门 | 检查什么 | 成本 |
|---|---|---|
| 1 真值自检 | 列表不重叠、金标准存在且分区正确、唯一性答案真唯一 | 0 run |
| 2 判分器自检 | `__main__` 能跑完、`score()` 不抛异常、每关不恒 0、不饱和 | 1 run |
| 3 方向探针 | 改参数先用 3 run 探方向，方向对了再上满批 | 3 run |
| 4 字段契约 | 判分器读的每个字段都在 `answer_schema.json` 里声明过 | 0 run |

**闸门 4 拦的是一类不报错、只静默算错的 bug**：判分器读了一个题面从没要求过的
字段名（幽灵字段）→ 模型永远不会给 → `sub.get()` 返回 `None` → 那一关**静默恒为 0**。
实例：`constraint_02` 的判分器读 `measured_max_legal_*`（那是 `satisfy_02` 的字段名，
抄的时候没改），题面要 `measured_max_*`，两侧各白掉 1/4 权重，
把 fixed 压到 0.577、open 压到 0.433。我们据此以为"题太难"去调预算调池子，烧掉几百个 run。

**关键设计：闸门 4 不依赖历史 run**（靠 schema 声明），新 case 零数据时同样生效——
而那正是最需要拦住的时候。

### 闸门 5：策略收益差自检（`triage_01` 用 120 run 换来的）

正式批前，**在真值上离线模拟两种策略各能得多少分**：

- **正确策略**：按题目本意的最优优先级去测 / 去选；
- **典型错误策略**：按最容易想到的错误线索去测（如"cLogP 中等偏高才像药"）。

**两者差值 < 0.15 就不要开批。**

为什么必须加这一关：`triage_01` 各项指标都健康（均值 0.421 落区间、不饱和不地板、
预算用满、零 tool_leak），**跑完 120 run 才发现档间差只有 0.069、淹在组内方差 0.172 里**。
而这件事**零 API 成本就能提前算出来**——真值在手，两种策略的得分直接算，
比"跑完才发现没区分度"便宜两个数量级。

**现状**：这一关目前**靠人工执行**（写个脚本在真值上模拟），尚未并进 `preflight.py`。
下一道 case 前应补进去。

## 九、跑批纪律

- **不盲跑**：先读 trace（`answer.json` / `tool_calls.jsonl`）离线诊断，改完再验证。
- **一次一停**：每次只启动一批，跑完立刻停下来报结果，**禁止自主连续迭代**。
  背景：此前自主连跑十余批，全项目累计 7321 run ≈ 610 机时，
  `chain_01` 单题 1455 run 其中 90% 作废——用活体跑批当设计迭代的反馈回路，代价极大。
- **并发 30 可行**（实测 29/30 成功、api_error 1/30、51 秒）。
- **run 目录不入库**（`.gitignore` 已配）：曾有 964 个 run 文件误入库，
  导致 `git add -A cases/` 一下子 stage 22368 个文件，真正的代码改动完全被淹没。

## 十、自查四问（每次算出"好结果"都要过一遍）

本项目已因此反复推翻自己的结论：

1. **是不是用 tol 凑档？** 调容差把模型分开 = 伪造区分度。
2. **是不是循环论证？** 用同批数据既排序又检验。正解：用具名模型 + 身份先验分档。
3. **是不是跑到显著就停？** 必须预先定死轮次再一次性检验。
4. **是不是过度宣称？** 点估计极差不是区分度，要做显著性检验。

实测教训：`chain_01` 曾报"模型排序稳定"，严格检验后 **0/15 配对显著**；
两批数据排序只有 9/15 一致（随机期望 7.5/15）。
