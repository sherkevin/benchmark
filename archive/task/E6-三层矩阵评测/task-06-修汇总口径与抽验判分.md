## 1. 修缓存口径 —— 两个 bug 叠加（🔴 最高）

### 1.1 根因

```
8,533,064（脚本实际输出）
  = 6,094,080（bug A：同一份 usage 里两个等价字段相加 → 翻倍）
  + 2,438,984（bug B：又把 run_meta 的汇总字段加了一遍）
```

**bug A 实证**：`prompt_tokens_details.cached_tokens` 与 `cacheReadInputTokensCompatible` **每条都相等**（`6272`/`6272`、`7168`/`7168`、`8192`/`8192`…），是 idealab 为兼容不同客户端给的同一个数的两种写法。`matrix_summarize.py` L124-127 把它们相加。

**bug B**：脚本先逐次累加每个 LLM 调用的缓存，**又把 run_meta 的 `token_usage.cached_tokens` 加了一遍**。

### 1.2 正确数字

| | 值 | 占 prompt |
|---|---|---|
| **正确口径** | **3,047,040** | **69.8%** ← 多轮对话缓存命中率高，合理 |
| 两字段相加 | 6,094,080 | 139.7% |
| 再叠加 run_meta | 8,533,064 | 186.7% ← 现在报的 |

### 1.3 要做的四条

| # | 动作 |
|---|---|
| 1 | 两个缓存字段**取其一**（建议 `max`，将来某模型只给一个也不漏），**不相加** |
| 2 | **只保留一条取数路径** —— 保留"逐次累加 llm_call 的 usage"（原始数据）；run_meta 的汇总字段**只做交叉校验，不参与累加** |
| 3 | **加断言 `cached_tokens <= prompt_tokens`**，越界报错、不许静默出表 |
| 4 | **加自动对账断言**：汇总跑完自动与 run_meta 逐项比（prompt / completion / cached / runs 四项），差值非 0 报错 |

第 3、4 条是 owner 明确批准的。**理由：占比 139% 这么显眼的数字写进了 summary 却没人拦住** —— 加了断言，同类错误当场暴露。

### 1.4 一处我的更正

我先前说"prompt 也对不上（4,357,438 vs 3,583,315）"是**错的**——那是拿不同时刻的数据比。同时刻重跑对账，**prompt / completion / runs 三项差值全为 0**，只有 cached 一项错。

### 1.5 验收

| # | 断言 |
|---|---|
| 1 | 缓存占比落回 0~1，且与手工复算一致（约 0.698） |
| 2 | 两条断言在位并能拦住越界 |
| 3 | 只剩一条取数路径 |
| 4 | 四项对账差值为 0 |
