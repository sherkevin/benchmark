## 二、依赖图（谁卡谁）

```
E2 (query风格/题量/专家审题) ──────────────────────┐
                                                  │
E3 (tools契约桩 → gateway/no_path_violation) ──┬──┼──┐
                                               ↓  ↓  ↓
E1 (数据集调研) ────────→ E1 (后端库 A/B分层) ──→ E5 (template+case) ──→ E6 (三层矩阵)
                                                  ↑                      ↑
E4 (harness: 契约 → LangGraph薄层 → 真实harness) ─┴──────────────────────┘

T-55 (修SMILES) ─────────────────────────────────→ E5【硬前置】
```

**边的含义（依赖颗粒度——区分"依赖桩"与"依赖完整产出"）**：

| 边 | 依赖的具体产物 | 颗粒度 |
|---|---|---|
| E3 → E1后端库 | tools 清单（知道为哪些 tool 建库） | **仅第二阶段构造需要**；第一阶段"调研现有 benchmark 后端库"**零依赖，可立即开工** |
| E3 → E4 | `tools_schema.json` **桩** | 桩即可，不等实现 |
| E3 → E5 | tools 契约桩 | 桩即可 |
| E2 → E5 | 风格规范（影响 template 怎么写）／题量（影响造多少 case） | **两者阻塞时点不同**：template 骨架只需风格规范 |
| E1后端库 → E5 | 真实后端库 | **仅 case 实例化与 \|G\| 穷举需要**；template 设计不需要 |
| E5 → E6 | 题集 | **仅最终跑测需要**；跑测管道/聚合脚本可用现有 37 case 提前搭 |

**关键路径**：`E3 → E1后端库 → E5 → E6`。E3 的 tools 清单是最早的瓶颈——它同时卡住 E1 的后端库设计和 E4 的接入，**应优先启动**。

## 四、交接契约（跨路的接口约定）

为避免并行返工，跨路交付必须落成**书面契约**，不靠口头对齐：

| 交接 | 交付方 | 接收方 | 契约内容 |
|---|---|---|---|
| tools 清单 | E3 | E1、E4、E5 | tools 数量、每个 tool 的名称/功能/出入参 schema |
| 后端库规格 | E1 | E3、E5 | 每个 tool 的子库：数据量、字段、读取方式、provenance |
| query 风格与题量 | E2 | E5 | 风格硬约束、模板类别数、每类题量 |
| harness 接口 | E4 | E5、E6 | agent 调用约定、trace 输出格式 |
| 题集 | E5 | E6 | case 清单、每个 case 的 template 归属与判分口径 |

## 四点五、契约必须落成机器可读文件 + 先出桩（并行不崩的关键）

**§4 的契约不能只是 markdown——下游无法用 markdown 做校验，只能靠人读人对，这是"并行崩在接口上"的标准剧本。**

| 契约 | 机器可读文件 | 校验方式 | **桩交付截止** |
|---|---|---|---|
| tools 契约 | `dag_poc/tools_schema.json` | 每个 tool 跑 jsonschema 入参/出参校验 | **Day-1** |
| 答卷契约 | `dag_poc/answer_schema.json` | `evaluate.py` 抽取校验 | **Day-1** |
| trace 契约 | `dag_poc/trace_schema.json` | adapter + 校验 | Day-2 |
| 题量/模板数 | `dag_poc/query_spec.json` | case 计数断言 | E2 交付即冻结 |
| 题集索引 | `dag_poc/case_index.json` | md5 冻结比对（T-50） | E5 交付即冻结 |

**先出桩再出实现**：E3 在 Day-1 先给**字段齐全、返回样例为空的 schema 桩**，E1/E4/E5 立刻可基于桩开工，**不必等真实现**。这是打开并行度的钥匙。

**冻结与变更**：契约冻结后变更须**立 ADR + 在 `problems.md` 立 PR + 通知全部下游线**，不得私改。题量、模板数、tools 数、trace 格式四项属冻结参数，**下游在冻结前不得开始 case 实例化**。

## 五、共同遵守的既有约束（不可绕过）

- **三条硬边界**（`goal.md` §3）：单 agent、一次性输入、hard 中间 checkpoint（不用 LLM judge）；
- **五条红线**（`goal.md` §5）：不出只看终答的退化版、不拿通用 agent 任务凑数、不用 LLM 凭知识硬判、不跳调研直接造题、不用训练分布内热门分子当答案而不防污染；
- **判分零联网**：权威库只在造题阶段用，题集发布时冻结为本地快照；
- **工作流**（`ACTION_RULES.md`）：无 task 不动手 → 完成写 report 收口；范围外发现登记为遗留或另立 task，不在当前 task 内顺手做掉。

## 十、认领与阻塞上报

**认领方式**：在自己 task.md 表头把「状态」改为 `🚧 进行中`，填「认领人」（真名）与「认领日期」「预计起止」；同时在本文件 §1 的表格里登记，避免两人撞领。

**被上游卡住时**（并行开发的常态）：

1. **用桩继续，不得空等**——上游的 schema 桩就是为此存在；
2. 在 `problems.md` 立一条 PR 说明被什么卡住；
3. 在 `TODO.md` 把自己那条标 ⛔️ 并回链该 PR。

**跨线同步**：契约冻结前每日 15 分钟对齐接口；契约冻结时开一次评审会，冻结后变更走 ADR。

**DoD（每条路收口标准）**：`report.md` 必须列「本 task 对已冻结契约的改动（无则写"无"）+ 已通知的下游线」。
