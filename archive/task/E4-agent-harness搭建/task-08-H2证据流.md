## 1. 问题（E6 登记 R3，我复验确认）

E6-07 抽验 3 道 × 2 harness，实测：

| harness | llm_calls | prompt | completion | cached |
|---|---|---|---|---|
| H1（3 道） | 15 / 15 / 16 | 207,077 / 387,556 / 210,269 | 4,831 / 11,657 / 8,872 | 118,272 / 244,992 / 156,288 |
| **H2（3 道）** | **0 / 0 / 0** | **0** | **0** | **0** |

H2 的 `_full.jsonl` 里 **llm_call 事件数为 0**（E6 用 meta7 独立复扫，我认这个证据）。

**后果**：三层矩阵第三层（H1 vs H2）在**成本维度上不可比**。H2 只有单元级的 `raw_stream.result.usage` 可看，进不了汇总。

**这条与 PR-55 同源**：当初 E6 之所以写出"H2 回落取 run_meta"那条路径，就是因为 H2 没有逐次证据流。那条路径已按我裁定删掉（只留逐次累加），于是 H2 的 token 就归零了——**归零是诚实的，但缺口摆在这里**。

## 2. 要做的：先判断，再决定改不改

**本任务的第一产出不是代码，是一个有依据的判断。**

| # | 动作 |
|---|---|
| 1 | 查清 H2 链路（claude CLI）**能不能拿到逐次 LLM 调用的 usage**。CLI 的流式输出里有没有每轮的 token 数？还是只有会话结束时的总数？ |
| 2 | 若**能拿到** → 补 llm_call 级证据流落盘，与 H1 同结构（这样两边可比） |
| 3 | 若**拿不到**（CLI 只给总数） → **如实封顶**，不要硬造：在结果表与论文里**明写"H2 成本维度不可比"**，并说明原因 |

**第 3 条是允许的结果，不算失败。** 但有一条硬要求：

> **不得用 H1 的数字代替 H2**，也不得用单元级总数假装成逐次累加值。

理由：ACTION_RULES §7.5 立的初衷是"数字可复算"。一个不可复算的数字比没有数字更坏——它会让人以为可比。

## 3. 判断依据要写清楚

report 里要能回答三个问题（每个都要有实证，不能只写结论）：

1. **CLI 到底给了什么**：贴出一次真实 H2 调用的原始流式输出片段（脱敏后），指出 token 信息出现在哪一层、颗粒度是每轮还是整会话；
2. **补流的代价**：如果要补，需要改哪里、有没有可能影响 H2 的正常执行（**改 harness 有回归风险，这是我最关心的**）；
3. **封顶的影响面**：如果不补，三份结果表里具体哪几列会空、论文里哪句话需要加限定。
