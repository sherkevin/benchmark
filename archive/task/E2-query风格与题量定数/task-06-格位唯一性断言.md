## 1. 缺口：扩量 4 倍，但查重能力为零

我实测：

| 探查项 | 结果 |
|---|---|
| lint 有 `grid` / `cell` / `bin_key` / `capacity_cell` 相关断言 | ❌ **全无** |
| lint 有 `duplicate` / `collision` 查重 | ❌ **全无** |

`check_m9_gt_unique` 管不了这个：它查的是"单题内部 gt 是否唯一"，不是"跨题是否撞格"。

## 2. 要做的两件

### 2.1 格位唯一性断言（主任务）

| 要求 | 说明 |
|---|---|
| 判据 | 同一 `(template_type, target_domain, grid_key)` 三元组在整个 case 集内**只允许出现一次** |
| 生效范围 | fixed 类（类型1/类型2）；open 类走 per-case 配对、不适用 |
| 报错信息 | 撞格时要指出**是哪两道题、撞在哪个格**，让 E5 能直接定位 |
| 批次口径 | **跨批次生效** —— 新造的 90 道要与已有 30 道一起查，不是只查本批内部 |

### 2.2 `grid_key` 字段的契约要你定

现在 case JSON **没有格位字段**，所以先要定它长什么样。你是 `query_spec.json` 的所有者，这个契约归你定，E5 按它落盘。

建议（你可自行调整后写进 `query_spec.json`）：

- 药物侧：`grid_key = [atom_count_bin, logS_bin]`
- 材料侧：`grid_key = [family, tc_band, element_count]`
- 字段类型统一（全整数或全字符串），**避免 `[3, "3"]` 这类比较陷阱**

定完**立刻知会 E5**（它的 task-05 正在造 90 道，越早拿到越好）。
