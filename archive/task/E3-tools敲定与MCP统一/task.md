## 1. 上游诉求（owner 原话）

> "把我们之前调研过的数据集与 mcp server 都看看，合并成同样的 mcp server 的调用方式，敲定 tools 数量（这里的意思是我们最后的 agent 要有调用工具的能力，工具的数量取决于你调研得到的相关文献里他们给 agent 的工具数量，做一个参考，我们现在是 23 个 tools，这里需要产出一个 tools 和 mcp server 的数量调研文档，标注出这些公开已发表的论文里给 agent 用的 tools 的数量是多少，给我们一个参考，然后根据我们具体的任务敲定我们 tools 的数量和每个 tools 的功能以及出参入参）"

## 2. 与 GOAL 的对齐

- **本 task 服务于**：GT-first 反查法**第 1 步与第 4 步的执行手段**——agent 靠 tools 反查性质，判分靠"产物必须被真实工具调用支撑"（§4 可信度支柱 2：验证器查产物不认动作，编造产物要能被工具落地检查抓出）。
- **硬边界关联**（§3）：agent 调工具查数据**不算多轮交互**，是它的工作方式，不违反"一次性输入"。
- **两类任务关联**（§1.5）：**open 发现类要求"只能看 A、gt 在 B"**——这个机制**必须由 tools 的分层设计来实现**（哪个 tool 是 A 源、哪个是 B 源、B 源怎样才不被轻易撞见）。**这是本 task 的设计难点，不可忽略。**

## 3. 子目标与验收（三要素）

| # | 子目标 | 打勾通过标准 | 验证方式 | 红线 |
|---|---|---|---|---|
| 1 | **文献 tools 数量调研** | 统计已发表论文给 agent 的工具数（每条注明论文+venue+工具数+工具清单出处） | 表格可逐条回溯原文 | 只给数字不给出处 |
| 2 | 我方 tools 数量敲定 | 给出最终数量 + **为何是这个数**（对标文献区间 + 我方任务需要） | 有对照依据 | 沿用 23 个而不给理由 |
| 3 | **每个 tool 的契约** | 逐个写：名称/功能一句话/入参 schema/出参 schema/错误语义 | 可据此直接实现 | 只写功能不写出入参 |
| 4 | **MCP 调用方式统一** | 现有分散实现收敛为同一套调用约定（命名、参数风格、返回结构、错误码） | 有统一规范文档 | 各 tool 各写一套 |
| 5 | **A/B 源分层 + 存在性接口** | 按 ADR-0012：A=可查、**B=完全不可查**；须设计 **`check_molecule_exists`**（只返存/不存，**不返性质**）。验收硬标准：**仅用 A 源 tools 穷举求解，无法得到 gt**（可执行验证，非"有专节"即可） | 隔离测试脚本 | 只写设计不做隔离验证 |
| 6 | 与判分的衔接 | 说明每个 tool 的调用记录如何支撑 checkpoint 的"工具落地检查" | 与 `INTERFACE_CONTRACT.md` 对齐 | 工具与判分脱节 |
