## 1. 上游诉求（owner 原话）

> "在此时我们可以构造 query template 了，根据我们之前拿到的 query 构造文档去构造这些 template，构造完之后去根据模板构造对应的 case，但是在这个过程中很显然会出现构造的 case 结构不合适或者 agent 运行之后不符合 check 的格式规范的情况，这时候就需要反过来修改 template，并且积累构造 case 的经验和约束（要为每一份 template 形成一份自己的构造自己 template 的 case 的经验，以及产出一批本 template 的 case，数量满足我们之前 query 模板里定下的要求，这里的 template 应该是包含我之前说的 fixed 和 open 两种模式的，这里的 agent 回复是测 template 构造好不好的一个指标，agent 根据 case 里的 query 去回答问题，然后根据 case 里的 check 点来验收 agent 的回复是否符合标准，但是这可能出现 agent 回复本身的格式不符合预期，某些 checkpoint 设置的有问题或者整个 DAG 有些不妥当等等这些都是修改和优化 template 的重要指标，也是积累构造 case 的经验的一个指标，构造 case 可以使用脚本批量制造也可以你来精细化一个一个构造，取决于后续实现的效果如何，优先还是选择脚本批量，如果效果不好要用手工你来逐条构造，质量是第一位的，时间可以放缓）"

## 2. 与 GOAL 的对齐

- **本 task 服务于**：GT-first 反查法**第 2、3 步的真正落地**（构造专属 query + 模板与 DAG），是**题集本体的产出环节**。
- **两类任务**（§1.5）：template **必须覆盖 fixed 推理类与 open 发现探索类两种模式**。

> ### ⚠️ open 类的定义已按 ADR-0012 更正，务必按新定义造
>
> **不是**"换个源就能查到 B"，而是：**B 完全不可见**，agent 靠 A 中的**线索性联系推理出一个 A 中不存在的分子**，用 `check_molecule_exists` 存在性接口验证（只知存不存在、不知性质）。造题须走 **`goal.md` §2b 五步**，其中第 ④ 步「**可发现性质量门**」是硬门：
>
> - **仅穷举 A 必须拿不到 gt**；
> - **沿线索推理必须能拿到 gt**；
> - 两条任一不成立，该 case **废弃**。
>
> **另注**：已落盘的 `open_discovery/` 模板**属 fixed 类**（约束最优、6cp、评过程），**不是** open 发现类——open 发现类当前 **0 template / 0 case**，须从零建。
- **硬边界**（§3）：所有 checkpoint 判定必须**可执行**（数值容差/集合成员/结构解析/约束函数/状态比对），**不用 LLM judge**。

## 3. 核心工作机制：**agent 回答是"测 template 好不好"的指标**

这是 owner 强调的关键机制——**不是造完就完，而是要用 agent 的真实回答反过来打磨 template**：

```
造 template → 造 case → 让 agent 跑 → 用 case 的 check 点验收回答
                ↑                              ↓
                └──── 反过来改 template ←── 发现问题
```

**哪些现象说明 template 需要改**（owner 列的三类）：
1. **agent 回复格式不符合预期**——说明题面的交付段（D 段）没写清楚要交什么字段；
2. **某些 checkpoint 设置有问题**——判分点不合理、判不出区分度、或误杀正确答案；
3. **整个 DAG 有些不妥当**——依赖关系连错、有跳步空间、或路径过于唯一。

**这三类现象同时也是"造 case 经验"的来源**，必须逐条记录，不能只在脑子里。

## 4. 构造方式：优先脚本，质量第一

| 优先级 | 方式 | 何时用 |
|---|---|---|
| **1** | **脚本批量** | 默认方式 |
| 2 | 手工逐条精细构造 | 脚本效果不好时 |

> **owner 明确：质量是第一位的，时间可以放缓。** 不要为了凑数量牺牲质量。

## 5. 子目标与验收（三要素）

| # | 子目标 | 打勾通过标准 | 验证方式 | 红线 |
|---|---|---|---|---|
| 1 | template 覆盖两类模式 | **fixed 与 open 两种都有** template | 目录可见 | 只做 fixed |
| 2 | template 符合 E2 的风格规范 | 逐条对照 E2 的风格硬约束清单打勾 | 检查表 | 自己另定风格 |
| 3 | **case 数量达标** | 数量满足 **E2 定下的每类题量** | 计数核对 | 少于定数而不说明 |
| 4 | **每 case 可解性已验证** | 出题时**穷举后端库**确认合格集 \|G\| 符合该类型预期（如唯一解类 \|G\|=1） | 有穷举脚本与结果 | 事后才发现无解 |
| 5 | checkpoint 全部可执行 | 无 LLM judge；每个 cp 的判定是数值/集合/结构/约束函数 | 逐个 cp 审查 | 用 LLM judge 兜底 |
| 6 | **agent 实跑验收** | 每个 template 至少跑通一轮 agent，且**三类轨迹区分正确**（金标准全过 / 空转不全过 / 陷阱在特定 cp 亮红） | 实跑结果表 | 只造不跑 |
| 7 | **每 template 一份造 case 经验文档** | 含遇到的问题、改 template 的原因、沉淀的约束 | 每个 template 一份 | 经验只在脑子里 |
| 8 | **防污染（可执行口径）** | ①gt 与候选池经**等价匿名变换**（ADR-0012 §3）②**无工具裸答基线实测**：不给 tools 直接问模型，命中率显著高于随机即判该 case 污染并废弃 | 有裸答基线的实测数字 | 只写"已考虑防污染"而无实测 |

## 7. 已知坑（**都是实战踩出来的，务必先看**）

1. **可解性必须出题时验证**：曾有 3 道题**结构性无解**却直到实跑才发现。**出题时就要穷举后端库确认 \|G\|**。
2. **约束收窄会连带影响**：曾因 mock 库扩容，原本 \|G\|=1 的题变成 \|G\|=8；反过来收窄约束窗口才锁回唯一解。**库一变，所有 case 的可解性都要重验。**
3. **排序类要防 None**：合格集里含性质值为 `None` 的候选会让排序崩溃，需加"该字段非空"约束。
4. **判分器的真实口径与直觉不同**（曾判错三处）：`cp4` 是 `2·tp/(|P|+|G|)`（交 1 个也可能满分）、`cp5` 集合相等即满分、`cp6` 是常数 0.5 而非距离衰减。**改 template 前先读 `evaluate.py` 的实际实现，别凭文档想象。**
5. **`no_path_violation` 至今零实现**——路径验证是"评过程"卖点的核心，**需与 E3 商定由谁补**。
6. **15 条 SMILES 错配影响 12/37 既有 case 的 gt**（T-55）——复用旧 case 前先确认数据已修。
