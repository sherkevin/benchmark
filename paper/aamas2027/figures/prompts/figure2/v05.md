## Design target

This is a timing/data-flow figure, not a prose explanation. Use three horizontal lanes and five time columns. A reader should see at a glance that one selected provider produces one terminal event, the event waits in a pending queue, and only a later release updates the state used by subsequent actions. Use short nouns, symbols, and arrows instead of sentence boxes.

## Visual structure

Columns, left to right: `decision t`; `selected call + terminal record`; `pending D`; `release τ_t`; `first action at or after τ_t`.

Lane 1, `selector / state`: show `$S_t + A_t$` entering a small selector node and producing one highlighted action `$a_t$`. During the pending column, show a grey state rail `$S_t$` continuing through intermediate decisions. At release, show a blue update to `$S_{\tau_t}$`, then the first later action reads the new state.

Lane 2, `execution / judge`: show one selected provider card entering one call, producing `output + status`, then a frozen endpoint judge after termination. Split runtime failure from chemical correctness using separate small badges.

Lane 3, `update / visibility`: show the selected outcome entering a purple pending queue, hidden until `$\tau_t=t+1+D$`, then a blue released event entering the relay updater. Draw no update from an unselected provider. Place a small grey ghost provider card near the decision column with a closed-eye icon and label `not observed`; do not use a large X.

The five columns must be separated by light vertical guides. Use a dashed horizontal phase boundary between action/terminal recording and feedback release. The queue must not block intermediate decisions. Mark `$D=0\Rightarrow\tau_t=t+1$` beside the release column; it must still be visibly after action `$t$`.

## Prompt to copy

Create a clean, publication-ready flat vector swimlane diagram for a top multi-agent systems paper. Use a 1400×560 white canvas, three horizontal lanes and five aligned time columns, one consistent Arial/Helvetica/Inter sans-serif font, flat fills, thin black arrows, and short labels only. This is a timing/data-flow architecture figure, not a numbered tutorial and not a text-heavy flowchart.

Use five column headers from left to right: “decision t”, “selected call + terminal”, “pending D”, “release τ_t”, and “first action ≥ τ_t”. Use three lane labels on the left: “selector / state”, “execution / judge”, and “update / visibility”.

In lane 1, show a small input state node “S_t + A_t” feeding a selector node and one highlighted action “a_t”. Across the pending column, draw a grey state rail “S_t” with two or three tiny grey decision markers labelled “t+1 … τ_t−1”. At the release column, draw a blue update node “S_{τ_t}”; in the last column show “read released state”.

In lane 2, show one blue provider card “one selected provider” entering one grey call node. Connect it to a compact terminal record with two small badges “output” and “runtime status”. Then connect to an amber node “frozen endpoint judge”. Branch runtime status to a grey badge “system failure”; branch a valid return to a small amber badge “chemical correctness”. The judge must be after termination.

In lane 3, show a selected outcome token entering a purple queue labelled “selected-only” and “τ_t = t + 1 + D”. Draw a dashed waiting arrow through the pending column, then a blue token “released outcome” entering a compact relay update node labelled “family residual + provider bias”. Draw a small grey fallback token to a separate node “diagnostic ledger”; it must not connect to the blue relay update.

Near the first column, show at most two pale-grey unselected provider cards with a closed-eye icon and the label “not observed”. Do not draw output values or arrows from these cards. Add a small note beside the release column: “D=0 ⇒ τ_t=t+1; after action t”. Use solid arrows for observed/completed transitions, dashed arrows for waiting/control, and faded cards for unavailable observations.

Use only navy #2E5DA1 for selected actions, relay update, and released state; light grey #B8C0CC for old/frozen/baseline state and unselected cards; amber #D99000 for terminal record and endpoint judge; muted purple #6B4C9A for pending queue; black text; white background. Use shape and line style as redundant encodings so the figure remains readable in grayscale.

Do not draw a vertical six-step checklist, long subtitles, a large crossed-out output box, a circular instantaneous-learning loop, a second provider call, refusal, escalation, current-action feedback, an arrow from unselected outputs, a system-wide pause during pending D, gradients, 3-D, drop shadows, decorative cartoon characters, fake metrics, or tiny prose.

## Negative prompt

Avoid “release → decision t+1” for positive D, avoid “only next decision reads it”, avoid merging terminal judge with the queue, avoid connecting runtime failure to chemical correctness, avoid mixing lane meaning with color meaning, and avoid poster/dashboard styling.
