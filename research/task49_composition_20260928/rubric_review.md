# 三份 v003 评价标准的组合贡献与闸门逻辑审查

- 审查日期：2026-09-29
- 审查对象：`docs/研究主线/生效/评价标准/` 下三份 v003
- 性质：只读审查记录；不修改生效标准、不修改故事线、方法论或 benchmark 主文档。
- 目的：检查标准是否能严格筛查论文质量，同时避免把“组件来自已有工作”误写成“组合不能构成贡献”。

## 1. 结论

v003 已经把问题契合、信息边界、证据链、段落组织和可复现性写得很细，但有五处逻辑需要在下一个版本修正，否则标准会反向阻塞主线：

1. 三份文档的硬门槛表把许多“通过条件”写成了正向问题，却规定“为是直接失败”。这会把满足定义、无泄漏、可复现等正确状态判成失败。
2. 故事线 H4、S4 及方法文档末尾对 backbone/loss/名称的否定措辞，容易被执行成“组合不能是创新”。这不符合用户已确认的策略，也不符合审稿人按整体贡献判断的方式。
3. 动态标准混合了两种动态性：反馈到达后更新，以及 provider/version/菜单随时间变化。若不区分，固定菜单上的实时更新会被误判为“不够 dynamic”。
4. benchmark 的 confirmation 既是通过分数要求，又是开放 confirmation 的前置条件，形成阶段上的循环依赖。
5. 评价标准中的内部防守语句与论文正文的正向叙事没有分层标记，后续可能把“内部不把重命名当贡献”原样带进论文。

建议保持 v003 的严格度，但把硬门槛改成显式 `PASS/FAIL`，将贡献评分从“组件是否新”改成“整体是否针对问题形成必要且可验证的机制”，把 confirmation 拆成冻结前资格门和冻结后证据门，并在标准中明确内部评语不得直接复制到论文正文。

## 2. 逐条问题

### 2.1 硬门槛正反问反转

三份文档均有同一结构性问题：

- 故事线 H1 写“对象是否属于选定 AAMAS area，且 agent 有不可替代作用”，H2 写“是否存在具体失败”，H5 写“每个主张是否有证据”；但第 3 节写“任一项为‘是’，直接不通过”。
- 方法论 H1 写“输入、动作、反馈……是否都有可执行定义”，H2 写“是否严格看不到泄漏”，H3 写“公式和实现是否一致”；同样会把正确状态当作失败。
- Benchmark H1–H10 也都是“来源是否固定”“规则是否公开”“是否独立”“是否共用输入”等正向条件，却规定“为是直接不通过”。

这不是措辞小问题，而是会让自动评分表、人工评分和未来脚本产生相反结论。最低修改方式是把每行拆成两列：`PASS 条件` 与 `FAIL 触发条件`，评分只允许填写 `PASS/FAIL/UNKNOWN`；或者把问题全部改写成“是否缺少……”“是否发生……”。推荐前者，因为它保留检查对象的自然表述，也避免双重否定。

### 2.2 “组合不是创新”的隐含一票否决

当前容易被误读的句子包括：

- 故事线 H4：“是否改变了问题中的信息、状态、目标或机制，而不只是换 backbone、loss 或名称？”
- 故事线 S4 的 1/0 分锚点：“只是 backbone/loss/命名变化”；“被最近邻完全覆盖”。
- 方法文档末尾：“普通 SGD、Bayesian posterior、PILOT 或 LinUCB……没有新增可观测信息或可识别动态事件时，不得把它们更名为动态 JEV 创新。”
- 主故事线中把这些组件写作“不单独算创新”。

内部应当防止“换名即创新”，但不能把“组件已有”当成组合贡献的否定证据。AAMAS 审稿人通常评价的是完整问题—机制—证据链：新的现实约束、模块之间的接口/不变量、整体收益、成本或适用范围，都可能使一个组合成为可发表贡献。组合贡献需要被证明，而不是被预先排除。

建议把 H4 改成条件式：

> 如果论文只能指出组件名称变化，无法说明完整组合针对目标失败改变了输入/状态/目标/计算，也没有机制级消融或交互收益证据，则 FAIL；组件已知本身不触发 FAIL。

建议把 S4 改成“整体贡献与必要性”，增加以下评分锚点：

- 4 分：明确一个统一接口或不变量；每个组件对应一个问题环节；完整组合相对最佳单组件/最近邻在预登记主指标、成本或覆盖范围上有可复核的交互收益，并有反例或边界。
- 3 分：组合与问题一一对应，至少一个机制消融支持必要性；收益或边界证据有局部缺口。
- 2 分：组合可运行且有直觉，但没有区分组件贡献与整体效应的证据。
- 1 分：模块串联，因果链主要靠命名或事后叙述。
- 0 分：组合与任务无关、泄漏或结果不能由日志恢复。

可增加一个内部但不必强制单一数值的交互证据：

$$\Delta_{\mathrm{int}}=U(A+B)-\max\{U(A),U(B),U(\mathrm{best\;single})\}.$$

其中 $U$ 必须在实验卡中预先定义为主要任务 utility；若交互收益不显著，也可以凭借更低延迟、少调用、扩大覆盖或清晰的新约束取得 3–4 分，但必须把收益类型写清楚，不能靠堆模块数量得分。

### 2.3 动态 JEV 与 provider drift 没有分层

当前方法 M10 和 benchmark B7 把动态事件写成 arrival、retire、version shift 或环境变化等实例。它们适合“动态 provider pool”主张，却不等于“实时学习”的唯一形式。

本项目至少有两种动态性：

- **反馈动态性（主线必需）**：每次调用后的 selected-only correctness 在延迟释放后进入状态，更新后影响下一次选择；固定 provider 菜单也可以满足这一点。
- **环境动态性（扩展主张）**：provider 到达/退出、版本切换、端点或分布变化，使最优动作本身随时间改变。

标准应当要求论文明确声明主张属于哪一类。若主张只是实时更新 JEV，M10/B7 的通过条件应允许反馈释放和状态变化满足 dynamic；provider drift 作为 E4 压力实验或“dynamic tool pool”额外 claim。只有在正文明确声称“动态 provider/version pool”时，arrival/retire/version shift 才能成为硬门槛。

建议新增字段 `dynamic_scope ∈ {feedback-adaptive, environment-nonstationary, both}`：

- `feedback-adaptive`：必须有事件时钟、selected-only delayed label、单事件 update、决策前可见状态变化和固定菜单对照。
- `environment-nonstationary`：在上述基础上增加预登记的 arrival/retire/version/shift 和相应恢复或遗忘指标。
- `both`：两组证据都要有。

这样既严格检验“实时”，也不把没有被论文声称的 provider drift 强加为必做实验。

### 2.4 confirmation 的阶段循环

Benchmark v003 的通过条件要求 E1–E6 全部完成，B15 的 3–4 分又要求 confirmation receipt；但“开放 confirmation”本来要求方法、菜单、阈值、epoch 和 baseline 先冻结并通过内部资格门。若没有分阶段定义，团队会陷入：要通过 benchmark 才能开 confirmation，而要有 confirmation 才能通过 benchmark。

建议把评分状态拆为两个明确阶段：

- **Stage A：冻结前资格**。只检查 truth、label、split、provider lineage、信息公平、baseline contract、日志和 runner。输出 `ELIGIBLE_FOR_CONFIRMATION` 或 `BLOCKED`。此阶段不使用 confirmation 标签，不要求 B14/B15 的 confirmation receipt。
- **Stage B：冻结后确认**。方法、菜单、epoch、阈值和 baseline 一次冻结后，读取 confirmation；只写入独立 receipt，不能回流训练或调参。完成后才给 B14/B15 的最终分数和 `CONFIRMED` 状态。

分数应有两套门槛：`pre_confirmation_score` 与 `post_confirmation_score`。前者决定能不能进行一次确认实验，后者决定论文能否把主结果写成确认结果。任何阶段都不能用总分抵消 H1–H10 的 FAIL。

### 2.5 评价标准和论文正文的语言层级

标准里“不可把普通算法更名为动态 JEV”“组合不自动算创新”是内部审查语言，用来防止自欺；论文正文应写正向的完整贡献：我们把哪些已知能力放进了什么新的信息合同/更新流程，为什么它们的接口形成了一个针对实际失败的统一机制，在哪些消融和边界上成立。

建议在三份标准的开头增加固定提示：

> 本文件中的“组合、重命名、组件已知”等词是内部审查标签，不是论文措辞。论文只写经过证据支持的正向机制、与最近工作的可检验差异和适用边界；不得把内部防守句子复制进正文。

同时，Story S4 和 Method M5/M8 应要求“贡献类型”字段：`problem setting / mechanism synthesis / interface or protocol / theory / empirical evidence`，允许多项联合，但每一项必须有对应证据。这样可以把“创新”落在整体贡献类别上，而不是要求每个子模块都原创。

## 3. 最小 v004 修改清单

不改变当前研究目标、不推翻已确认的创新候选，只改标准的判定逻辑：

1. 三份 H 表统一加 `PASS 条件`、`FAIL 条件`、`证据路径`，删除“正向问题回答是即失败”的歧义；评分表统一使用 `PASS/FAIL/UNKNOWN`。
2. 将 H4、S4、M5/M8 的“组件/名称否定”改为“整体组合是否针对问题形成必要机制”的检查；明确已知组件可以通过，前提是接口、不变量、交互收益或额外覆盖有证据。
3. 在故事线和方法论的评分表加入 `contribution_type` 和 `integration_gain`；允许 gain 来自准确性、可靠性、调用成本、延迟、覆盖范围或可审计性中的预登记目标。
4. 将 dynamic scope 拆成 `feedback-adaptive`、`environment-nonstationary`、`both`；固定菜单上的延迟反馈更新可以满足第一类，provider drift 仅在第二/第三类成为必需。
5. 将 benchmark 确认流程拆成 `ELIGIBLE_FOR_CONFIRMATION` 与 `CONFIRMED` 两阶段；E6/B15 的 receipt 不再作为开放 confirmation 的前置条件。
6. 在每份标准开头标记“内部评语不直接复制进论文”；故事线的正文写作要求改成正向表述：统一问题、机制、接口、证据和边界。
7. 评分仍保持严格：核心项最低分、硬门槛、双人取低分、证据路径和独立重算全部保留；不以提高总分为目的删掉负结果或放宽泄漏/真值规则。

## 4. 建议的复核问题

下次用 v004 候选重评分时，先逐项回答：

1. 这是在判定“组件是否新”，还是在判定“整体是否对目标失败形成必要且可验证的解决方案”？
2. 当前 dynamic claim 属于 feedback-adaptive、environment-nonstationary 还是 both？标准是否只要求相应证据？
3. 这一项是在决定能否开始 confirmation，还是在评价 confirmation 完成后的论文主结果？
4. 评分表中的词是否可能原样出现在论文里而削弱正向叙事？
5. 如果组合带来同等准确率但更低调用成本、更小延迟或更强审计能力，评分是否允许它通过？

## 5. 本审查不做的事

本记录不推翻故事线、动态 JEV 候选、benchmark 或 baseline；也不把组合贡献预先宣布为已证实。它只要求评价标准以整体任务贡献、可验证机制和证据闭环来判分，并把尚未完成的确认和实验继续留作待验证事项。
